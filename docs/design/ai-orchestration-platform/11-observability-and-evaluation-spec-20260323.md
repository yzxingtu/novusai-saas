# AI 编排与工作流平台可观测性与评估规范（2026-03-23）

## 一、文档目标

本文档用于定义平台在“上线后”必须具备的两套能力：

1. `observability`：看得见系统和业务是否正常。
2. `evaluation`：知道 AI 输出和工作流结果是否真的有效。

如果没有这两套能力，平台只能做到“能跑”，做不到：

- 可治理
- 可优化
- 可追责
- 可持续交付

本文档是平台级规范，不绑定具体行业。

---

## 二、核心结论

### 2.1 监控不等于评估

两者必须明确区分：

- 监控回答“系统有没有出问题”
- 评估回答“结果好不好、值不值得继续跑”

例如：

- 成功返回 200，不代表输出质量合格
- 工作流执行完成，不代表业务目标达成

### 2.2 可观测性至少要覆盖四层

建议平台至少同时看四层：

1. 基础设施层
2. 运行时层
3. AI 质量层
4. 业务结果层

### 2.3 评估必须绑定到版本

所有评估结果都不应只归到“某个工作流”或“某个 Agent”，而应尽量绑定到：

- 工作流版本
- Agent 版本
- 方案包版本
- 企业副本版本

否则后续无法比较升级前后差异。

### 2.4 管理端和企业端看到的观测视图必须不同

管理端看的是：

- 跨企业治理
- 全局成本
- 风险命中
- 模板故障率

企业端看的是：

- 本企业运行效果
- 本企业审批耗时
- 本企业草稿质量
- 本企业 ROI 或业务改善

### 2.5 第一阶段先做“可解释可追踪”，再做“自动评分”

第一阶段不建议一上来追求复杂 AI 评分系统。

优先级建议：

1. 跑一次要能回放
2. 每一步要有证据
3. 成本、耗时、失败原因要可见
4. 再逐步增加自动评估与对比

---

## 三、为什么这份文档是必需的

前面的文档已经解决了：

- 平台架构
- 授权和计费
- 审批和风险闸门
- 构建器边界
- 触发与发布
- 定制交付模型

但如果没有观测与评估，平台上线后仍会遇到以下问题：

- 不知道哪个模板最耗钱
- 不知道哪个节点最容易失败
- 不知道某次版本升级到底变好还是变差
- 不知道企业说“效果不好”到底指哪一步不好

所以这份文档是从“能设计”迈向“能运营”的关键一环。

---

## 四、定义两套体系

### 4.1 `Observability`

指对系统、运行实例、调用链、成本、风险、审批和异常的持续可见能力。

它回答：

- 发生了什么
- 在哪里发生
- 为什么失败
- 成本是多少
- 哪一层出问题

### 4.2 `Evaluation`

指对 AI 输出质量、业务适用性、策略命中率和版本效果的判断能力。

它回答：

- 结果质量怎么样
- 是否符合规则
- 是否比旧版本更好
- 是否真正帮助业务

---

## 五、四层可观测性模型

### 5.1 基础设施层

关注：

- HTTP 请求
- Celery 队列
- WebSocket 状态
- 数据库连接池
- Redis
- 插件运行健康

这一层可优先复用当前项目已有的 Prometheus + Grafana 监控基础。

### 5.2 运行时层

关注：

- `WorkflowRun` 成功率
- `WorkflowNodeRun` 耗时和失败率
- 触发器成功率
- 审批等待时长
- 版本分布
- 回滚次数

### 5.3 AI 质量层

关注：

- 模型调用成功率
- Token 与成本
- 联网来源质量
- Prompt 命中质量
- 输出结构化合格率
- 人工驳回率

### 5.4 业务结果层

关注：

- 草稿采用率
- 审核通过率
- 复盘建议采纳率
- 周期性业务改善指标
- 企业满意度

## 七、工作流运行观测模型

### 7.1 每个 `WorkflowRun` 至少要能回答什么

建议每个运行实例至少要能回答：

1. 谁触发的
2. 用的哪个版本
3. 跑了哪些节点
4. 卡在哪一层
5. 花了多少钱
6. 是否经过审批
7. 最终结果是什么

### 7.2 每个 `WorkflowNodeRun` 至少要能回答什么

建议每个节点至少要能回答：

1. 输入是什么
2. 输出是什么
3. 使用了哪个 Agent / Skill / 模型
4. 耗时多少
5. 失败原因是什么
6. 产生了哪些 Artifact

### 7.3 关键运行指标建议

| 指标 | 含义 |
|---|---|
| `workflow_run_total` | 总运行次数 |
| `workflow_run_success_rate` | 运行成功率 |
| `workflow_run_p95_duration` | P95 总耗时 |
| `workflow_node_failure_rate` | 节点失败率 |
| `workflow_approval_wait_seconds` | 审批等待耗时 |
| `workflow_cost_per_run` | 单次运行平均成本 |
| `workflow_retry_rate` | 重试率 |

## 八、评估对象分层

评估对象建议至少分 5 层：

1. 节点级评估
2. 工作流级评估
3. Agent 级评估
4. 方案包级评估
5. 企业级评估

### 8.1 节点级评估

适合回答：

- 某个 Prompt 节点输出是否结构化合格
- 某个联网节点引用是否充分
- 某个审核节点误杀率是否过高

### 8.2 工作流级评估

适合回答：

- 这条流程是否达成目标
- 总体成功率和采用率如何
- 哪一步拉低了整体效果

### 8.3 Agent 级评估

适合回答：

- 某个 Agent 预设是否稳定
- 某个 Agent 版本是否比上个版本更好

### 8.4 方案包级评估

适合回答：

- 某个行业方案在不同企业上的效果如何
- 哪个模板组合最有价值

### 8.5 企业级评估

适合回答：

- 该企业投入这套平台后，是否真的取得业务收益

---

## 九、评估维度建议

建议把评估维度正式分成 6 类：

| 维度 | 说明 |
|---|---|
| `correctness` | 结果是否正确或合理 |
| `groundedness` | 是否有足够证据支撑 |
| `policy_compliance` | 是否符合审批、品牌、合规和平台规则 |
| `usability` | 结果是否可直接被业务使用 |
| `efficiency` | 成本、耗时是否合理 |
| `business_impact` | 是否带来业务提升 |

### 9.1 不同行业看重的维度不同

例如：

- 内容行业更看重可用性、风格一致性、审核通过率
- 电商分析更看重正确性、预测偏差、建议可执行性

所以平台要给统一维度框架，但允许行业样板再细化。

## 十、评估方法建议

### 10.1 第一阶段建议采用四种评估方法

1. 规则评估
2. 人工评估
3. 对比评估
4. 结果评估

### 10.2 规则评估

适用于：

- 输出格式校验
- 结构字段完整性
- 敏感词和规则检查
- 证据是否齐全

### 10.3 人工评估

适用于：

- 草稿质量
- 风格一致性
- 建议是否可执行
- 复盘是否有价值

### 10.4 对比评估

适用于：

- 新旧版本对比
- 模板 A/B 对比
- Prompt 变体对比

### 10.5 结果评估

适用于：

- 最终草稿是否被采用
- 审核是否通过
- 是否触发业务结果改善

---

## 十一、版本级评估模型

### 11.1 为什么评估必须绑定版本

如果不绑定版本，就会出现：

- 今天结果好，明天结果差，但不知道是哪个改动导致的
- 无法判断一次升级到底是否有效

### 11.2 建议绑定的版本对象

建议评估至少绑定：

- `workflow_template_version`
- `tenant_workflow_version`
- `agent_version`
- `plugin_version`
- `release_id`

### 11.3 评估结论应支持版本对比

建议后续平台支持至少三类对比：

- 当前版本 vs 上一个稳定版本
- 平台标准版 vs 企业定制版
- 模板 A vs 模板 B

---

## 十二、评分与标签模型

第一阶段不一定要上很复杂的绝对评分，但建议至少支持：

- 评估标签
- 简单分数
- 评估备注

### 12.1 建议标签

例如：

- `usable`
- `needs_revision`
- `policy_risk`
- `low_confidence`
- `high_cost`
- `high_value`

### 12.2 建议评分范围

第一阶段可用：

- `pass / warning / fail`

或：

- `1-5` 星

不必一开始就追求复杂的 100 分体系。

---

## 十三、企业端与管理端的观测视图

### 13.1 管理端视图

建议重点展示：

- 全局运行量
- 全局成本
- 模板成功率
- 高风险运行数量
- 审批命中率
- 方案包采用率
- 企业分布和异常企业

### 13.2 企业端视图

建议重点展示：

- 本企业运行量
- 本企业成本
- 本企业审核通过率
- 本企业草稿采用率
- 本企业耗时趋势
- 本企业复盘结论

### 13.3 端隔离原则

管理端可看全局。

企业端只能看本企业。

不要把当前 Admin 级监控直接原样开放到 Tenant 端。

---

## 十四、评估数据来源

建议评估数据来源至少有 5 类：

1. 运行时 Artifact
2. 审批决策
3. AI 操作审计日志
4. 人工反馈
5. 业务结果回写

### 14.1 Artifact

来自：

- Prompt
- 输出
- 联网来源
- 预览包
- 审批包

### 14.2 审批决策

可用于衡量：

- 被驳回原因
- 高风险命中点
- 哪些模板最容易被否决

### 14.3 人工反馈

建议企业端支持对结果进行：

- 采用
- 退回
- 改写
- 标注问题类型

### 14.4 业务结果回写

例如：

- 草稿是否最终发布
- 选题是否被采纳
- 建议是否带来转化提升

---

## 十五、评估生命周期

建议把评估分成四个时点：

1. 运行时即时评估
2. 审批时评估
3. 结果产出后评估
4. 周期性复盘评估

### 15.1 运行时即时评估

适合：

- 结构校验
- 风险打标
- 输出质量初检

### 15.2 审批时评估

适合：

- 审批人判断结果可用性
- 记录驳回原因

### 15.3 结果产出后评估

适合：

- 草稿采用率
- 业务使用率

### 15.4 周期性复盘评估

适合：

- 按周或按月比较版本表现
- 识别是否需要回滚或优化

---

## 十六、报警与治理建议

### 16.1 平台级报警

建议至少覆盖：

- 某模板失败率异常升高
- 某节点耗时异常
- 某企业成本异常飙升
- 审批积压异常
- 某方案包驳回率异常

### 16.2 企业级提醒

建议企业端至少可收到：

- 审批积压提醒
- 运行失败提醒
- 成本阈值提醒
- 结果低质量提醒

### 16.3 报警不是目的，治理动作才是目的

建议每类报警尽量绑定可执行动作：

- 暂停触发器
- 下线版本
- 提高审批等级
- 切换回稳定版本

## 十八、第一阶段实施建议

### Phase 1：先把“可回放 + 可统计”做出来

优先建设：

- Run / NodeRun / Artifact 查询
- 审批耗时统计
- 成本统计
- 版本绑定

### Phase 2：再补“人工反馈 + 规则评估”

补齐：

- 人工采用/退回标注
- 结果标签
- 规则校验结果沉淀

### Phase 3：最后做“版本对比 + 自动评估”

补齐：

- 版本 A/B 对比
- 行业包版本效果对比
- 自动评分与回滚建议

---

## 十九、关键结论

1. 监控和评估必须分开建模，前者解决“有没有问题”，后者解决“效果好不好”。
2. 平台至少应覆盖基础设施层、运行时层、AI 质量层、业务结果层四层可观测性。
3. 评估必须尽量绑定到工作流版本、Agent 版本、方案包版本和企业副本版本，否则无法判断升级效果。
4. 管理端和企业端必须看到不同的观测视图，管理端看全局治理，企业端只看本企业业务效果。
5. 第一阶段先把运行回放、成本统计、审批统计、人工反馈做扎实，再逐步增加自动评估与版本对比。
6. 平台现有的 Prometheus/Grafana、AI 审计日志、调用计量和插件健康能力可以直接作为这一规范的实施基础。

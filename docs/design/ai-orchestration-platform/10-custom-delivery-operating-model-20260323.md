# AI 编排与工作流平台定制交付运营模型（2026-03-23）

## 一、文档目标

本文档用于定义平台的“企业定制交付”应如何运营，而不是只把它当成一个计费项。

需要解决的问题包括：

1. 什么情况属于标准方案，什么情况属于定制交付。
2. 定制交付从售前到验收、上线、升级、接管的完整流程是什么。
3. 管理端和企业端在交付期间分别负责什么。
4. 复杂代码型工作流为什么只能由管理端制作，以及交付后如何控制边界。
5. 如何避免“卖完一套之后就变成长期人工代运营”。

本文档是平台级运营模型，不绑定某个具体行业。

---

## 二、核心结论

### 2.1 定制交付不是“企业自己做不出来的工作流”，而是“平台托管生产能力”

平台上的复杂能力之所以要做成定制交付，不是因为企业不会点页面，而是因为它本身涉及：

- 代码执行逻辑
- 连接器接入
- 系统级执行器
- 高风险写操作
- 行业特定运行策略

这些都属于平台生产能力，不应下放到企业端。

### 2.2 定制交付必须挂在“平台内核 + 标准方案包”之上，而不是从零起项目

建议原则：

- 先有平台内核
- 再有标准行业方案包
- 最后才有企业定制交付

定制交付应该是“在标准能力之上的受控扩展”，而不是每个客户一套完全独立系统。

### 2.3 定制交付要区分三种交付形态

建议正式区分：

1. `managed_locked_delivery`
2. `managed_partial_delivery`
3. `tenant_operated_delivery`

说明：

- `managed_locked_delivery`：平台持续托管，企业只用不改。
- `managed_partial_delivery`：平台托管核心结构，企业可调部分参数和低风险节点。
- `tenant_operated_delivery`：平台完成交付后，企业接管日常运行与部分迭代。

### 2.4 日常运营权仍然遵守“谁拥有工作流谁管理”

即使是定制交付，也不能自动推导为“平台方永久代企业运营”。

正确做法是：

- 平台负责开发、发布、升级、回滚、风险治理
- 企业负责使用、审批、业务配置、运行结果复盘

只有在显式签约“托管运营服务”时，平台才额外承担运营职责。

### 2.5 复杂代码型工作流永远不能直接放给企业自行开发

这条必须写死：

- 企业端不允许新增代码节点
- 企业端不允许新增连接器
- 企业端不允许修改平台托管执行器
- 企业端不允许直接修改交付包中的系统级逻辑

---

## 三、为什么还需要单独写这份文档

现有文档已经回答了：

- 平台架构是什么
- 授权和计费怎么做
- 行业方案插件怎么包装
- 工作流构建器开放到什么程度

但还没有回答：

- 当一个企业提出复杂定制需求时，平台内部怎么接单
- 标准方案和定制方案怎么分界
- 交付给企业的是“模板”“插件”“副本”还是“托管服务”
- 验收标准、变更申请、升级责任怎么划分

这部分如果不单独建模，后面平台很容易陷入：

- 每个客户都做成一次性项目
- 交付物边界不清
- 平台团队被企业拖进日常运营
- 标准产品能力无法沉淀

---

## 四、定制交付适用边界

### 4.1 什么情况不应进入定制交付

以下场景优先走标准产品能力：

- 企业只需要启用标准行业包
- 企业只需要配置企业知识、素材和审批人
- 企业只需要复制平台模板后做简单改动
- 企业只需要企业简单工作流

这些情况不应被包装成定制交付。

### 4.2 什么情况应进入定制交付

建议以下场景进入定制交付：

1. 需要新的系统级连接器。
2. 需要新的执行器或托管代码逻辑。
3. 需要跨系统复杂数据流。
4. 需要高风险动作的专门风险模型。
5. 需要企业专属页面、企业专属模板簇、企业专属运行策略。
6. 需要与企业内部复杂流程深度集成。

### 4.3 一个关键判断标准

如果需求满足下面任一项，就不要让企业自己做：

- 需要写代码
- 需要扩展平台能力
- 需要修改运行时内核
- 需要突破企业简单构建器白名单

## 五、交付对象分层

建议把“定制交付”拆成 5 种交付对象，而不是只理解为“交一个工作流”。

| 交付对象 | 说明 | 是否可企业自管 |
|---|---|---|
| `custom_connector` | 企业专属或行业专属连接器 | 否 |
| `managed_workflow_template` | 平台托管模板 | 部分可 |
| `tenant_workflow_copy` | 企业副本 | 可 |
| `custom_agent_profile` | 企业专属 Agent 预设 | 部分可 |
| `solution_plugin_extension` | 挂在方案插件下的增强包 | 否或部分可 |

### 5.1 实际交付通常是组合包

多数企业定制交付不是交一个单独对象，而是一个组合：

```text
方案插件
-> 托管模板
-> 企业配置 Schema
-> 企业副本
-> 审批预设
-> 专属 Agent 预设
```

---

## 六、三种交付形态

### 6.1 `managed_locked_delivery`

适用：

- 高风险流程
- 涉及复杂连接器
- 涉及高价值业务逻辑

特点：

- 平台全权维护结构
- 企业只能配置参数和业务知识
- 企业不能改核心流程结构
- 升级和回滚由平台负责

### 6.2 `managed_partial_delivery`

适用：

- 有平台托管内核
- 但允许企业做低风险本地化调整

特点：

- 平台锁定核心片段
- 企业可改可编辑片段
- 企业可管理审批人、文案、业务字段映射

### 6.3 `tenant_operated_delivery`

适用：

- 平台已完成复杂能力建设
- 企业具备一定运营能力
- 风险和权限边界已收口

特点：

- 平台完成首次交付
- 企业接管日常发布、触发器、审批和运营
- 平台仍保留高危能力和系统逻辑控制权

---

## 七、交付流程总览

建议定制交付至少拆成 8 个阶段：

1. 需求分流
2. 方案评估
3. 商务报价
4. 需求冻结
5. 实施交付
6. 内部验收
7. 企业验收
8. 上线与交接

### 7.1 流程图

```text
线索进入
-> 判断标准方案 or 定制交付
-> 交付评估
-> 报价与签约
-> 需求冻结
-> 平台实施
-> 内部测试
-> 企业 UAT
-> 发布到指定企业
-> 交接与运维
```

---

## 八、阶段一：需求分流

### 8.1 先分流，不要直接接需求开发

建议管理端先做“需求分流台”：

- 标准方案可解决
- 标准方案 + 企业配置可解决
- 标准方案 + 模板复制可解决
- 必须进入定制交付

### 8.2 分流标准建议

| 问题 | 如果答案是“是” | 建议 |
|---|---|---|
| 是否需要新增代码逻辑 | 是 | 进入定制交付 |
| 是否需要新增连接器 | 是 | 进入定制交付 |
| 是否标准方案已能覆盖 80% | 是 | 优先走标准方案 |
| 是否只是企业知识和配置问题 | 是 | 不进入定制交付 |
| 是否需要高风险动作 | 是 | 进入定制交付评估 |

---

## 九、阶段二：方案评估

### 9.1 评估不只是技术评估

建议至少做四类评估：

1. 业务价值评估
2. 平台复用评估
3. 风险与合规评估
4. 实施成本评估

### 9.2 评估结果建议分类

- `reject`
- `redirect_to_standard`
- `accept_as_custom_delivery`
- `accept_and_productize_first`

### 9.3 什么叫 `accept_and_productize_first`

有些需求虽然来自单个企业，但明显有行业共性。

此时建议先沉淀为平台能力或方案插件能力，再交付给该企业。

这样可以避免平台长期积累大量单客户专属逻辑。

---

## 十、阶段三：报价与签约

### 10.1 报价应拆成两部分

建议继续坚持你前面确定的“两重收费”表达，但在定制交付里要再细化：

1. 平台使用费 / 方案授权费
2. 定制交付费 / 托管服务费

### 10.2 定制交付费建议拆项

例如：

- 需求分析费
- 交付开发费
- 联调测试费
- 上线支持费
- 年度托管维护费

### 10.3 合同里必须写清的边界

至少要写清：

- 交付对象是什么
- 什么不在本次交付范围内
- 企业是否可修改交付物
- 升级和回滚由谁负责
- 是否包含持续托管服务

---

## 十一、阶段四：需求冻结

### 11.1 需求冻结是必须节点

没有冻结点，定制交付会无限膨胀。

建议冻结以下内容：

- 业务目标
- 数据来源
- 交付范围
- 风险边界
- 审批要求
- 验收标准

### 11.2 建议形成交付规格包

每次定制交付建议产出一份 `delivery_spec_bundle`，至少包含：

- 业务背景
- 流程图
- 节点清单
- 集成清单
- 审批闸门
- 输入输出 Schema
- 验收口径

---

## 十二、阶段五：实施交付

### 12.1 实施应优先复用，不要先写代码

实施顺序建议：

1. 复用平台已有能力
2. 复用现有行业方案插件
3. 复用现有托管模板
4. 最后才新增托管代码或连接器

### 12.2 交付形式建议

根据复杂度，交付物可以是：

- 新的方案插件增强包
- 新的托管模板
- 指定企业的企业副本
- 新的专属连接器
- 新的专属 Agent 预设

### 12.3 复杂代码只能放在平台托管侧

任何涉及代码的交付，都建议作为：

- 平台插件
- 平台托管执行器
- 平台模板

而不是直接放进企业工作流编辑区。

---

## 十三、阶段六：内部验收

### 13.1 平台内部先验收，再给企业验收

内部验收至少包括：

- 权限与授权验证
- 风险闸门验证
- 触发器验证
- 运行回放验证
- 成本与并发验证
- 失败与回滚验证

### 13.2 内部验收产物建议

建议至少产出：

- 测试报告
- 风险清单
- 已知限制清单
- 上线建议

---

## 十四、阶段七：企业验收

### 14.1 企业验收不是“看页面差不多就算过”

建议企业验收分三层：

1. 功能验收
2. 业务验收
3. 风险验收

### 14.2 功能验收

关注：

- 流程是否能跑通
- 数据是否接通
- 输出格式是否正确

### 14.3 业务验收

关注：

- 是否解决真实业务问题
- 输出是否可被企业团队使用
- 审批和草稿流是否符合组织习惯

### 14.4 风险验收

关注：

- 是否存在越权动作
- 是否存在缺失审批
- 是否存在不应自动执行的步骤

### 14.5 验收状态建议

建议与前文商业状态打通：

- `delivered`
- `accepted`
- `accepted_with_limitations`
- `rework_required`

---

## 十五、阶段八：上线与交接

### 15.1 上线不是“直接给企业开放”

建议上线分三步：

1. 发布到 `selected_tenants`
2. 小范围启用
3. 正式切换触发器和生产入口

### 15.2 交接内容建议

企业正式接收时，建议同时交接：

- 工作流说明
- 触发器说明
- 审批说明
- 异常处理手册
- 升级和支持说明

### 15.3 交接后谁管理什么

交接后建议按对象区分：

| 对象 | 平台 | 企业 |
|---|---|---|
| 平台托管代码 | 管理 | 不可改 |
| 连接器实现 | 管理 | 不可改 |
| 企业知识与素材 | 不管理 | 管理 |
| 企业审批人 | 不管理 | 管理 |
| 企业触发器启停 | 视模式而定 | 通常管理 |
| 企业日常运行 | 只治理 | 管理 |

---

## 十六、升级、变更与返工模型

### 16.1 定制交付必须有变更申请机制

交付后新增需求不应直接塞回原交付单。

建议区分：

- `defect_fix`
- `minor_change`
- `major_change`
- `new_delivery_request`

### 16.2 哪些属于缺陷修复

例如：

- 与规格不符
- 权限校验错误
- 审批缺失
- 输出字段错误

### 16.3 哪些属于新增需求

例如：

- 新接一个系统
- 新增一整条流程
- 新增高风险动作
- 新增企业用户端入口

这些应进入新的评估与报价流程。

---

## 十七、定制交付与标准产品沉淀的关系

### 17.1 平台不能只做项目，不做产品沉淀

建议每次定制交付结束后做一次归档判断：

- 哪些能力是客户专属
- 哪些能力有行业通用性
- 哪些能力应反向沉淀进标准方案包

### 17.2 沉淀优先级建议

优先沉淀：

- 通用连接器
- 通用审批预设
- 通用模板结构
- 通用企业配置 Schema

### 17.3 不应沉淀的内容

通常不建议沉淀到标准产品里的内容：

- 客户专属业务术语
- 客户专属敏感流程
- 客户专属品牌规则
- 客户专属私有数据映射

---

## 十八、管理端页面建议

建议在管理端增加专门的“定制交付中心”，至少包含：

- 交付线索池
- 交付项目列表
- 评估与报价页
- 需求冻结页
- 交付物清单页
- 企业验收页
- 上线与回滚页

### 18.1 企业端需要什么页面

企业端不需要看到整套交付项目管理，只需要看到：

- 已交付能力
- 当前启用版本
- 交付说明
- 验收结果
- 升级通知

## 二十、第一阶段实施建议

### Phase 1：先把“交付记录 + 交付边界”做出来

优先建设：

- `custom_delivery_records`
- 交付模式枚举
- 交付状态流转
- 企业可见的交付结果页

### Phase 2：再补“需求冻结 + 验收包”

补齐：

- 规格包
- 验收包
- 已知限制清单

### Phase 3：最后补“变更管理 + 产品沉淀回流”

补齐：

- 变更申请
- 沉淀建议
- 标准能力回流机制

## 二十一、关键结论

1. 定制交付本质上是平台托管生产能力，不应被理解为“把开发能力下放给企业”。
2. 定制交付必须建立在平台内核和标准方案包之上，而不是每个客户从零做一套系统。
3. 建议正式区分 `managed_locked_delivery`、`managed_partial_delivery`、`tenant_operated_delivery` 三种交付形态。
4. 复杂代码型工作流、连接器和执行器永远只能由管理端制作和托管，企业端不能自行开发。
5. 定制交付必须有明确的分流、评估、冻结、实施、验收、上线、交接和变更流程，否则平台会被项目化拖垮。
6. 交付后的日常业务运营仍应由企业负责，平台只在显式托管协议下承担额外运营职责。
7. 每次定制交付结束后都应判断哪些能力应沉淀回标准产品和标准方案包。

# AI 编排与工作流平台运行时预算、配额与成本守卫规范（2026-03-23）

## 一、文档目标

本文档用于定义平台在工作流运行、Agent 调度、联网分析、审批等待、Artifact 生成、企业运营过程中，应该如何治理预算、配额与成本。

前面的文档已经回答了：

- 套餐和授权怎么做
- 运行时策略怎么裁决
- 数据契约如何控制上下文
- 运行图如何恢复和补偿
- 企业运营控制台怎么看运行和结果

但如果没有预算、配额和成本守卫，平台很快会遇到另外一类问题：

1. 企业工作流能跑，但成本失控。
2. `agentic` 模式可以连续规划，但没人知道一步步花了多少钱。
3. 预算用完时系统是暂停、降级、审批还是直接失败，没有统一规则。
4. 一个企业或一个行业方案的高成本行为会拖垮整个平台队列和商业模型。

所以，这份文档要解决的是：

> 平台如何把“能运行”升级为“能在预算、配额和成本边界内稳定运行”。

---

## 二、核心结论

### 2.1 成本治理不是计费后台的事，而是运行时内核的一部分

很多系统把成本治理放到月底报表里看，但 AI 编排平台不行。

原因：

- 模型调用是实时成本
- 联网和大上下文也是实时成本
- 并行节点、重试、补偿、回放都会放大成本

所以预算守卫必须进入：

- 运行前
- 节点执行前
- 运行中
- 恢复与重试时

### 2.2 必须同时区分“配额”“预算”“实际成本”

建议正式区分三个概念：

1. `quota`
2. `budget`
3. `actual_cost`

说明：

- `quota` 是套餐或授权层规定的资源上限
- `budget` 是某次运行、某个工作流、某个企业当前愿意或允许消耗的额度
- `actual_cost` 是已经实际发生的消耗

这三个不拆开，后面规则一定混乱。

### 2.3 成本守卫必须分层，不能只在企业月额度层拦一次

建议至少分成：

1. 平台全局层
2. 企业套餐层
3. 行业方案层
4. 工作流层
5. 单次运行层
6. 节点层

这样才能避免：

- 企业没超月额度，但某一次单跑就花爆
- 某行业方案总是异常贵，却没有单独守卫
- 某个节点无限重试导致成本飙升

### 2.4 预算耗尽后的动作必须标准化

预算不是只用来报警的。

建议平台统一定义几类动作：

- `allow`
- `warn`
- `pause_for_confirmation`
- `pause_for_approval`
- `degrade`
- `deny`

### 2.5 高自治模式必须带更强的预算守卫

`agentic` 和 `L4` 模式最大的风险之一，不只是业务动作，而是：

- 连续思考
- 连续调用工具
- 连续联网
- 连续重试

因此高自治必须同时带：

- 成本预算
- 步数预算
- 工具调用预算
- 时间预算

---

## 三、为什么必须单独写这份文档

前面的 `04-billing-and-entitlement-spec` 更偏商业授权。

但运行时成本治理还有大量更细的问题：

- 某次工作流是否允许消耗 10 元还是 100 元
- 某个节点最多允许联网几次
- 某条恢复链最多允许重试几轮
- 成本超线时是直接停，还是降级到便宜模型

如果这些不单独定义，后面一定会出现：

1. 计费系统知道花了多少钱，但运行时已经来不及阻止。
2. 运营人员看到成本超标，却没有标准动作。
3. 企业套餐和工作流预算互相打架。

所以，这份文档是在回答：

> 平台如何把成本、配额和预算从“事后报表”变成“运行时守卫”。

---

## 四、正式对象模型

建议把预算和配额治理相关对象正式抽出来。

### 4.1 核心对象建议

| 对象 | 作用 |
|---|---|
| `quota_policy` | 套餐或授权层的配额规则 |
| `budget_policy` | 某个作用域下的预算规则 |
| `runtime_budget_snapshot` | 一次运行使用的预算快照 |
| `runtime_budget_meter` | 一次运行中的实时消耗计量器 |
| `cost_event` | 单次消耗事件 |
| `budget_guard_decision` | 某次预算守卫决策结果 |
| `cost_allocation_record` | 消耗分摊记录 |
| `cost_guard_alert` | 成本守卫告警 |

### 4.2 为什么需要 `runtime_budget_snapshot`

因为同一个工作流版本，在不同时间、不同企业、不同套餐下，预算可能不一样。

所以每次运行都应固化：

- 当时允许多少
- 从哪些层汇总而来
- 哪些守卫规则在生效

---

## 五、正式概念定义

### 5.1 `quota`

定义：

- 在某个时间窗口内可使用的资源上限

典型例子：

- 每月运行次数
- 每月模型调用额度
- 每月联网调用次数
- 最大并发运行数

### 5.2 `budget`

定义：

- 为某次运行、某类工作流、某个方案、某个审批阶段预先设定的可消耗额度

典型例子：

- 单次运行最多 5 元
- 单个节点最多消耗 0.5 元
- 单次规划最多 8 步

### 5.3 `actual_cost`

定义：

- 已经真实发生的成本

典型例子：

- Token 成本
- 外部 API 成本
- 存储和检索成本
- 人工审核成本估算

### 5.4 `forecast_cost`

定义：

- 在执行前或执行中估算接下来大概率还会消耗多少

这个概念很重要，因为很多守卫不是看“已花多少”，而是看：

- 如果继续跑，大概率会不会超预算

---

## 六、预算与配额的分层模型

### 6.1 平台全局层 `platform_global_guard`

目标：

- 防止平台级灾难性成本失控

适合限制：

- 全平台并发上限
- 全平台高成本模型调用速率
- 全平台异常重试风暴

### 6.2 企业套餐层 `tenant_quota_guard`

目标：

- 执行 `TenantPlan` 和企业授权中的资源边界

适合限制：

- 每月运行次数
- 每月模型额度
- 每日联网调用上限
- 最大激活工作流数

### 6.3 行业方案层 `solution_budget_guard`

目标：

- 控制某个行业方案包的典型成本边界

适合限制：

- 某方案单次分析预算
- 某方案默认模型池
- 某方案最大联网深度

### 6.4 工作流层 `workflow_budget_guard`

目标：

- 控制某条工作流的总体预算和运行上限

适合限制：

- 单次运行预算
- 最大步数
- 最大并行分支数
- 最大恢复次数

### 6.5 节点层 `node_budget_guard`

目标：

- 控制单节点的细粒度消耗

适合限制：

- 单节点 Token 上限
- 单节点联网次数
- 单节点外部调用次数
- 单节点超时

---

## 七、预算维度建议

成本不应只看人民币金额，平台应至少维护多维预算。

### 7.1 建议的预算维度

| 维度 | 说明 |
|---|---|
| `money_budget` | 货币成本预算 |
| `token_budget` | Token 预算 |
| `step_budget` | 规划与执行步数预算 |
| `tool_call_budget` | 工具调用次数预算 |
| `web_fetch_budget` | 联网/检索次数预算 |
| `artifact_budget` | Artifact 数量或大小预算 |
| `duration_budget` | 总耗时预算 |
| `retry_budget` | 重试次数预算 |
| `approval_wait_budget` | 审批等待时间预算 |

### 7.2 为什么必须是多维

因为很多时候：

- 钱还没超
- 但步骤已经失控
- 或联网次数已经异常
- 或重试已经不合理

如果只看一个金额数字，治理会很迟钝。

---

## 八、预算来源与合并规则

一次运行的预算通常来自多层来源，不应由单一页面临时写死。

### 8.1 预算来源建议

| 来源 | 说明 |
|---|---|
| 平台基线 | 平台最低或最高边界 |
| 套餐配额 | `TenantPlan.features` / `TenantPlan.quota` |
| 方案默认预算 | 行业方案建议预算 |
| 企业覆盖预算 | 企业可自行加严 |
| 工作流局部预算 | 某条工作流的局部守卫 |
| 节点局部预算 | 某个节点的预算限制 |

### 8.2 合并原则建议

建议遵守：

```text
平台基线
-> 套餐配额
-> 方案默认预算
-> 企业覆盖预算
-> 工作流局部预算
-> 节点局部预算
```

总体原则：

- 下层可以加严
- 下层不能突破上层硬上限

### 8.3 为什么企业预算默认只能加严

因为企业本地不能借由“预算配置”来绕过：

- 套餐限制
- 高风险能力限制
- 平台全局保护阈值

---

## 九、预算状态与守卫动作

### 9.1 建议的预算状态

| 状态 | 说明 |
|---|---|
| `healthy` | 远低于阈值 |
| `warning` | 接近阈值 |
| `projected_overrun` | 预测继续执行会超线 |
| `hard_exceeded` | 已经超线 |
| `guarded_pause` | 因预算守卫而暂停 |

### 9.2 建议的守卫动作

| 动作 | 说明 |
|---|---|
| `allow` | 继续执行 |
| `warn` | 记录并提醒 |
| `pause_for_confirmation` | 暂停等待请求人确认 |
| `pause_for_approval` | 暂停进入正式审批 |
| `degrade` | 降级到更便宜策略 |
| `deny` | 直接阻断 |

### 9.3 `degrade` 的正式含义

建议仅允许在白名单场景降级，例如：

- 切换到成本更低的模型
- 减少检索深度
- 关闭次要证据召回
- 缩短上下文

不应把 `degrade` 理解为“偷偷输出一个明显质量更差的东西”，必须让平台和企业都可见。

---

## 十、预测成本与提前守卫

### 10.1 只看已发生成本不够

很多流程到了真正超线时已经来不及。

例如：

- `agentic` 模式已经规划了 20 步
- 大上下文节点已经构建完成
- 外部高价接口已经准备调用

所以平台必须支持：

- `forecast_cost`

### 10.2 建议的预测输入

预测时至少结合：

- 当前已消耗成本
- 剩余计划步数
- 节点历史平均成本
- 当前模型和工具类型
- 当前上下文大小

### 10.3 预测成本触发的典型动作

例如：

- 提前提醒
- 暂停等待确认
- 降级运行
- 拒绝继续扩图

---

## 十一、不同节点类型的成本守卫

### 11.1 `llm` / `planner` 节点

建议重点守卫：

- Token 预算
- 输出长度
- 最大重试次数
- 规划步数上限

### 11.2 `knowledge_lookup` / `web_search` 节点

建议重点守卫：

- 联网次数
- 单次抓取数量
- 单次检索结果预算
- 证据摘要大小

### 11.3 `data_read` 节点

建议重点守卫：

- 查询规模
- 返回结果行数
- 大表读取限制

### 11.4 `external_write` 节点

建议重点守卫：

- 调用次数
- 幂等重试预算
- 失败后人工介入阈值

### 11.5 恢复与补偿节点

建议重点守卫：

- 最大恢复次数
- 最大补偿次数
- 不确定状态人工接管阈值

---

## 十二、与自治等级和审批的关系

### 12.1 高自治默认需要更紧预算

建议至少遵守：

| 自治等级 | 预算策略 |
|---|---|
| `L1` | 可使用标准预算 |
| `L2` | 可略放宽，但仍需明确上限 |
| `L3` | 需要步数预算和工具预算 |
| `L4` | 需要步数预算、成本预算、审批预算、扩图预算 |

### 12.2 预算问题也可以触发审批

例如：

- 预计成本明显超出企业常规阈值
- 单次运行触发大额联网分析
- 大规模并行处理要启动

此时不一定直接拒绝，也可以：

- `pause_for_approval`

### 12.3 预算审批不是财务审批替代品

这里讨论的是运行时预算守卫审批，不是企业财务付款流程。

两者不能混淆。

---

## 十三、与套餐和授权的关系

### 13.1 套餐决定“可不可以”，预算决定“这次能花多少”

例如：

- 套餐允许使用 `agentic`
- 不代表这次运行可以无限规划

### 13.2 建议复用 `TenantPlan.quota`

`TenantPlan` 中适合承载：

- 月度运行次数
- 月度 Token 配额
- 并发数上限
- 可用模型等级

### 13.3 建议引入工作流级预算快照

套餐和授权给的是长期上限。

而单次运行还需要：

- 当前这次预算是多少
- 来自哪个方案和哪个工作流

所以建议新增：

- `runtime_budget_snapshot`

---

## 十四、企业运营控制台中的预算视图

企业端不应只在月底账单里看到成本。

### 14.1 企业端建议展示的视图

- 本月累计成本
- 本周运行成本
- 高成本工作流排行
- 高成本节点排行
- 预算预警列表
- 预算导致的暂停/终止记录

### 14.2 企业端建议的操作

- 设置提醒阈值
- 给某类工作流加严预算
- 暂停高成本低价值流程
- 提交升级套餐申请

### 14.3 企业端不应能做什么

- 放宽平台硬上限
- 绕过套餐配额
- 强制解除平台级成本冻结

---

## 十五、成本分摊与归因

### 15.1 为什么要做分摊

如果成本只记在企业总账上，后面无法回答：

- 到底是哪个方案贵
- 到底是哪条工作流贵
- 到底是哪个节点拖累

### 15.2 建议的归因维度

至少归因到：

- 企业
- 方案包
- 工作流
- 运行实例
- 节点类型
- 模型/工具

### 15.3 人工接管和审批成本也可做估算归因

虽然不一定直接计费，但至少可内部估算：

- 审批耗时成本
- 人工恢复成本
- 补偿处置成本

这样平台才能判断：

- 哪些流程看起来自动化，实际上很贵

---

## 十六、报警与治理动作

### 16.1 平台级报警

建议至少覆盖：

- 某企业预算异常突增
- 某方案单次运行成本异常
- 某节点重试风暴
- 高价模型调用异常升高

### 16.2 企业级提醒

建议至少覆盖：

- 本日预算即将耗尽
- 某条流程接近暂停阈值
- 某版本升级导致成本显著上升
- 某审批链长期卡住导致成本沉没

### 16.3 报警后的建议动作

至少支持：

- 暂停触发器
- 降级模型策略
- 要求确认
- 要求审批
- 切回稳定版

---

## 十七、与现有文档的关系

### 17.1 与 `04-billing-and-entitlement-spec`

`04` 负责商业授权与套餐语义。

`20` 负责这些套餐和授权在运行时如何变成实际预算守卫。

### 17.2 与 `12-runtime-policy-engine-spec`

预算与成本守卫应成为策略引擎的重要子域，至少可抽象为：

- `budget_policy_domain`

### 17.3 与 `16-runtime-execution-graph-and-recovery-spec`

恢复、重试、补偿本身也会消耗预算，因此恢复路径必须再次进入成本守卫判断。

### 17.4 与 `17-enterprise-operator-console-spec`

企业运营控制台应承接预算提醒、成本趋势、守卫暂停与恢复动作。

---

## 十八、第一阶段实施建议

### Phase 1：先把“预算快照 + 基础守卫 + 运行告警”做出来

优先建设：

- `runtime_budget_snapshot`
- `runtime_budget_meter`
- 基础预算守卫动作
- 企业端预算提醒

### Phase 2：再补“多维预算 + 预测成本 + 降级策略”

补齐：

- Token / Money / Step / Tool 多维预算
- `forecast_cost`
- 白名单降级策略

### Phase 3：最后补“平台/方案/企业三层联动”

补齐：

- 平台全局守卫
- 行业方案预算模板
- 企业覆盖预算
- 成本分摊与精细归因

---

## 十九、关键结论

1. 预算、配额与成本治理必须进入运行时内核，而不能只停留在事后计费报表。
2. 平台必须明确区分 `quota`、`budget` 和 `actual_cost`，并在平台、企业、方案、工作流、节点多个层次同时治理。
3. 成本守卫应支持多维预算，不仅看货币金额，还要看 Token、步数、工具调用、联网次数、耗时和重试次数。
4. 预算耗尽后的动作必须标准化，至少应支持提醒、确认、审批、降级和阻断，而不是统一报错。
5. 高自治模式必须默认带更强的预算守卫，否则 `agentic` 和 `L4` 很容易在成本层面失控。
6. 第一阶段先把预算快照、基础守卫、运行告警和企业端提醒做出来，再逐步扩展到预测成本、多维预算和三层联动治理。

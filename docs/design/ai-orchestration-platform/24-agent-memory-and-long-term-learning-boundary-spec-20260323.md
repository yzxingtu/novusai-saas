# AI 编排与工作流平台记忆与长期学习边界规范（2026-03-23）

## 一、文档目标

本文档用于定义平台中的记忆能力、长期学习能力、反馈沉淀能力之间的正式边界。

这份文档要回答的核心问题是：

1. 什么叫会话记忆，什么叫长期记忆，什么又只是运行时上下文。
2. 哪些信息可以被记住，哪些信息绝不能被记住。
3. 记忆的作用域、所有权、启用层级、清理语义应该如何设计。
4. 长期学习应来自什么信号，不应来自什么信号。
5. 平台如何避免把“记忆”做成无边界聊天堆积或无审查自学习。

本文档是平台级规范，不绑定某个行业，但会直接影响 Agent、工作流、企业控制台、评估体系、审批体系和解决方案插件的设计。

---

## 二、核心结论

### 2.1 当前仓库已经具备会话记忆起点，但尚未批准“无边界长期记忆”

从当前仓库实现看，平台已经有一套比较克制的会话记忆机制：

- 只在 `ai_chat_page` 场景生效
- 有平台默认开关
- 有管理端 Agent 开关
- 有企业侧关闭覆盖
- 有 `memory-state` 查询与清理接口
- 对会话归档、删除和 TTL 清理有兜底

这说明平台已经有可控起点。

但当前并没有证据表明平台已经批准：

- 跨会话长期记忆
- 跨工作流经验库自动积累
- 企业级无审查自学习
- 跨企业知识迁移式学习

所以后续设计必须明确区分“已落地的会话记忆”和“尚未批准的长期学习”。

### 2.2 会话记忆不等于长期记忆，长期记忆也不等于聊天记录累积

这条必须正式写入平台内核。

真正应区分的至少有：

- `runtime_context`
- `session_memory`
- `task_memory`
- `user_preference_memory`
- `enterprise_rule_memory`
- `learned_signal`
- `knowledge_base`

如果不拆开，后面就会把：

- 临时上下文
- 原始聊天
- 业务规则
- 经验反馈

全部混成一个“记忆仓”，最终既不安全，也不可治理。

### 2.3 企业规则和长期业务知识，原则上应进入配置或知识库，而不是让 Agent 私下记住

例如：

- 品牌规则
- 审批规则
- 产品知识
- 组织流程
- 固定禁用词

这些都应该优先进入：

- 配置注入
- 知识库注入
- 评估反馈资产

而不是依赖某个 Agent 的聊天记忆。

### 2.4 长期学习应主要来自结构化反馈和经过审查的结果信号，而不是原始聊天自由沉淀

平台后续真正有价值的“学习”，更应来自：

- 草稿采用率
- 驳回原因
- 编辑差异
- 业务结果标签
- 盲测评估结果
- 人工标注结论

而不是简单把历史聊天越存越多。

### 2.5 持久记忆必须具备作用域、同意、证据、清理和审计

任何会跨会话、跨运行持续存在的记忆，都不应只靠一个布尔开关生效。

它至少应回答：

- 记忆归属于谁
- 作用于哪个场景
- 什么时候写入
- 为什么写入
- 如何清理
- 谁能审核和撤销

### 2.6 第一阶段应坚持保守策略，不做无边界自学习 Agent

第一阶段推荐：

- 会话记忆继续保持强场景限制
- 长期记忆默认关闭
- 长期学习优先做“结构化反馈资产”，不直接回写成 Agent 私有记忆
- 任何会改变长期推荐行为的资产，都必须可解释、可追溯、可撤销

---

## 三、为什么必须单独写这份文档

前面的文档已经写清了：

- 企业知识如何注入
- 审批和风险如何治理
- 执行图如何恢复
- 评估资产如何治理
- 人机协作如何组织

但平台还没有系统回答另外一个核心问题：

> AI 在一次运行之后，到底什么应该被留下，什么不应该被留下。

如果不把这个问题正式写清楚，后续会出现四类典型风险：

1. 原始聊天被误当长期知识，导致污染和泄漏。
2. 企业规则被错误塞进 Agent 私有记忆，最终不可维护、不可版本化。
3. 所谓“长期学习”变成不可解释的黑盒漂移。
4. 用户想清空、撤销、纠错时，根本不知道该删哪里。

所以，这份文档是在回答：

> 平台如何把“记住一些东西”从模糊能力，变成正式受治理的数据和学习系统。

---

## 四、记忆、上下文、知识与学习的正式区分

建议平台统一采用“容器分治”思路，而不是把所有长期信息都叫 memory。

## 4.1 正式容器定义建议

| 容器 | 作用 | 生命周期 | 推荐写入方式 | 默认是否允许自动写入 |
|---|---|---|---|---|
| `runtime_context` | 当前这次运行所需的临时上下文 | 单次运行 | 运行时注入 | 是 |
| `session_memory` | 同一会话内的短期偏好、约束、事实和任务状态 | 单会话、短 TTL | 结构化提取 | 是 |
| `task_memory` | 同一任务或执行图内的中期状态、检查点和决策 | 单任务或单运行 | 执行图写入 | 是 |
| `user_preference_memory` | 用户反复确认的稳定偏好 | 跨会话、可撤销 | 显式确认或审查后写入 | 否 |
| `enterprise_rule_memory` | 企业固定规则和业务约束 | 长期 | 不建议走记忆，应转配置或 KB | 否 |
| `learned_signal` | 采用率、驳回原因、效果标签等结构化反馈信号 | 长期、版本化 | 反馈系统写入 | 是，但不直入 Prompt |
| `knowledge_base` | 长文档、案例、SOP、资料库 | 长期、版本化 | 文档治理流程写入 | 否 |

## 4.2 `runtime_context` 不属于记忆

例如：

- 当前页面筛选条件
- 当前选择的记录
- 本次触发事件 payload
- 当前审批意见补充

这些都只是当前运行的输入，不应因为被模型看过就自动升级成记忆。

## 4.3 `session_memory` 的定位应继续保持克制

会话记忆更像是：

- 本会话偏好
- 本会话约束
- 本会话任务状态
- 本会话事实摘要

它不应被理解为：

- 用户永久画像
- 企业永久知识
- 跨会话无限累积的聊天摘要

## 4.4 `enterprise_rule_memory` 原则上应被迁移为正式知识资产

企业长期有效的规则，如果真的重要，就不应依赖某次聊天偶然提取。

它应转化为：

- 配置项
- 知识库文档
- 模板变量
- 审批策略参数
- 评估标准

这样才能版本化、审计化、可回滚。

## 4.5 长期学习不等于自动修改代码、工作流和连接器

这条必须和前面“企业不可扩核、代码型工作流由平台交付”的原则保持一致。

所谓长期学习，在本平台里更合理的含义应是：

- 学到更好的推荐偏好
- 学到更稳的草稿策略
- 学到某类样本的常见驳回模式
- 学到某方案在某行业的有效提示参数

而不是：

- Agent 自行改代码
- 企业端自动生成复杂执行器
- 运行中自动篡改平台基线规则

## 五、作用域与所有权边界

## 5.1 记忆至少要有五层作用域

建议后续平台统一支持：

| 作用域 | 说明 |
|---|---|
| `conversation_scope` | 单个对话会话 |
| `task_scope` | 单个任务、单个执行图或单次审批流程 |
| `user_scope` | 某个用户的可撤销偏好 |
| `agent_scope` | 某个 Agent 的默认记忆能力配置 |
| `tenant_scope` | 某家企业的记忆与学习资产边界 |

### 5.1.1 为什么不直接做平台级共享记忆

因为一旦允许平台级共享记忆，很容易出现：

- 跨企业污染
- 无法解释来源
- 无法判断是否仍适用
- 难以做企业删除和撤销

所以平台级共享更适合做：

- 通用评估资产
- 平台模板
- 方案基线

而不是企业业务明细记忆。

## 5.2 所有权规则建议

建议明确：

- `session_memory` 归属于企业边界内的具体会话
- `task_memory` 归属于某次运行实例或任务实例
- `user_preference_memory` 归属于企业边界内的具体用户
- `learned_signal` 归属于企业或方案资产，不归属于单个聊天会话

## 5.3 “谁来管理”也应遵守既有原则

延续前面的平台原则：

- 平台方管平台能力和平台基线
- 企业方管企业自己的记忆资产、偏好资产和反馈资产
- 平台方不介入企业的日常记忆运营
- 平台方只有在交付、审计、事故例外通道中才可受控介入

## 六、哪些信息可以记住，哪些不能记住

## 6.1 可以进入记忆的内容建议

建议只允许进入“低到中风险、稳定、对后续确有帮助”的信息。

| 类别 | 示例 | 推荐容器 |
|---|---|---|
| 会话内偏好 | 本次对话中要求的输出格式、称呼偏好、展示偏好 | `session_memory` |
| 会话内约束 | 本次不讨论哪些内容、必须遵守哪些限制 | `session_memory` |
| 会话内任务状态 | 当前已完成步骤、待补资料、已确认目标 | `session_memory` / `task_memory` |
| 用户稳定偏好 | 用户明确确认的固定输出风格、默认模板 | `user_preference_memory` |
| 反馈信号 | 驳回原因标签、采用结果、编辑差异摘要 | `learned_signal` |

## 6.2 原则上不应进入记忆的内容

| 类别 | 原因 |
|---|---|
| 原始凭据、API Key、Cookie、账号口令 | 应走凭据系统，不应记忆化 |
| 完整身份信息、支付信息、受监管原文 | 风险过高，应按数据治理规则单独处理 |
| 整段原始聊天历史 | 这不是结构化记忆，只是堆积 |
| 未验证推断 | 例如模型猜测出的企业偏好、客户意图、敏感身份标签 |
| 平台基线规则 | 应由平台配置和策略引擎管理 |
| 企业长期规则 | 应转配置或知识库，不应只靠聊天提取 |
| 高风险草稿结论 | 未经审查的结论不应变成长期事实 |

## 6.3 “重要”不等于“应该记住”

很多内容对本轮任务很重要，但并不适合持久化。

例如：

- 当前订单明细
- 本次审批说明
- 某次草稿的临时备注
- 某次复盘中的争议意见

这些通常更适合留在运行记录、审批记录或 Artifact 中，而不是进入长期记忆。

## 七、启用层级与场景闸门

## 7.1 建议采用分层生效模型

记忆生效状态建议至少由以下层级共同决定：

1. 平台默认开关
2. 方案预设
3. 管理端 Agent 级开关
4. 企业侧覆盖
5. 工作流或节点级策略
6. 场景闸门 `scene_gate`

其中越靠后的层级越接近实际运行，但不能突破更高层设置的硬性禁区。

## 7.2 `scene_gate` 应是最后一道强约束

即使其他开关都允许，如果场景闸门不允许，记忆也不应生效。

建议至少区分这些场景：

| 场景 | 第一阶段建议 |
|---|---|
| `ai_chat_page` | 允许受控 `session_memory` |
| `admin_chat` | 默认关闭 |
| `plugin_tool_call` | 默认关闭 |
| `workflow_step` | 默认关闭，仅后续按节点类型灰度开放 |
| `approval_review` | 默认关闭 |
| `ephemeral_writing` | 强制关闭 |

### 7.2.1 为什么插件和审批场景默认关闭

因为这些场景要么跨工具链、要么高风险、要么强临时性。

如果在这些场景中默认开启记忆，很容易出现：

- 工具调用噪声被误当长期偏好
- 审批过程中的高敏信息被错误沉淀
- 写作临时状态污染后续正式任务

## 7.3 企业侧应有“关闭权”，但不应有“突破禁区权”

企业可以：

- 关闭某个 Agent 的记忆
- 关闭某个场景的记忆
- 提高写入门槛

但企业不应：

- 让平台禁用场景强行开启长期记忆
- 绕过数据治理把高敏信息沉淀为长期记忆

## 八、提取、写回与确认策略

## 8.1 写回时机应严格受控

建议不同容器采用不同写回时机：

| 容器 | 建议写回时机 |
|---|---|
| `session_memory` | 一轮对话完成后，结构化提取并写入 |
| `task_memory` | 节点完成、检查点提交、人工动作完成后写入 |
| `user_preference_memory` | 用户显式确认后写入 |
| `learned_signal` | 采用、驳回、编辑、效果回流后写入 |

## 8.2 自动提取必须是“结构化增量”，不是直接落聊天全文

建议提取结果至少应包含：

- 类型
- 内容摘要
- 置信度
- 来源证据
- 写入时间
- 作用域

没有结构化结果，就不应进入正式记忆容器。

## 8.3 持久记忆应设置更高门槛

建议：

- `session_memory` 可自动写入，但短 TTL、易清理
- `user_preference_memory` 需要显式确认或重复证据
- `enterprise_rule_memory` 不自动写入，转交配置/知识治理
- `learned_signal` 可自动写入反馈仓，但不直接变成 Prompt 主记忆

## 8.4 冲突、重复和降级要有正式语义

后续记忆写入至少要支持：

- 幂等事件 ID
- 版本冲突检测
- 重复写入抑制
- 提取失败降级
- 存储失败不阻塞主流程

当前仓库在会话记忆里已经有这类方向，这应继续保留并扩展。

## 九、长期学习的正式定义

## 9.1 长期学习的核心不是“越聊越懂”，而是“越来越可验证”

平台的长期学习不应是神秘黑盒，而应主要来自结构化反馈资产。

建议长期学习信号来源优先级如下：

1. 人工标注与人工确认
2. 草稿采用和驳回结果
3. 编辑差异与复盘标签
4. 业务结果指标
5. 评估基准结果

越靠前的信号越可靠。

## 9.2 长期学习更适合沉淀为“推荐资产”，不直接沉淀为“聊天记忆”

例如：

- 某类行业常用标题策略
- 某类客户群常见风格偏好
- 某类素材组合的效果倾向
- 某类风险动作的审批习惯

这些更适合进入：

- 推荐特征
- 方案参数建议
- 模板优化候选
- 运营复盘看板

而不是让 Agent 私下带着一堆不可见记忆去漂移。

## 9.3 长期学习不能突破前面已定的产品边界

因此正式禁止：

- 自动修改平台内核代码
- 自动修改复杂执行器代码
- 自动修改连接器实现
- 自动降低审批或风控闸门

如果后续真的要做这类“自优化”，也必须走平台方的研发、评审、发布、灰度和验收链路，而不是让运行时偷偷改。

## 十、留存、清理、导出与撤销语义

## 10.1 不同记忆容器的保留策略应不同

建议：

- `session_memory` 保持短 TTL，第一阶段继续沿用当前 24h 级思路
- `task_memory` 跟随任务生命周期，任务结束后按策略清理
- `user_preference_memory` 允许长期保留，但必须支持查看、编辑、撤销
- `learned_signal` 允许版本化保留，但应尽量去标识化、摘要化

## 10.2 清理入口必须清楚可用

后续平台至少要支持：

- 清空当前会话记忆
- 清空某类用户偏好记忆
- 让企业撤销某个学习信号
- 会话删除、归档时联动清理短期记忆

## 10.3 导出和查看不应成为新的泄漏面

如果后续支持查看记忆内容，应遵守：

- 只展示结构化结果，不展示无意义原始堆积
- 高敏内容默认继续脱敏
- 查看和导出同样要走审计

---

## 十一、评估、审计与风控要求

## 11.1 平台需要能评估“记忆是否真的有益”

建议至少跟踪：

- 记忆命中率
- 记忆帮助率
- 错误记忆率
- 过期记忆率
- 泄漏事件数
- 清理成功率
- 用户/企业关闭率

## 11.2 平台需要能评估“学习是否可解释”

长期学习资产至少应回答：

- 来源于哪些反馈
- 影响了哪些推荐
- 是否经过人工确认
- 是否可以回滚

## 11.3 风控审计重点

重点应覆盖：

- 是否把高敏信息错误记忆化
- 是否把企业规则错误留在 Agent 私有记忆中
- 是否出现跨企业污染
- 是否出现无法撤销的学习结果

---

## 十二、分阶段实施建议

## 12.1 第一阶段：受控会话记忆

第一阶段建议继续坚持当前方向：

- 只做 `session_memory`
- 只在受控场景开启
- 保持短 TTL
- 提供查询和清理能力
- 存储失败不影响主流程

## 12.2 第二阶段：受审查的偏好与任务记忆

第二阶段可逐步引入：

- `task_memory`
- 显式确认的 `user_preference_memory`
- 企业可见、可撤销的记忆面板

但仍不建议开放无边界长期学习。

## 12.3 第三阶段：结构化长期学习资产

第三阶段更合理的目标应是：

- 建立 `learned_signal` 仓
- 把采用、驳回、编辑差异、效果标签沉淀为结构化资产
- 用这些资产驱动推荐、评估和方案优化

而不是直接把历史聊天全部视为“智能成长”。

## 12.4 对行业方案插件的直接要求

所有行业方案插件如果声称自己具备“记忆”或“学习”能力，必须提交：

- 记忆容器说明
- 作用域说明
- 写入时机说明
- 清理与撤销说明
- 高敏信息排除说明
- 是否会影响推荐或执行决策的说明

否则不应在正式市场中以“可商用智能体”名义出售。

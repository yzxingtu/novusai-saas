# AI 编排与工作流平台组织角色模型与人机协作通道规范（2026-03-23）

## 一、文档目标

本文档用于定义平台中的组织角色模型，以及人在 AI 编排和工作流中的正式协作通道。

前面的文档已经把很多能力和边界定下来了，但平台要真正长期运行，还必须回答另外一类问题：

1. 平台方内部哪些角色负责生产、治理、交付、应急。
2. 企业方内部哪些角色负责配置、运营、审批、内容修订、结果复盘。
3. 人在工作流里到底以哪些正式方式介入，是审批、补料、改稿、恢复、接管，还是例外升级。
4. 一条流程从“AI 自动运行”切到“人机协作”，再切回自动时，语义和责任如何保持清晰。

所以，这份文档要解决的是：

> 平台如何把“Human in the Loop”从一句口号，变成正式的组织模型和协作通道体系。

---

## 二、核心结论

### 2.1 人机协作不等于“有个审批按钮”

很多系统提到人机协作，实际上只有：

- 一个确认弹窗
- 一个审批节点

这远远不够。

真正的人机协作至少应包括：

- 请求发起
- 计划审阅
- 证据补料
- 草稿修订
- 正式审批
- 异常接管
- 结果复盘

### 2.2 角色模型不能只靠传统 RBAC 资源权限表达

RBAC 只能回答：

- 谁能看哪个页面
- 谁能点哪个按钮

但人机协作还要回答：

- 谁是这条运行的责任人
- 谁有权接管异常
- 谁能修改草稿后继续流程
- 谁能做审批后的业务确认

因此除了 RBAC，还必须有：

- 角色职责模型
- 协作通道模型
- 责任归属模型

### 2.3 平台方和企业方都需要各自的协作通道，但职责必须严格分开

平台方负责：

- 平台治理
- 方案生产
- 连接器托管
- 紧急冻结
- 定制交付

企业方负责：

- 企业知识配置
- 日常运营
- 审批实例
- 草稿修订
- 异常接管

人机协作通道必须服务于这两类组织，但不能打破前面已经确定的所有权边界。

### 2.4 人类介入点应被正式建模为“协作通道”

建议不要把所有人工介入都塞进一个“manual task”。

更合适的做法是正式定义若干协作通道，例如：

- `request_lane`
- `review_lane`
- `approval_lane`
- `editor_lane`
- `operator_lane`
- `incident_lane`
- `owner_lane`

### 2.5 一条工作流必须能回答“此刻等谁”

任何进入人工协作状态的运行实例，都应能清楚回答：

- 当前在等哪个角色
- 在等哪种动作
- 不做会怎样
- 超时后会如何升级

这是平台日后可运营的关键。

---

## 三、为什么必须单独写这份文档

前面的审批、运行恢复、企业控制台文档，已经隐含了大量人机协作语义，但还没有系统回答：

- 这些动作归属给谁
- 谁和谁之间如何交接
- 哪些是企业内部协作，哪些是平台介入
- 同一个人是否可以扮演多个通道角色

如果这层不单独规范，后面会出现：

1. 审批人、运营人、编辑人职责混在一起。
2. 企业端和管理端都能看到某些人工接管入口，但谁该负责不清楚。
3. 异常接管、草稿修订、审批驳回后的回改都被当成同一种人工任务。

所以，这份文档是在回答：

> 平台如何把“人与 AI 一起完成工作”设计成正式组织通道，而不是靠临时人肉兜底。

---

## 四、正式对象模型

建议把组织协作相关对象正式抽出来。

### 4.1 核心对象建议

| 对象 | 作用 |
|---|---|
| `org_role_profile` | 角色职责画像 |
| `collaboration_lane` | 一类正式协作通道定义 |
| `lane_assignment_rule` | 协作通道分配规则 |
| `human_task` | 某次具体人工任务 |
| `human_task_action` | 人工任务中的具体动作 |
| `run_responsibility_binding` | 某次运行的责任人绑定 |
| `escalation_policy` | 协作超时与升级策略 |
| `human_feedback_record` | 人工修订、意见、采用、驳回记录 |

### 4.2 为什么 `human_task` 不能替代全部概念

因为平台不仅需要知道“有个任务”，还需要知道：

- 它属于哪个协作通道
- 它的职责是什么
- 它应该交给哪类角色

所以协作通道必须先于具体任务被定义。

---

## 五、组织角色模型

建议分别定义平台方和企业方角色。

### 5.1 平台方角色建议

| 角色 | 主要职责 |
|---|---|
| `platform_governor` | 平台规则、风控、冻结与治理 |
| `solution_designer` | 行业方案设计与模板生产 |
| `connector_operator` | 连接器与外部动作托管治理 |
| `delivery_manager` | 定制交付推进与交接 |
| `platform_reviewer` | 平台级验收、回归、质量门禁 |
| `incident_commander` | 平台级事故应急 |

### 5.2 企业方角色建议

| 角色 | 主要职责 |
|---|---|
| `tenant_owner` | 企业负责人，关键启用与高风险决策 |
| `tenant_operator` | 日常运行与异常处理 |
| `tenant_approver` | 审批高风险动作 |
| `tenant_editor` | 草稿修订与内容补料 |
| `tenant_analyst` | 结果复盘、样本标注、优化建议 |
| `tenant_context_admin` | 知识、素材、规则和上下文维护 |

### 5.3 为什么 `tenant_context_admin` 需要单独存在

因为很多问题不是运行和审批本身，而是：

- 知识没配好
- 素材没上传
- 品牌规则不完整

这类职责不应默认丢给运营人员或审批人。

---

## 六、协作通道模型

建议把人工介入正式拆成 7 条通道。

### 6.1 `request_lane`

作用：

- 负责流程发起、目标确认、输入确认

典型角色：

- 企业业务发起人
- 企业负责人

### 6.2 `review_lane`

作用：

- 对计划、证据、建议、草稿进行业务审阅

典型角色：

- 企业分析人员
- 企业业务负责人

### 6.3 `approval_lane`

作用：

- 对高风险动作做正式批准或驳回

典型角色：

- 企业审批人
- 企业负责人

### 6.4 `editor_lane`

作用：

- 修改草稿、补充说明、替换 Artifact、修正文案

典型角色：

- 内容编辑
- 品牌负责人

### 6.5 `operator_lane`

作用：

- 处理运行异常、恢复、暂停、重新提交

典型角色：

- 企业运营人员

### 6.6 `incident_lane`

作用：

- 处理高风险异常、未知状态、连接器故障、预算超限事故

典型角色：

- 企业负责人
- 企业运营负责人
- 平台应急角色

### 6.7 `owner_lane`

作用：

- 承接必须由资源所有者决定的动作，例如：
  - 接受升级
  - 切换正式版本
  - 接受重大风险动作

典型角色：

- 企业负责人
- 平台交付负责人

---

## 七、协作通道与人工动作映射

建议每类人工动作都明确归属于某条通道。

### 7.1 建议映射

| 人工动作 | 协作通道 |
|---|---|
| 发起运行 | `request_lane` |
| 确认目标或参数 | `request_lane` |
| 审阅计划 | `review_lane` |
| 审阅证据 | `review_lane` |
| 审批通过/驳回 | `approval_lane` |
| 修改草稿 | `editor_lane` |
| 补充素材或上下文 | `editor_lane` / `request_lane` |
| 重试运行 | `operator_lane` |
| 从检查点恢复 | `operator_lane` |
| 确认外部回执 | `incident_lane` |
| 接受升级 | `owner_lane` |

### 7.2 为什么不能只做一个万能人工通道

因为不同动作需要：

- 不同角色
- 不同 SLA
- 不同审计语义
- 不同升级路径

---

## 八、责任归属模型

平台必须明确每条运行的责任链，而不是只知道由谁触发。

### 8.1 建议的责任绑定

每次 `workflow_run` 至少可绑定：

- `request_owner`
- `business_owner`
- `operation_owner`
- `approval_owner_group`
- `exception_owner`

### 8.2 为什么 `request_owner` 不等于 `operation_owner`

发起人通常只负责：

- 提出需求
- 说明目标

但实际运营和恢复，往往要由：

- 企业运营人员
- 企业负责人

承担。

### 8.3 责任链必须可见

运行详情和企业控制台至少应显示：

- 当前责任人是谁
- 当前等待谁
- 下一个接力角色是谁

---

## 九、协作任务 `human_task` 规范

### 9.1 人工任务建议字段

| 字段 | 说明 |
|---|---|
| `task_type` | `approval` / `review` / `edit` / `recover` / `confirm` / `handover` |
| `lane_code` | 所属协作通道 |
| `owner_type` | 平台或企业 |
| `owner_tenant_id` | 企业归属 |
| `assigned_role_code` | 指派给哪类角色 |
| `assigned_user_id` | 具体到人时的用户 |
| `source_run_id` | 来源运行 |
| `source_node_run_id` | 来源节点 |
| `deadline_at` | 截止时间 |
| `escalation_policy_id` | 超时升级策略 |
| `required_action_schema` | 该任务要求的人类动作结构 |

### 9.2 任务应和运行图直接打通

任何人工任务都不应游离在运行系统之外。

建议都能回到：

- 某次运行
- 某个节点
- 某个审批包
- 某个 Artifact

---

## 十、人类动作结构化要求

### 10.1 人类动作也必须结构化

不要只记录一段“已处理”备注。

建议至少结构化记录：

- `action_code`
- `action_result`
- `comment`
- `artifact_refs`
- `changed_fields`
- `reason_label`

### 10.2 典型动作结构

例如：

- 审批通过：理由、附加条件、查看证据版本
- 草稿修改：改了哪些字段、为什么改
- 恢复执行：从哪个检查点、为什么恢复
- 确认外部回执：依据什么确认

### 10.3 这样做的价值

后续可以用于：

- 复盘
- 评估
- 升级
- 基准样本沉淀

---

## 十一、超时与升级规则

### 11.1 每条协作通道都应有自己的超时语义

例如：

- 审批通道超时，可能升级提醒或取消
- 编辑通道超时，可能退回草稿
- 事故通道超时，可能直接冻结相关触发器

### 11.2 建议的升级策略

| 策略 | 说明 |
|---|---|
| `remind_same_role` | 同角色提醒 |
| `reassign_within_role` | 同角色改派 |
| `escalate_to_owner` | 升级给负责人 |
| `escalate_to_platform` | 平台介入 |
| `expire_and_stop` | 超时终止 |

### 11.3 平台介入必须是例外通道

企业日常协作超时，不应默认升级为平台代办。

只有以下场景才应考虑平台介入：

- 平台托管交付
- 平台级风险事故
- 外部连接器异常
- 紧急冻结和回滚

---

## 十二、人机协作在不同工作流模式下的区别

### 12.1 `deterministic`

特点：

- 人工介入点固定
- 通道稳定
- 适合明确流程化协作

### 12.2 `hybrid`

特点：

- 主流程固定
- 人工主要介入审阅、审批、编辑和异常恢复

### 12.3 `agentic`

特点：

- 人工介入点可能随规划结果动态出现
- 更依赖 `review_lane`、`approval_lane`、`incident_lane`

### 12.4 `L4`

特点：

- 必须至少存在计划审阅通道和高风险动作审批通道
- 企业负责人或授权高级角色必须能看到关键决策节点

---

## 十三、平台方与企业方的协作边界

### 13.1 平台方协作通道的适用场景

平台方应主要参与：

- 方案生产
- 方案验收
- 连接器治理
- 平台级事故
- 定制交付交接

### 13.2 企业方协作通道的适用场景

企业方应主要参与：

- 日常审批
- 日常运行恢复
- 草稿修订
- 业务结果反馈
- 企业知识补料

### 13.3 什么不能因为“协作”而越界

例如：

- 平台不能代企业做日常审批
- 企业不能代平台做连接器可信度审核
- 企业运营不能直接修改平台托管逻辑

---

## 十四、与企业运营控制台的关系

### 14.1 控制台应成为协作通道的承载面

企业运营控制台中的：

- 今日待办
- 审批中心
- 异常恢复中心
- 草稿与结果中心

本质上就是协作通道的 UI 呈现。

### 14.2 为什么需要这层抽象

因为页面是会变的，但协作语义不应漂移。

未来即使换 UI，平台仍然应该知道：

- 这条任务属于哪个协作通道
- 交给了哪个角色
- 需要什么人类动作

---

## 十五、与评估和样本回流的关系

### 15.1 人类动作是评估的重要数据来源

例如：

- 审批驳回理由
- 草稿修改痕迹
- 手工采用/退回
- 异常恢复选择

这些都不应只当作运营日志，而应能进入：

- 评估样本候选池
- 基准集回流
- 标注修正

### 15.2 为什么这很重要

因为真正高价值的“人机协作经验”，往往就藏在这些人工动作里。

---

## 十六、与现有文档的关系

### 16.1 与 `17-enterprise-operator-console-spec`

`17` 负责企业运营控制台页面与任务结构。

`22` 负责这些页面背后的组织职责与协作通道语义。

### 16.2 与 `05-approval-and-risk-gate-spec`

`22` 把审批进一步放回到更大的协作通道体系里，不让审批变成人机协作的全部。

### 16.3 与 `16-runtime-execution-graph-and-recovery-spec`

人工恢复、人工接管、人工补料都应作为正式协作通道进入运行图。

### 16.4 与 `19-evaluation-dataset-and-benchmark-governance-spec`

人类修订和审批记录应成为候选评估样本的重要来源。

---

## 十七、第一阶段实施建议

### Phase 1：先把“角色职责 + 协作通道 + 人工任务”做出来

优先建设：

- `org_role_profile`
- `collaboration_lane`
- `human_task`
- `run_responsibility_binding`

### Phase 2：再补“通道级升级和结构化动作”

补齐：

- `lane_assignment_rule`
- `escalation_policy`
- `human_task_action`
- 人工动作结构化记录

### Phase 3：最后补“平台/企业协作联动与样本回流”

补齐：

- 平台级协作例外通道
- 定制交付交接协作链
- 人工修订回流评估样本

---

## 十八、关键结论

1. 人机协作不能被简化成审批按钮，平台至少要正式支持请求、审阅、审批、编辑、运营、事故和所有者决策七类协作通道。
2. 单纯 RBAC 资源权限不足以表达人机协作，还必须建立角色职责模型、责任归属模型和协作通道模型。
3. 平台方和企业方都需要各自的人机协作通道，但必须继续遵守“谁拥有工作流谁管理”的所有权边界。
4. 任何进入人工协作状态的运行实例，都应能明确回答“此刻等谁、等什么动作、超时后怎么办”。
5. 人类动作必须结构化记录，因为它们不仅服务审计，也会成为后续评估、升级和样本回流的重要依据。
6. 第一阶段先把角色职责、协作通道、人工任务和责任绑定做出来，再逐步补齐升级策略、结构化动作和跨层协作联动。

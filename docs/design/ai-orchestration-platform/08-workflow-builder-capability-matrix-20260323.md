# AI 编排与工作流平台构建器能力矩阵（2026-03-23）

## 一、文档目标

本文档用于把“工作流构建器到底开放到什么程度”正式定下来，避免后续出现以下问题：

- 企业端被做成“可写代码的开发者后台”
- 管理端和企业端的能力边界漂移
- `deterministic`、`hybrid`、`agentic` 三种模式在构建器层面没有明确差异
- 审批、授权、风险闸门只在运行时兜底，而设计阶段没有前置约束

本文档重点定义：

1. 平台到底有几种构建器形态。
2. 哪类角色可以创建哪类工作流。
3. 哪些节点、触发器、能力、数据操作允许出现在不同层级的构建器里。
4. 保存、发布、运行三个阶段分别要做哪些校验。

---

## 二、核心结论

### 2.1 平台不是只有一个工作流构建器，而是三种构建面

建议把“工作流构建器”拆成三种正式构建面：

1. `platform_workflow_studio`
2. `tenant_template_editor`
3. `tenant_simple_builder`

说明：

- `platform_workflow_studio` 面向管理端，用于平台模板、代码型工作流、托管方案模板。
- `tenant_template_editor` 面向企业端对“可复制模板”的派生编辑。
- `tenant_simple_builder` 面向企业端新建简单工作流。

### 2.2 能力控制不能只看页面入口，必须看“能力分类 + 构建面”

是否允许拖入某个节点，不能只看用户当前在哪个页面，而要同时看：

- 当前构建面
- 当前工作流类型
- 当前企业授权
- 当前套餐能力
- 节点能力分类
- 风险等级

### 2.3 企业可以编排，但不能扩核

这一点应在构建器层面就被强制落实。

结论：

- 企业可组合白名单能力
- 企业不可新增连接器
- 企业不可新增执行器
- 企业不可写自定义代码
- 企业不可绕过平台审批基线

### 2.4 “纯 AI 编排”不等于“任意放开”

平台支持 `agentic` 模式，但不意味着企业端可以随意让 Agent 自主做任何事情。

正确理解应是：

- `agentic` 只是“规划方式更自主”
- 可用能力、预算、审批和风险边界仍然受控

### 2.5 构建器要在三个阶段同时校验

建议至少有三道校验：

1. 拖拽或配置阶段校验
2. 保存或发布阶段校验
3. 运行前校验

不能把所有风险都压到运行时再报错。

## 三、三种构建面定义

### 3.1 `platform_workflow_studio`

定义：

面向管理端的全量工作流制作环境，用于生产平台正式资源。

适用场景：

- 平台级工作流模板
- 行业方案托管模板
- 代码型工作流
- 定制交付工作流

特点：

- 能看到全部能力分类
- 可以创建 `deterministic`、`hybrid`、`agentic`
- 可以引用平台托管连接器和执行器
- 可以配置强制审批策略

### 3.2 `tenant_template_editor`

定义：

企业端对“可复制模板副本”的受限编辑环境。

适用场景：

- 复制平台模板为企业版
- 修改企业参数
- 调整节点顺序
- 替换低风险提示词和业务变量

特点：

- 只能编辑允许复制的模板
- 只能在白名单节点范围内调整
- 不能修改平台锁定片段
- 不能引入新代码节点或高危节点

### 3.3 `tenant_simple_builder`

定义：

企业端从零新建简单工作流的无代码构建环境。

适用场景：

- 企业内部 SOP
- 内容草稿流
- 线索分流
- 报表汇总与分析
- 企业内部审批前置流转

特点：

- 只能用白名单无代码节点
- 只能使用已授权能力
- 不能扩展平台内核
- 不能引入高危外部写动作

---

## 四、工作流类型与构建面的关系

### 4.1 三种工作流类型

平台沿用前文定义：

- `deterministic`
- `hybrid`
- `agentic`

### 4.2 不同构建面的支持矩阵

| 构建面 | `deterministic` | `hybrid` | `agentic` |
|---|---|---|---|
| `platform_workflow_studio` | 完整支持 | 完整支持 | 完整支持 |
| `tenant_template_editor` | 支持 | 支持 | 受限支持 |
| `tenant_simple_builder` | 完整支持 | 受限支持 | 轻量支持或按套餐开放 |

### 4.3 企业端的 `agentic` 只能是“轻量受限 Agentic”

企业端即使开放 `agentic`，也建议只开放：

- 目标规划
- 白名单工具选择
- 有预算和步数上限
- 关键节点必须审批

不允许：

- 任意访问系统级工具
- 任意跨租户数据
- 任意外部写动作
- 无约束的长链自动执行

## 五、节点能力分类

建议不要只按“节点名字”管理，而是先做能力分类，再让节点挂到能力分类上。

### 5.1 五大节点能力类

#### A 类：基础流程节点 `flow_core`

典型节点：

- `trigger`
- `input`
- `condition`
- `router`
- `merge`
- `output`

特点：

- 风险低
- 构建器通用
- 企业端可开放

#### B 类：AI 处理节点 `ai_core`

典型节点：

- `llm`
- `planner`
- `rewrite`
- `summarize`
- `classification`

特点：

- 风险中低
- 需受模型额度、提示词边界和输出约束控制

#### C 类：能力调用节点 `tool_runtime`

典型节点：

- `tool`
- `skill_call`
- `knowledge_lookup`
- `data_read`

特点：

- 风险取决于底层能力
- 不能一概放开

#### D 类：治理节点 `governance`

典型节点：

- `approval`
- `policy_check`
- `human_review`
- `rate_guard`
- `quota_guard`

特点：

- 平台必须强支持
- 企业端可以使用，但不能移除平台强制闸门

#### E 类：受控扩展节点 `managed_extension`

典型节点：

- `external_write`
- `connector_action`
- `code_execution`
- `system_mutation`

特点：

- 高风险
- 只能在平台托管范围内使用
- 默认不进入企业简单构建器

### 6.2 对企业端来说，“API / Webhook 触发”是平台托管入口，不是自定义代码

这点必须明确：

- 企业端允许配置 `api` 或 `webhook` 触发，不等于企业端能写后端代码。
- 企业端只能配置平台提供的标准触发入口、认证和字段映射。
- 企业端不能编写自定义 webhook handler。

## 七、能力分类与开放级别

除了节点类型，还应再抽一层“能力分类”，用于做更稳定的开放控制。

### 7.1 建议的能力分类

| 能力分类 | 说明 | 企业简单构建器 |
|---|---|---|
| `internal_read` | 读取企业内部已授权数据 | 允许 |
| `external_read` | 联网检索或外部只读抓取 | 允许 |
| `content_generation` | 生成文案、摘要、报告、草稿 | 允许 |
| `internal_write_low` | 写入草稿、标签、候选记录 | 审批后允许 |
| `internal_write_high` | 覆盖正式数据、批量写入 | 默认不允许 |
| `external_write_low` | 对外提交低风险内容 | 默认不允许 |
| `external_write_high` | 改价、发货、发布、消息外发 | 不允许 |
| `code_execution` | 执行代码 | 不允许 |
| `connector_admin` | 管理连接器、凭据、安装 | 不允许 |

### 7.2 企业构建器开放的核心不是“节点数量”，而是“能力等级”

建议产品上做两级控制：

1. 节点是否可见
2. 节点背后的能力等级是否可用

这样后续即使节点名称变化，授权模型仍然稳定。

## 八、变量、数据和上下文边界

### 8.1 企业端允许配置什么变量

企业端应允许配置：

- 业务输入变量
- 固定模板参数
- 品牌和风格参数
- 审批人和审批组映射
- 运行预算上限

### 8.2 企业端不应直接配置什么

企业端不应直接配置：

- 原始数据库连接
- 代码执行环境
- 系统级密钥
- 平台内核运行参数
- 非授权模型提供商参数

### 8.3 上下文注入建议分层

建议上下文分为三层：

1. 平台上下文
2. 方案上下文
3. 企业上下文

企业端主要能编辑第三层，少量能调整第二层的业务参数，不应直接改第一层内核约束。

---

## 九、Prompt、模型和工具边界

### 9.1 企业端可以改什么 Prompt

建议企业端可改：

- 业务补充说明
- 品牌语气要求
- 行业关键词
- 输出格式偏好

### 9.2 企业端不应改什么 Prompt

建议企业端不可改：

- 平台安全底线 Prompt
- 风险和审批底线 Prompt
- 工具选择黑名单
- 跨租户隔离规则

### 9.3 企业端模型选择也应受控

企业端可在授权范围内做模型选择，但不应做到：

- 任意填 provider base URL
- 任意新增模型
- 任意关闭输出约束

建议企业端只在“平台允许的模型池”里选。

## 十、三类工作流的构建约束

### 10.1 `deterministic`

建议特征：

- 固定节点顺序
- 显式条件分支
- 无自由规划

开放建议：

- 企业端完整支持
- 最适合作为企业简单构建器的主形态

### 10.2 `hybrid`

建议特征：

- 主骨架固定
- 局部由 AI 生成参数、推荐路径、调用低风险工具

开放建议：

- 企业端支持
- 但底层工具必须来自白名单

### 10.3 `agentic`

建议特征：

- 由 Planner 生成步骤或局部计划
- 可动态选择白名单工具

开放建议：

- 管理端完整支持
- 企业端仅开放轻量版
- 必须带预算、步数、风险、审批四层约束

## 十一、锁定片段与可编辑片段

平台模板如果允许企业复制和调整，建议模板结构里显式区分：

- `locked_segment`
- `editable_segment`
- `parameterized_segment`

### 11.1 `locked_segment`

不可改内容包括：

- 平台强制审批节点
- 关键合规校验
- 高危调用约束
- 平台托管执行器引用

### 11.2 `editable_segment`

企业可改内容包括：

- 提示词补充
- 节点文案
- 条件阈值
- 路由分支
- 业务字段映射

### 11.3 `parameterized_segment`

企业只能填值，不能改结构，例如：

- 品牌信息
- 渠道信息
- 产品清单
- 审批组

---

## 十二、保存、发布、运行三阶段校验

### 12.1 设计阶段校验

在拖入节点和配置节点时就应校验：

- 当前构建面是否允许该节点
- 当前套餐是否允许该模式
- 当前授权是否覆盖该能力
- 当前节点是否命中平台黑名单

### 12.2 保存阶段校验

保存时建议校验：

- 图结构完整性
- 变量引用合法性
- 审批闸门完整性
- 高风险节点是否缺失预览或审批配置
- 预算或并发限制是否有默认值

### 12.3 发布阶段校验

发布时建议额外校验：

- 是否含未授权能力
- 是否含企业不允许的高危节点
- 是否通过风险基线校验
- 是否通过模板 Schema 校验
- 是否需要人工审核后才能发布

### 12.4 运行前校验

运行前建议校验：

- 当前版本是否已发布
- 当前触发器是否启用
- 当前授权是否仍有效
- 插件 License 是否仍有效
- 审批策略是否可解析

## 十三、发布权限矩阵

| 动作 | 管理端 | 企业端 |
|---|---|---|
| 新建平台模板 | 允许 | 不允许 |
| 新建企业简单工作流 | 不需要 | 允许 |
| 复制平台模板为企业副本 | 可操作 | 允许 |
| 发布平台模板 | 允许 | 不允许 |
| 发布企业工作流 | 不需要 | 允许 |
| 引入代码节点 | 允许 | 不允许 |
| 引入外部写能力 | 允许 | 不允许或强限制 |
| 修改平台锁定片段 | 允许 | 不允许 |
| 调整企业本地审批加严规则 | 不需要 | 允许 |

## 十四、与授权和计费的联动

构建器开放能力应直接受以下因素驱动：

1. `TenantPlan.features`
2. `TenantPlan.quota`
3. `TenantEntitlement`
4. 插件 License
5. 风险基线

### 14.1 建议的套餐能力开关

可考虑在套餐层加入：

- `workflow_builder_basic`
- `workflow_builder_hybrid`
- `workflow_builder_agentic_lite`
- `workflow_api_trigger`
- `workflow_webhook_trigger`
- `workflow_schedule_trigger`
- `workflow_internal_write`

### 14.2 不建议把构建器开放写死在前端

前端只负责展示和交互，真正是否可用应由后端能力矩阵解析结果决定。

---

## 十五、第一阶段建议如何落地

### Phase 1：先收敛企业简单构建器

第一阶段建议企业简单构建器只开放：

- `deterministic`
- 受限 `hybrid`
- 基础触发器
- 只读工具和内容生成工具
- 审批节点

不要一上来开放：

- 代码执行
- 外部写动作
- 无约束 `agentic`

### Phase 2：再开放企业模板派生编辑

补齐：

- 锁定片段
- 可编辑片段
- 参数化片段
- 企业模板复制逻辑

### Phase 3：最后再开放企业轻量 `agentic`

前提：

- 预算模型成熟
- 审批闸门成熟
- 运行回放成熟
- 白名单工具体系成熟

---

## 十六、关键结论

1. 工作流构建器应明确拆成管理端工作室、企业模板编辑器、企业简单构建器三种构建面。
2. 企业端的核心边界是“可编排，不可扩核”，这必须在节点、能力和配置三个层面同时落地。
3. 企业端即使支持 `agentic`，也只能支持轻量受限版，而不是任意自主执行。
4. 节点开放控制不应只靠页面入口，而应基于“构建面 + 能力分类 + 授权 + 风险”联合判断。
5. 平台模板若允许企业复制，必须显式区分锁定片段、可编辑片段和参数化片段。
6. 风险和审批不应只在运行时拦截，构建、保存、发布三个阶段都应有前置校验。

# AI 编排与工作流平台架构草案（2026-03-23）

## 一、文档定位

本文档用于定义本项目后续建设的**平台级方向**，目标不是继续围绕某个单一行业场景做功能堆叠，而是抽象出一套可复用的：

- AI 编排平台
- 工作流平台
- 插件市场与行业解决方案分发体系
- 企业级授权、计费、审批、审计体系

本文档同时约束两个目标：

1. 平台内核必须保持行业无关。
2. 行业能力必须通过插件或解决方案包挂载，不得反向污染平台内核。

---

## 二、背景与目标

### 2.1 背景

当前项目已具备以下基础：

- 多租户 SaaS 平台能力
- Admin / Tenant 双端架构
- Agent -> Skill -> AIGateway 的 AI 运行链路
- 插件系统、插件市场、SkillPackage / Skill 目录投影机制
- 定时任务、异步任务、权限、审计、通知等基础设施

但当前能力仍偏向：

- 通用 AI 能力平台
- 智能体管理平台
- 插件扩展平台

缺少一个上层抽象，将以下能力统一纳入平台模型：

- 固定工作流
- 混合工作流
- 纯 AI 编排
- 行业解决方案分发
- 企业级定制交付
- 强人工审核闸门

### 2.2 目标

建设一套“企业级 AI 编排与工作流 SaaS 平台”，满足：

- 管理端负责平台治理、分发、授权、售卖、升级、禁用
- 企业端负责消费能力、注入业务知识、搭建简单工作流、管理企业审批和运行结果
- 平台同时支持：
  - 固定工作流 `deterministic`
  - 混合工作流 `hybrid`
  - 纯 AI 编排 `agentic`
- 行业解决方案以插件形式交付，纳入插件市场
- 平台支持“两重付费”：
  - 平台基础能力订阅
  - 行业方案 / 工作流方案授权
- 平台允许企业自建简单工作流，但不允许企业扩展平台内核或创建代码型工作流

### 2.3 非目标

当前阶段不追求以下目标：

- 企业端任意编写 Python / JS 代码扩展平台
- 把平台做成通用低代码开发平台
- 在第一阶段直接做高风险的跨平台自动发布或资金类自动执行
- 让管理端代管企业日常工作流运营

---

## 三、平台定位

平台建议正式定位为：

> 插件化行业解决方案 + AI 编排 + 工作流 SaaS 平台

该定位强调 3 个重点：

1. **插件化行业解决方案**
   行业能力不直接写进主系统，而是通过插件分发。
2. **AI 编排**
   平台不仅支持固定规则流，也支持 Agent 参与规划和路径选择。
3. **工作流 SaaS**
   平台必须具备运行时、审批、治理、审计、授权、计费等企业级能力。

## 四、核心产品原则

### 4.1 行业解决方案并入插件市场

“行业解决方案中心”不单独建设为与插件市场平行的系统，而是作为插件市场中的一种正式插件类别存在。

结论：

- 能力插件属于插件市场
- 行业解决方案插件也属于插件市场
- 插件市场负责安装、升级、授权、停用、售卖

### 4.2 企业价值不在于“创建工具”

企业端的核心价值不是开发底层工具，而是：

- 使用平台能力
- 注入企业业务知识
- 组合已授权能力
- 配置自己的流程和审批规则
- 管理草稿、审核和运行结果

因此：

- 企业端允许“轻编排”
- 企业端不允许“扩内核”

### 4.3 管理权遵循资源所有权

平台资源由管理端管理，企业资源由企业端管理。

管理端职责：

- 上架
- 授权
- 分发
- 升级
- 禁用
- 平台治理

企业端职责：

- 使用
- 配置
- 搭建简单工作流
- 管理审批实例
- 管理企业知识和草稿

结论：

> 谁的工作流谁来管理，管理端不介入企业日常运营。

### 4.4 高自治执行必须强审核

平台支持高自治执行，但必须带有强人工审核闸门、证据链和可回放能力。

本平台的高自治执行定义为：

> L4：高自治执行 + 强人工审核闸门

其特征：

- Agent 可自主规划多个步骤
- 可跨多个已授权能力连续执行
- 高风险节点必须审批
- 所有关键动作必须生成预览和审计记录

### 4.5 代码型能力必须由平台方交付

涉及代码、执行器、连接器、复杂后端逻辑的工作流或能力，只能由管理端制作并交付。

企业端禁止：

- 新增代码执行逻辑
- 新增系统级 Skill
- 新增连接器
- 修改运行时内核

## 六、平台一级模块

### 6.1 插件市场

职责：

- 插件安装、启用、禁用、卸载、升级
- 插件版本管理
- 插件运行时闸门控制
- 插件授权可见性控制
- 插件售卖与可订阅目录展示

插件市场中的插件建议分为五类：

- `capability_plugin`
- `product_module_plugin`
- `solution_plugin`
- `ui_plugin`
- `content_plugin`

其中：

- `product_module_plugin` 用于任务编排、语义指标层、BI 助手等跨行业可售卖产品模块
- `solution_plugin` 即行业解决方案插件

### 6.2 解决方案中心

逻辑上存在，物理上并入插件市场。

职责：

- 展示行业方案目录
- 组织行业模板、Agent、Skill、页面、审批流
- 管理方案包版本与适用范围
- 管理方案包授权记录

### 6.3 能力中心

职责：

- 管理 SkillPackage、Skill、AgentProfile、知识库、模型路由
- 管理可用于工作流节点的白名单能力
- 管理平台级 Prompt 模板和工具分类

约束：

- `SkillPackage` 仍只负责目录、来源、归组，不承担运行时绑定真相
- 运行时能力真相仍由 Agent 直接持有 Skill 授权决定

### 6.4 工作流中心

职责：

- 管理 WorkflowTemplate
- 管理模板版本
- 管理节点、边、条件、变量
- 管理运行模式
- 管理模板发布与分发

在产品交付层，工作流 / 任务编排能力不要求每个企业默认开通，建议作为 `product_module_plugin` 交付；平台内核只保留通用执行基元、策略、审批与治理能力。

平台原生支持三种模式：

- `deterministic`
- `hybrid`
- `agentic`

### 6.5 审批治理中心

职责：

- 风险分级
- 审批策略
- 审批人配置
- 双人审批
- 超时与驳回规则
- 审批实例记录

### 6.6 授权与计费中心

职责：

- 平台套餐
- 行业方案授权
- 定制交付授权
- 模板和能力的企业可见性控制
- 使用量计量

### 6.7 企业知识与轻编排中心

职责：

- 企业知识库
- 素材库
- 品牌规范
- 审核规范
- Prompt 参数
- 企业简单工作流

### 6.8 运行监控与审计中心

职责：

- Run 监控
- 节点执行记录
- 产物留存
- 回放
- 错误分析
- 成本分析
- 安全审计

## 七、平台作用域模型

为避免单一 `scope` 字段承担过多语义，平台级设计建议拆成三类作用域。

### 7.1 Ownership Scope：归属作用域

表示资源归谁拥有。

建议枚举：

- `system`
- `platform`
- `tenant`

### 7.2 Availability Scope：可用作用域

表示谁可以看到或使用资源。

建议枚举：

- `global_public`
- `licensed_tenants`
- `selected_tenants`
- `owner_only`

### 7.3 Billing Scope：计费作用域

表示资源如何售卖或计费。

建议枚举：

- `included`
- `addon`
- `custom_delivery`
- `usage_metered`

### 7.4 资源作用域示例

| 资源 | ownership_scope | availability_scope | billing_scope |
|---|---|---|---|
| 平台基础能力 | `system` / `platform` | `licensed_tenants` | `included` |
| 行业解决方案插件 | `platform` | `licensed_tenants` / `selected_tenants` | `addon` |
| 企业定制工作流 | `platform` 或 `tenant` | `selected_tenants` / `owner_only` | `custom_delivery` |
| 企业自建简单工作流 | `tenant` | `owner_only` | `included` / `usage_metered` |

## 八、授权与计费模型

### 8.1 对外收费模型

对外建议维持“两重付费”表达：

1. 平台基础能力订阅
2. 行业方案 / 工作流方案授权

### 8.2 对内实现模型

系统内部建议拆成三层授权对象：

- `platform_subscription`
- `solution_package_entitlement`
- `custom_delivery_entitlement`

### 8.3 推荐授权链路

```text
ProductPlan
-> SolutionPlugin
-> TenantEntitlement
-> WorkflowTemplateBinding / SkillBinding
-> Agent / Workflow Run
```

### 8.4 商业模型解释

#### 第一层：平台订阅

提供：

- AI 编排引擎
- 工作流运行
- 审批和审计
- 基础模型额度
- 基础模板使用权

#### 第二层：行业方案包

提供：

- 行业插件
- 行业模板
- 行业 Agent 预设
- 行业 Skill 包
- 行业页面与配置面板

#### 第三层：企业定制交付

提供：

- 企业专属工作流
- 企业专属 Agent 配置
- 企业专属 Prompt / 审核规则
- 企业专属插件能力组合

## 九、工作流类型与创建权限

### 9.1 工作流分层

#### A 类：代码型工作流

特征：

- 包含自定义代码
- 包含新执行器、连接器、复杂后端逻辑
- 可能改动平台运行时边界

结论：

- 只能由管理端制作
- 必须作为插件或受控模板交付
- 可售卖给指定企业

#### B 类：托管型可视化工作流

特征：

- 无代码
- 使用平台白名单节点
- 组合已授权 Skill
- 支持变量、条件、审批、模板配置

结论：

- 管理端可以创建并分发
- 企业端可以使用
- 企业端可在受限条件下复制为企业版

#### C 类：企业自建简单工作流

特征：

- 无代码
- 仅可使用已授权白名单能力
- 不允许新增系统级能力
- 不允许绕过审批与权限边界

结论：

- 企业端允许创建
- 企业自己管理
- 管理端不介入企业日常运营

### 9.2 创建权限矩阵

| 能力 | 管理端 | 企业端 |
|---|---|---|
| 安装行业解决方案插件 | 允许 | 不允许 |
| 创建代码型工作流 | 允许 | 不允许 |
| 创建托管型可视化工作流 | 允许 | 可复制受限模板 |
| 创建企业自建简单工作流 | 不需要 | 允许 |
| 新增代码执行节点 | 允许 | 不允许 |
| 新增外部连接器 | 允许 | 不允许 |
| 组合已授权白名单 Skill | 允许 | 允许 |
| 修改平台级审批基线 | 允许 | 不允许 |
| 管理企业审批实例 | 不介入 | 允许 |
| 紧急禁用企业工作流 | 允许 | 不需要 |

### 9.3 企业自建简单工作流的允许范围

允许节点：

- `trigger`
- `input`
- `router`
- `condition`
- `llm`
- `tool`
- `approval`
- `merge`
- `memory`
- `output`

禁止内容：

- 自定义 Python / JS 代码
- 任意 HTTP 请求
- 自定义数据库连接
- 新执行器注册
- 平台运行时修改
- 未授权高风险外部写操作

平台原则：

> 企业可以编排，不可以扩核。

## 十、统一运行时模型

平台必须使用同一套运行时承载固定流、混合流和纯 AI 流。

建议核心对象：

- `WorkflowTemplate`
- `WorkflowTemplateVersion`
- `WorkflowRun`
- `WorkflowNodeRun`
- `ExecutionArtifact`
- `ApprovalTask`

### 10.1 三种运行模式

#### `deterministic`

固定工作流，步骤和顺序已确定。

#### `hybrid`

主骨架固定，局部节点交给 AI 做路由、工具选择或参数推断。

#### `agentic`

给出目标和边界，由 Planner 生成动态步骤并执行。

### 10.2 统一执行链路

```text
接收任务
-> 选择模板或 Planner
-> 创建 WorkflowRun
-> 逐节点执行并生成 NodeRun
-> 每个节点输出 Artifact
-> 高风险节点触发 ApprovalTask
-> 审批通过后继续
-> 最终产出结果并归档
```

### 10.3 WorkflowRun 状态机

建议状态：

- `draft`
- `queued`
- `planning`
- `running`
- `waiting_approval`
- `resumed`
- `completed`
- `failed`
- `cancelled`

建议状态流转：

```text
draft
-> queued
-> planning
-> running
-> waiting_approval
-> resumed
-> completed

running
-> failed
-> cancelled

waiting_approval
-> approved -> resumed
-> rejected -> cancelled
-> expired -> failed
```

### 10.4 WorkflowNodeRun 状态

- `pending`
- `running`
- `waiting_approval`
- `success`
- `failed`
- `skipped`
- `cancelled`

### 10.5 Artifact 内容

建议保存：

- 输入快照
- Prompt 快照
- LLM 输出
- 工具结果
- 动作预览
- 审批意见
- 风险说明
- 最终结论

## 十一、L4：高自治执行 + 强人工审核闸门

### 11.1 定义

L4 指：

- Agent 可以自主规划多个步骤
- 可以连续调用多个已授权能力
- 可以形成跨节点动作链
- 关键节点必须审批
- 所有关键动作必须有审计与可回放能力

### 11.2 L4 默认要求

- 高风险节点必须生成 `Action Preview`
- 所有外部写操作必须留存 `before / after artifact`
- 支持单人审批或双人审批
- 支持驳回、重新提交、超时失效
- 必须记录执行证据链

### 11.3 当前阶段建议

第一阶段可以建设 L4 架构，但行业样板先只做低风险内容生产与审核，不直接进入外部平台自动发布。

## 十二、插件市场与行业解决方案插件

### 12.1 行业解决方案插件的定位

行业解决方案插件是插件市场中的正式插件类别，不是独立于插件系统的特殊对象。

建议分类：

- `capability_plugin`
- `solution_plugin`
- `ui_plugin`
- `content_plugin`

其中：

- `solution_plugin` 负责行业样板包
- `capability_plugin` 负责连接器、执行器、复杂能力扩展

### 12.2 行业解决方案插件建议包含

- `plugin.yaml`
- 页面扩展
- `SkillPackage`
- `Skill`
- `WorkflowTemplate`
- `AgentProfile` 预设
- `PromptTemplate`
- `ApprovalPolicy` 预设
- 方案元数据
- 版本与授权信息

### 12.3 与现有插件系统的对齐原则

- 继续使用 `plugin.yaml`
- 继续使用 `PluginBase`
- 继续通过 `extensions.capabilities[*]` 声明能力
- 继续通过 `extensions.skills[*]` 同步 Skill 投影
- 继续通过 `source_plugin` 标识插件来源
- 行业包只在 `admin` / `tenant` 端落地，不扩展到当前不支持的 `user` 端插件

## 十三、最小行业样板：爆款短视频增长方案包

### 13.1 样板目标

用一个足够直观、足够有编排感、又不涉及高风险自动执行的行业包，验证平台内核是否合理。

推荐样板：

- 插件名：`short-video-growth`
- 中文名：`爆款短视频增长方案包`

### 13.2 第一版边界

第一版只做到：

- 热点发现
- 选题生成
- 脚本生成
- 标题 / 封面文案生成
- 内容审核
- 草稿归档
- 复盘建议

第一版不做：

- 直接发布到抖音 / 快手
- 自动跨平台发布
- 自动评论互动
- 自动账号矩阵运营

### 13.3 行业插件结构建议

```text
short-video-growth/
├── plugin.yaml
├── backend/
```

### 13.4 内置模板建议

#### 1. 热点选题工作流

流程：

```text
输入赛道与账号定位
-> 联网抓热点
-> 竞品拆解
-> AI 生成选题池
-> 人工筛选
-> 入库
```

#### 2. 爆款脚本草稿工作流

流程：

```text
选择选题
-> 生成 3 套内容结构
-> 生成口播脚本
-> 生成标题与封面文案
-> 审核
-> 保存草稿
```

#### 3. 内容审核工作流

流程：

```text
检查品牌调性
-> 检查敏感表达
-> 检查平台规则
-> 给出修改建议
-> 审核通过后归档
```

#### 4. 复盘优化工作流

流程：

```text
输入内容表现数据
-> 找高表现与低表现样本
-> AI 归因
-> 生成下周优化建议
```

### 13.5 企业端输入的核心价值

企业端不负责造底层工具，而负责输入业务知识：

- 品牌定位
- 账号风格
- 目标人群
- 禁用词
- 审核规范
- 产品资料
- 素材库
- 过往爆款样本
- 表达偏好

平台提供：

- 热点采集能力
- 选题分析能力
- 脚本草稿生成能力
- 审核工作流
- 运行时编排和审计能力

## 十四、第一阶段建议建设顺序

### Phase 1：平台内核与授权

- WorkflowTemplate / Run / NodeRun / Artifact / ApprovalTask
- SolutionPlugin / TenantEntitlement / CustomDeliveryEntitlement
- 管理端分发与企业端可见性控制

### Phase 2：工作流创建边界

- 管理端托管型可视化工作流
- 企业端简单工作流

### Phase 3：L4 审批治理

- 审批中心
- 风险等级
- 动作预览
- 双人审批
- 回放审计

### Phase 4：爆款短视频行业样板

- 行业解决方案插件安装
- 模板分发

- 企业知识注入
- 热点 -> 脚本 -> 审核 -> 草稿闭环

## 十五、关键结论

1. 行业解决方案中心应并入插件市场，并以插件形式安装和授权。
2. 平台的重点不是让企业开发底层工具，而是让企业使用平台能力并提供自己的业务知识。
3. 代码型工作流必须由管理端交付；企业端只允许创建无代码简单工作流。
4. 平台必须同时支持固定工作流、混合工作流、纯 AI 编排，但运行时统一。
5. 管理权由所有权决定，管理端不介入企业日常工作流运营。
6. 高自治执行必须默认具备强人工审核、证据链和可回放能力。
7. 第一版行业样板建议采用“爆款短视频增长方案包”，并控制在“内容草稿”边界内。

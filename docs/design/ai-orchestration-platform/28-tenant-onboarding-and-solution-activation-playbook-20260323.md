# AI 编排与工作流平台企业开通与方案激活作战手册（2026-03-23）

## 一、文档目标

本文档用于定义企业从签约、开通、方案选择、配置准备、试运行到正式上线的标准激活流程。

这份文档要回答的核心问题是：

1. 企业购买平台或方案后，怎样才算真正“开通成功”。
2. 平台方和企业方分别要准备哪些东西。
3. 方案插件、工作流模板、知识资产、连接器、审批和角色权限应该按什么顺序激活。
4. 企业何时进入试点、何时进入正式生产、何时进入稳定运营。
5. 如何把开通从“项目经理盯人”沉淀为标准交付作战机制。

本文档是平台运营、交付、企业成功和企业侧启用的共同作战标准。

---

## 二、核心结论

### 2.1 签约不等于开通，安装不等于激活

企业从购买到真正用起来，中间至少还隔着：

- 权益开通
- 角色建模
- 方案安装
- 知识与数据准备
- 连接器绑定
- 审批与风险确认
- 试运行验收

如果这些不做完，平台就只是“买了一个后台”。

### 2.2 企业开通必须被当作正式项目治理，而不是临时客服过程

建议每次正式开通都形成：

- 开通项目
- 责任人
- 准备清单
- 风险清单
- 验收清单
- 上线窗口

### 2.3 平台方负责能力和方法，企业方负责业务信息和启用决策

平台方负责：

- 平台与方案能力
- 标准配置方法
- 交付作战包
- 风险提示

企业方负责：

- 业务规则
- 数据准备
- 审批人和运营人
- 连接器授权
- 试点放行和正式放行

### 2.4 先做小范围激活，再做正式扩量

第一阶段不建议企业一装好就全量启用。

更合理的是：

- 先 `sandbox`
- 再 `pilot`
- 再 `tenant_prod`

这样才能在真实场景下逐步收敛配置、风险和协作方式。

### 2.5 行业方案激活必须与企业基线配置分开

企业装上一个行业方案后，不代表可以直接运行。

至少还需要企业补齐：

- 品牌和业务规则
- 组织角色与审批链
- 连接器凭据与字段映射
- 样本与知识
- 指标口径和成功定义

### 2.6 第一阶段要先把开通流程产品化，而不是追求完全自动化

第一阶段重点应是：

- 有标准清单
- 有责任绑定
- 有状态看板
- 有签字验收

而不是一开始就做全自动无人交付。

## 三、为什么必须单独写这份文档

前面的文档已经写了：

- 方案插件
- 定制交付
- 企业运营控制台
- 交付规格包和验收包

但平台仍然缺一份“企业真正如何从 0 到 1 启用”的标准手册。

如果这层不单独写，后面常见问题会是：

1. 企业装了插件，但没有配置，平台看起来已交付，企业实际上无法用。
2. 权限、审批、连接器、知识配置的顺序混乱，导致试运行反复返工。
3. 企业成功、交付、售后和平台运营各自理解的“上线”含义不同。
4. 企业进入生产后才发现关键审批人、关键数据或关键授权根本没准备好。

所以，这份文档是在回答：

> 平台如何把“卖出去”真正变成“用起来、跑起来、稳下来”。

## 四、正式对象模型建议

建议引入以下对象：

| 对象 | 作用 |
|---|---|
| `activation_project` | 一次企业开通/方案激活项目 |
| `readiness_checklist` | 准备清单 |
| `tenant_baseline_profile` | 企业基础画像和基线配置 |
| `solution_activation_plan` | 某方案在某企业的激活计划 |
| `cutover_plan` | 切换上线计划 |
| `hypercare_window` | 上线后护航期 |
| `acceptance_signoff` | 启用签字记录 |

## 4.1 `tenant_baseline_profile` 建议包含

- 企业组织与角色映射
- 基础业务目标
- 风险承受范围
- 审批模式
- 关键连接器清单
- 知识和素材准备状态
- 指标口径

## 五、企业开通标准阶段

建议统一分为八个阶段。

## 5.1 阶段一：资格确认 `fit_and_scope`

目标是回答：

- 企业买的是平台底座、行业方案，还是定制交付
- 计划先启用哪些场景
- 哪些场景第一阶段先不做
- 关键风险和依赖是什么

### 5.1.1 输出物建议

- 场景范围清单
- 非范围清单
- 风险初判
- 责任人映射

## 5.2 阶段二：租户与权益开通 `tenant_provisioning`

包括：

- 企业租户创建
- 套餐权益绑定
- 方案 License 开通
- 企业管理员初始化

## 5.3 阶段三：方案安装与基线配置 `solution_installation`

包括：

- 安装方案插件
- 激活默认模板
- 确认可用工作流
- 设定企业级默认配置

### 5.3.1 为什么这一步不应直接进入试运行

因为方案只是平台提供的起点。

企业真正可运行，还要有自己的：

- 业务规则
- 审批链
- 数据映射
- 连接器权限

## 5.4 阶段四：角色、审批与运营模型配置 `org_and_policy_setup`

包括：

- 角色权限分配
- 协作通道分配
- 审批链配置
- 风险级别与例外策略确认

## 5.5 阶段五：知识、数据与连接器准备 `context_and_connector_setup`

包括：

- 企业知识导入
- 素材与样本导入
- 指标数据源确认
- 外部系统凭据绑定
- 字段映射和干跑验证

## 5.6 阶段六：沙盒试运行 `sandbox_acceptance`

建议使用：

- 样本数据
- 低风险真实数据
- 只读连接器
- 干跑模式

进行：

- 流程回放
- 草稿验收
- 审批路径演练
- 异常恢复演练

## 5.7 阶段七：试点上线 `pilot_go_live`

试点应至少收敛：

- 适用范围
- 操作窗口
- 风险控制
- 观察指标
- 失败回退方式

## 5.8 阶段八：正式扩量与护航 `prod_and_hypercare`

正式生产后，不应立刻把责任完全甩给企业。

建议设立：

- 护航期
- 每日问题汇总
- 关键指标观察
- 异常快速升级链路

## 六、平台方与企业方的职责边界

## 6.1 平台方职责

- 提供平台与方案能力
- 提供安装、配置、干跑、验收方法
- 提供交付规格包和限制说明
- 处理平台缺陷和托管能力问题

## 6.2 企业方职责

- 提供业务规则和上下文
- 指定负责人、审批人、运营人
- 提供合法数据和系统授权
- 决定是否进入试点和正式生产

## 6.3 不应混淆的边界

平台方不应代企业长期运营。

企业方也不应要求平台方把所有业务准备工作都替自己完成。

平台方给的是：

- 能力
- 方法
- 模板
- 托管生产力

企业方必须补齐：

- 业务知识
- 组织流程
- 最终启用决策

---

## 七、开通完成的正式判定标准

建议把“开通完成”正式拆成三个等级：

| 状态 | 含义 |
|---|---|
| `provisioned` | 租户和权益已创建，但未完成业务激活 |
| `activated` | 方案已装好、关键配置完成，可进入试点 |
| `live` | 已通过试点并进入正式生产 |

### 7.1 `live` 前建议强制满足的条件

- 权限和角色已分配
- 审批链已验证
- 高风险连接器已干跑通过
- 最小测试和验收记录已完成
- 企业负责人已确认上线窗口

---

## 八、与企业运营控制台的关系

企业运营控制台不只是给已上线企业用，也应支撑开通过程。

建议在企业或交付视角中提供：

- 当前准备状态
- 缺失项清单
- 待审批项
- 待干跑项
- 待验收项
- 上线倒计时与风险提示

这样开通过程就不再依赖项目经理手工表格。

## 十、第一阶段实施建议

第一阶段建议至少产品化以下内容：

| 能力 | 建议 |
|---|---|
| 开通项目卡片 | 让每个企业激活有状态可追踪 |
| 准备清单模板 | 按平台、方案、企业分层显示缺项 |
| 角色与审批配置向导 | 避免企业第一次配置混乱 |
| 连接器干跑清单 | 所有高风险外部动作必须过一遍 |
| 沙盒验收记录 | 每个企业都留痕 |
| 试点切换单 | 进入生产前正式确认 |
| 护航期看板 | 上线后集中观察关键问题 |

第一阶段的目标不是让开通过程完全无人化，而是先让每家企业的开通都有标准路径、有责任、有验收、有上线判定。

# AI 编排与工作流平台审批与风险闸门规范（2026-03-23）

## 一、文档目标

本文档定义平台级的审批、风险分级与执行闸门规则，重点回答以下问题：

1. 什么情况下 AI 可以直接执行，什么情况下必须人工确认或审批。
2. 管理端、企业端、方案包、工作流节点各自对审批规则拥有什么权限。
3. `L4` 高自治执行如何在不失控的前提下落地。
4. 审批实例、预览包、审计证据链应如何设计，才能支撑后续复盘与责任追踪。

本文档是平台通用规范，不绑定某个单一行业。

---

## 二、核心结论

### 2.1 审批闸门不是页面提醒，而是运行时强约束

审批与风险闸门必须在运行时生效，而不是只在前端做一个“确认弹窗”。

结论：

- 页面提示只能算交互层辅助。
- 最终是否可执行，必须由运行时策略解析结果决定。

### 2.2 要区分“确认”“审批”“禁止”

平台至少要区分三类动作：

- `user_confirmation`
- `formal_approval`
- `hard_block`

说明：

- `user_confirmation` 是请求发起人的即时确认。
- `formal_approval` 是正式审批任务，需有审批人、审批记录、超时和意见。
- `hard_block` 表示该动作在当前上下文下根本不允许执行。

### 2.3 `L4` 是自治等级，不是风险等级

本平台中的 `L4` 代表：

> 高自治执行 + 强人工审核闸门

但自治高，不等于风险一定高。

因此必须同时存在两套尺度：

- 自治等级：描述 Agent 拥有多大自主规划权
- 风险等级：描述当前动作本身有多危险

最终闸门应由两者共同决定。

### 2.4 谁拥有工作流，谁负责实例审批

坚持前文已确认原则：

> 谁的工作流谁来管理。

因此：

- 企业自有工作流的日常审批，由企业端负责。
- 平台方不代替企业审批日常业务实例。
- 管理端只负责平台基线、方案预设、紧急禁用和跨租户治理。

### 2.5 企业可以加严，不能突破平台底线

审批策略应允许多层叠加，但只允许下层更严格，不允许更宽松。

结论：

- 企业可以追加审批人、缩短超时、提高风险门槛。
- 企业不能移除平台强制审批节点。
- 企业不能把平台定义的 `hard_block` 改成可执行。

## 三、先区分两套等级体系

### 3.1 自治等级

建议平台对运行自治程度采用如下分层：

| 等级 | 名称 | 说明 |
|---|---|---|
| `L1` | 固定执行 | 流程和路径基本固定，AI 只生成内容或参数 |
| `L2` | 辅助决策 | 主骨架固定，AI 可做局部路由和推荐 |
| `L3` | 受限 Agentic | AI 可在边界内规划若干步骤，但可用能力和预算受控 |
| `L4` | 高自治执行 | AI 可连续规划并调用多个能力，但必须带强人工审核闸门 |

### 3.2 风险等级

建议平台对动作风险采用如下分层：

| 等级 | 名称 | 默认处理 |
|---|---|---|
| `R0` | 只读分析 | 直接执行 + 审计 |
| `R1` | 低风险生成 | 可直接执行，必要时请求人确认 |
| `R2` | 中风险业务动作 | 单人审批 |
| `R3` | 高风险业务动作 | 双人或顺序审批 |
| `R4` | 受控或禁止动作 | 平台托管执行或直接禁止 |

### 3.3 最终闸门由两者共同计算

建议规则：

- 先算当前动作风险等级。
- 再看当前工作流自治等级是否抬高最低审批要求。
- 取二者中的更严格结果作为最终闸门。

示例：

- `L1 + R0`：直接执行。
- `L2 + R1`：可直接执行，保留确认能力。
- `L4 + R1`：虽然动作本身低风险，但因自治等级高，至少要求计划预览或关键节点确认。
- `L4 + R3`：必须正式审批，且需完整证据链。

## 四、风险判定维度

平台不要只用“节点类型”来判断风险，应综合以下维度：

1. 是否是外部写操作。
2. 是否会修改企业关键数据。
3. 是否涉及批量操作。
4. 是否不可逆。
5. 是否涉及金钱、合同、合规、法务或品牌风险。
6. 是否可能跨租户、跨账号或跨系统传播。
7. 是否由 Agent 自主决定路径，而非用户显式指定。
8. 是否依赖联网信息且结果可能快速过时。
9. 是否缺少足够证据或预览包。

### 4.1 建议的风险维度字段

为了后续可计算，建议风险评估快照至少包含：

- `data_sensitivity`
- `external_write`
- `batch_size`
- `irreversible`
- `financial_impact`
- `compliance_impact`
- `brand_impact`
- `cross_scope_impact`
- `autonomy_level`
- `evidence_completeness`

### 4.2 风险评分不是目的，闸门动作才是目的

平台内部可以做数值评分，但外部治理语义应收敛为“闸门动作”。

推荐闸门动作枚举：

- `allow`
- `allow_with_confirmation`
- `require_single_approval`
- `require_dual_approval`
- `managed_only`
- `deny`

## 五、风险等级与默认闸门矩阵

| 风险等级 | 典型场景 | 默认闸门 | 企业简单工作流是否允许 |
|---|---|---|---|
| `R0` | 联网检索、趋势分析、报表生成、只读查询 | `allow` | 允许 |
| `R1` | 生成草稿、生成建议、内部标签分类、非覆盖式内容生成 | `allow_with_confirmation` | 允许 |
| `R2` | 覆盖草稿、入库为正式候选、发起内部流转、修改有限业务记录 | `require_single_approval` | 允许 |
| `R3` | 批量写入、对外提交、价格修改、库存建议直写、合规敏感输出 | `require_dual_approval` | 受限允许 |
| `R4` | 代码执行、跨租户影响、不可逆删除、平台内核变更、高危外部写操作 | `managed_only` 或 `deny` | 不允许 |

### 5.1 `R4` 的两个处理分支

`R4` 不一定都直接拒绝，可分两类：

- `managed_only`
- `deny`

其中：

- `managed_only` 表示只能由平台托管能力或受控方案执行。
- `deny` 表示当前平台阶段根本不支持。

### 5.2 平台第一阶段的默认保守策略

第一阶段建议：

- 所有“直接对外发布”的动作至少视为 `R3`。
- 所有“代码执行、系统配置变更、连接器安装、平台数据写入”视为 `R4`。
- 所有“仅生成草稿、不对外提交”的内容生产默认不高于 `R2`。

## 六、审批策略分层与作用域

### 6.1 建议采用四层策略

审批规则建议按以下四层叠加：

1. 平台基线策略 `platform_baseline_policy`
2. 方案包预设策略 `solution_preset_policy`
3. 企业覆盖策略 `tenant_overlay_policy`
4. 工作流或节点局部策略 `workflow_policy`

### 6.2 各层职责

#### 平台基线策略

由管理端维护，职责是定义全平台不可突破的底线，例如：

- 哪些能力永远不能在企业简单工作流出现
- 哪些动作最低必须双人审批
- 哪些节点必须生成预览包

#### 方案包预设策略

由解决方案插件随包交付，职责是定义该行业方案的推荐风险治理方式，例如：

- 某个模板默认审批节点
- 某类草稿默认走品牌审核
- 某类输出默认要求法务角色审核

#### 企业覆盖策略

由企业端维护，职责是把方案包或平台能力接到企业自己的组织上，例如：

- 绑定本企业审批角色或审批组
- 加严审批条件
- 缩短超时
- 增加会签人

#### 工作流或节点局部策略

由模板或具体工作流配置指定，用于表达某个节点的特殊要求，例如：

- 节点 A 一定要审批
- 节点 B 只要用户确认
- 节点 C 的审批意见必须填写理由

### 6.3 生效优先级

建议固定优先级如下：

```text
hard_block
> platform_baseline_policy
> solution_preset_policy
> tenant_overlay_policy
> workflow_policy
```

解释：

- 下层可以加严，但不能降级上层要求。
- 任一层算出 `deny`，最终即 `deny`。

### 6.4 作用域必须明确

审批策略本身建议带以下作用域字段：

| 字段 | 说明 |
|---|---|
| `policy_scope` | `platform_global` / `solution_plugin` / `tenant_local` |
| `target_scope` | `plugin` / `workflow_template` / `tenant_workflow` / `agent_profile` / `capability_class` |
| `owner_type` | `platform` / `tenant` |
| `allow_lower_scope_override` | 是否允许下层覆盖 |
| `override_mode` | `tighten_only` / `full_override` |

建议默认：

- 平台基线：`tighten_only`
- 方案包预设：`tighten_only`
- 企业自有工作流：可在企业本地 `full_override`，但仍不得越过平台基线

## 七、所有权与职责边界

### 7.1 平台拥有的职责

管理端负责：

- 定义平台底线风险模型
- 定义哪些能力可出现在企业简单工作流
- 为解决方案插件提供审批预设
- 做全局监控、冻结、禁用、事后审计

管理端不负责：

- 代企业审批其日常业务实例
- 代企业决定业务是否上线
- 长期运营企业内部审批流

### 7.2 企业拥有的职责

企业端负责：

- 维护本企业审批角色与审批人
- 处理本企业审批任务
- 决定企业本地是否加严审批
- 管理本企业工作流的审批时效与流转方式

### 7.3 哪些场景允许管理端插手

管理端只应在以下场景介入：

1. 平台风控触发紧急冻结。
2. 方案插件被禁用或 License 失效。
3. 平台托管交付的代码型工作流需要升级或回滚。
4. 首次启用高危受控能力时，需要平台做上架侧审核。

## 八、不要把前端确认弹窗和正式审批混为一谈

当前项目已经有页面操作确认与 AI 操作审计机制，这很好，但它只能解决一部分问题。

建议明确分层：

### 8.1 交互确认

适合：

- 单用户即时确认
- 页面内危险按钮确认
- 轻量可逆操作

特点：

- 无独立审批任务
- 通常由请求发起人完成
- 更偏向 UI 层交互保护

### 8.2 工作流正式审批

适合：

- 需要他人批准
- 需要审批超时
- 需要审批意见
- 需要双人或顺序审批

特点：

- 必须创建正式 `ApprovalTask`
- 审批结果直接影响 `WorkflowRun` 继续或终止
- 必须保留证据链

### 8.3 平台硬阻断

适合：

- 当前能力不在授权范围内
- 风险超过可运行边界
- 企业简单工作流尝试使用平台禁止能力

特点：

- 不创建审批任务
- 直接返回禁止原因

## 九、审批对象模型建议

本文档在 `02-platform-data-model-20260323.md` 基础上，对审批对象做进一步细化。

### 9.1 `ApprovalPolicy` 建议补充字段

除已有基础字段外，建议补充：

| 字段 | 说明 |
|---|---|
| `policy_scope` | 策略层级 |
| `gate_action` | 默认闸门动作 |
| `min_risk_level` | 命中最低风险等级 |
| `min_autonomy_level` | 命中最低自治等级 |
| `approver_selector_json` | 审批人选择规则 |
| `timeout_minutes` | 审批超时 |
| `on_timeout_action` | 超时策略 |
| `on_reject_action` | 驳回策略 |
| `require_reason` | 是否必须填写理由 |
| `require_preview_artifact` | 是否必须附预览包 |
| `require_evidence_artifacts` | 是否必须附证据链 |

### 9.2 `ApprovalTask` 建议补充字段

| 字段 | 说明 |
|---|---|
| `gate_action` | 本次实际闸门动作 |
| `required_approvals` | 需要多少个有效审批 |
| `received_approvals` | 当前已完成多少个 |
| `approval_scope` | `tenant_business` / `platform_managed` |
| `policy_snapshot_json` | 运行时策略快照 |
| `preview_artifact_id` | 对应的预览包 |
| `risk_snapshot_json` | 本次命中的风险维度快照 |
| `escalation_at` | 升级或提醒时间 |
| `resubmittable` | 是否允许修改后重提 |

### 9.3 `ApprovalDecision` 建议补充字段

| 字段 | 说明 |
|---|---|
| `decision_role_code` | 审批角色 |
| `decision_source` | `manual_ui` / `api` / `delegated` |
| `comment_required` | 是否要求意见 |
| `attachment_artifact_id` | 附加说明或附件 |
| `decision_snapshot_json` | 审批时看到的快照 |

### 9.4 必须保留运行时快照，而不是只存引用

审批任务一旦创建，以下内容建议固化为快照：

- 风险等级结果
- 当时生效的审批策略
- 当时的预览包
- 当时的输入摘要
- 当时的模型与工具调用摘要

原因：

- 原模板可能后续升级
- 企业规则可能后续变化
- 事后追责必须还原“当时为什么能通过”

## 十、预览包与证据链规范

### 10.1 高风险节点必须生成 `Approval Packet`

建议把正式审批看到的材料统一称为 `Approval Packet`，至少包含：

1. 动作摘要
2. 业务目的
3. 输入来源
4. 联网来源摘要
5. 模型结论摘要
6. 计划步骤摘要
7. 影响范围
8. 前后对比预览
9. 风险说明
10. 回滚或补救建议

### 10.2 联网分析必须带来源快照

如果动作依赖联网分析，审批包中应至少包含：

- 关键信息来源列表
- 抓取时间
- 结论生成时间
- 重要证据摘录或结构化摘要

这样可以避免审批人在面对时效性极强的信息时没有上下文。

### 10.3 建议的 Artifact 分类

审批相关 Artifact 建议至少有：

- `risk_assessment`
- `action_preview`
- `approval_packet`
- `evidence_bundle`
- `before_snapshot`
- `after_preview`
- `decision_note`

## 十一、`L4` 高自治执行的审批模型

### 11.1 `L4` 不应只在最后一步审批

对于 `L4`，建议至少有两层闸门：

1. 计划闸门
2. 动作闸门

### 11.2 计划闸门

当 Agent 需要自主规划多个步骤时，应先生成：

- 目标说明
- 计划步骤
- 可能用到的能力
- 预估风险范围
- 中止条件

此时应允许人工先批准“这条执行计划是否可以进入运行阶段”。

### 11.3 动作闸门

即使计划已通过，运行时遇到高风险节点时，仍需再审批。

原因：

- 计划批准不等于所有实际动作都批准
- 运行时可能出现新证据或新分支

### 11.4 `L4` 的最低基线

建议 `L4` 默认至少满足：

- 必须生成计划预览
- 必须记录每一步关键证据
- 高风险节点不得自动越过审批
- 审批超时后不得偷偷继续执行
- 必须支持中止、回放和追责

## 十二、审批模式建议

第一阶段建议支持以下几类审批模式即可：

| 模式 | 说明 | 适用场景 |
|---|---|---|
| `single` | 单人审批 | `R2` 默认 |
| `dual_parallel` | 双人并行审批 | `R3` 常见 |
| `sequential` | 顺序审批 | 品牌后法务、运营后老板 |
| `requester_confirm` | 发起人确认 | `R1` 低风险动作 |

### 12.1 第一阶段不建议上太复杂的审批编排

例如以下能力可以后置：

- 多分支会签
- 比例投票
- 复杂组织树自动升级
- 跨企业联合审批

第一阶段重点是把运行时阻断、审批证据、状态机跑通。

## 十三、状态机与运行时语义

### 13.1 `ApprovalTask` 状态建议

建议继续沿用前文主状态：

- `pending`
- `approved`
- `rejected`
- `expired`
- `cancelled`

对于双人审批，不建议额外引入太多顶层状态，而是通过聚合决策来判断：

- 未达到阈值前仍为 `pending`
- 达到通过阈值后变为 `approved`
- 命中拒绝条件后变为 `rejected`

### 13.2 `WorkflowRun` 与审批联动

建议语义：

```text
running
-> waiting_approval
-> resumed
-> running
-> completed
```

其它分支：

```text
waiting_approval
-> rejected -> cancelled
waiting_approval
-> expired -> failed 或 cancelled
```

### 13.3 驳回后的处理模式

建议策略枚举：

- `cancel_run`
- `return_to_draft`
- `request_revision_and_resubmit`
- `fallback_to_manual`

第一阶段推荐默认：

- 平台托管模板：`cancel_run`
- 企业草稿流：`request_revision_and_resubmit`

## 十四、超时、提醒与升级规则

### 14.1 超时必须显式建模

审批超时后不能悄悄继续，也不能无限挂起。

建议策略：

- `expire_and_fail`
- `expire_and_cancel`
- `escalate_once_then_expire`

### 14.2 提醒与升级

建议审批任务支持：

- 创建时通知
- 临近超时提醒
- 超时后升级提醒

但升级提醒默认仍在企业自己的审批链条内完成，不意味着管理端介入审批。

### 14.3 审批人不可达时的处理

建议允许：

- 手动改派
- 指定候补角色
- 角色级审批而非固定个人审批

---

## 十五、与授权、插件和工作流的联动

审批闸门不是孤立系统，需与授权和方案包联动。

### 15.1 与授权联动

任一动作进入审批前，先做授权校验：

- 企业是否有平台订阅
- 企业是否有该方案包授权
- 节点依赖能力是否已授权
- 插件 License 是否有效

未经授权的动作不进入审批，直接阻断。

### 15.2 与方案插件联动

方案插件可以交付：

- 审批策略预设
- 风险分级建议
- 预览包模板
- 审批页面扩展

但企业侧审批人、审批组和最终日常实例管理权仍归企业。

### 15.3 与企业简单工作流联动

企业简单工作流必须遵守：

- 仅能使用白名单节点
- 高危节点不得通过“删审批节点”来绕过
- 若节点命中平台基线审批，运行时必须补出正式审批任务

---

## 十六、审计、监控与回放要求

审批体系必须天然可审计。

建议至少打通以下链路：

```text
WorkflowRun
-> WorkflowNodeRun
-> ExecutionArtifact
-> ApprovalTask
-> ApprovalDecision
-> AI Action Audit Log
```

### 16.1 企业端视角

企业端应可查看：

- 待审批
- 已审批
- 被驳回
- 审批耗时
- 对应运行结果

### 16.2 管理端视角

管理端应以只读治理视角查看：

- 高风险运行数量
- 高频驳回模板
- 经常超时的方案包
- 风险闸门命中统计
- 全局紧急禁用入口

---

## 十七、第一阶段实施建议

### Phase 1：先把“阻断”做对

优先建设：

- 风险评估快照
- 正式 `ApprovalTask`
- `waiting_approval` 运行状态
- 超时与驳回处理
- 审批证据包

### Phase 2：再做多层策略叠加

补充：

- 平台基线策略
- 方案包预设策略
- 企业覆盖策略
- 有效策略解析器

### Phase 3：最后做 `L4` 两阶段审批

补充：

- 计划审批
- 动作审批
- 审批前计划预览
- 高自治回放能力

---

## 十八、关键结论

1. 审批闸门必须是运行时强约束，不能只做前端提醒。
2. 必须同时区分自治等级和风险等级，最终闸门由两者共同决定。
3. 审批策略应按平台基线、方案预设、企业覆盖、工作流局部四层叠加，且下层只能加严不能放宽。
4. 企业日常业务实例审批应归企业端负责，管理端只做平台治理和紧急干预。
5. `L4` 高自治执行至少应具备计划闸门、动作闸门、证据链和回放能力。
6. 高风险节点必须生成正式 `Approval Packet`，包括预览、证据、影响范围和风险说明。
7. 第一阶段先把“阻断、审批、回放、审计”闭环做扎实，再上更复杂的审批编排能力。

# AI 编排与工作流平台开放集成与嵌入式编排规范（2026-03-23）

## 一、文档目标

本文档用于定义平台对外开放能力，包括 API、Webhook、事件订阅、嵌入式工作台、外部触发入口和外部回执链路的统一规范。

这份文档要回答的核心问题是：

1. 外部系统如何安全地触发平台工作流、获取结果、接收回调。
2. 平台如何把编排能力嵌入第三方系统，而不是要求所有用户都进入平台完整后台。
3. 对外开放时，如何继续遵守多企业隔离、权限、审批、计费、配额和风险治理。
4. 哪些开放能力允许企业自用，哪些必须由平台方托管与审核。
5. 平台如何把“开放集成”做成正式产品面，而不是零散接口堆积。

本文档适用于管理端、企业端、插件市场、合作伙伴接入与第三方业务系统集成。

---

## 二、核心结论

### 2.1 开放集成不等于开放数据库和内部实现

平台对外提供的应是受治理的能力接口，而不是内部模型裸露。

外部系统应消费的是：

- 正式 API
- 正式事件
- 正式 Artifact
- 正式回执
- 正式嵌入工作台

而不是直接访问平台内部表结构和执行细节。

### 2.2 所有外部入口都必须经过统一策略裁决

外部请求不应绕过：

- 企业作用域
- 权限与授权
- 套餐和 License
- 风险与审批
- 预算与配额
- 数据治理与脱敏

也就是说，对外开放能力只是“多了一层入口”，不应变成“少了一层治理”。

### 2.3 开放能力应分成四类，而不是一股脑叫开放 API

建议正式区分：

1. `inbound_api`
2. `event_and_webhook`
3. `embedded_orchestration`
4. `partner_managed_integration`

不同类型的安全、授权、时延和交互语义完全不同。

### 2.4 嵌入式编排必须保留平台真相，而不是复制一套影子系统

嵌入第三方页面时，真正运行、审批、记账、审计、授权仍应在平台内部完成。

外部宿主系统只应承载：

- 外壳体验
- 局部上下文
- 单点登录桥接
- 必要的宿主操作回调

而不应复制平台内核。

### 2.5 代码型开放能力仍应由平台方生产与审核

与前面整体原则一致：

- 企业可配置开放接入
- 企业可创建简单编排入口
- 复杂代码型 SDK、连接器、嵌入脚本框架、对外事件协议仍应由平台方统一生产和治理

### 2.6 第一阶段应优先开放“可治理入口”，而不是追求接口数量

第一阶段更重要的是：

- 几个真正可商用的开放模式
- 明确的租户与权限边界
- 签名、幂等、回执、限流、审计齐全

而不是一开始把所有内部能力都暴露出去。

## 三、为什么必须单独写这份文档

前面的文档已经把平台内部机制写得很完整了，但要成为 SaaS 平台，必须回答一个更实际的问题：

> 外部系统如何接入这套编排能力。

如果这层不单独写清楚，后面会出现：

1. 每个行业方案自己发明一套接口。
2. 企业要嵌入能力时，只能复制页面或私下写临时脚本。
3. Webhook、API、嵌入、事件流没有统一授权和审计口径。
4. 外部调用绕过审批与配额，平台内部治理形同虚设。

所以，这份文档是在回答：

> 平台如何把“内核能力”变成“可对外集成的产品接口”，同时不牺牲治理能力。

## 四、开放能力的正式分层

## 4.1 `inbound_api`

用于外部系统主动调用平台能力。

典型场景：

- 提交一条分析请求
- 触发某个工作流
- 查询一次运行结果
- 拉取生成的 Artifact

## 4.2 `event_and_webhook`

用于事件驱动式集成。

典型场景：

- 外部业务系统把订单创建、工单更新、线索变化推送给平台
- 平台把审批结果、运行完成、异常告警回调给外部系统

## 4.3 `embedded_orchestration`

用于把平台能力嵌入第三方系统界面。

典型场景：

- 在企业自有 CRM 内嵌“AI 建议面板”
- 在客服后台内嵌“审批与改稿工作台”
- 在 BI 页面内嵌“推荐策略解释卡片”

## 4.4 `partner_managed_integration`

用于合作伙伴或平台方托管的高级集成。

典型场景：

- 平台官方 SDK
- 平台官方嵌入组件
- 平台官方管理型连接器
- 合作伙伴交付的托管接入方案

## 五、对象模型建议

建议正式引入以下对象：

| 对象 | 作用 |
|---|---|
| `integration_app` | 一类对外集成应用定义 |
| `app_installation` | 某企业安装某集成应用的实例 |
| `api_scope_grant` | 可调用能力范围 |
| `credential_binding` | 外部调用凭据绑定 |
| `webhook_subscription` | Webhook 订阅 |
| `event_topic_binding` | 事件主题绑定 |
| `embed_session` | 嵌入式会话 |
| `external_run_request` | 外部发起的一次运行请求 |
| `callback_receipt` | 回调回执 |
| `integration_policy` | 集成侧专属安全与配额策略 |

### 5.1 `integration_app` 不是连接器

这两者必须区分：

- 连接器更偏运行时工具能力
- `integration_app` 更偏外部接入和宿主系统集成

例如：

- “抖音订单读取”更像连接器
- “第三方 ERP 通过 API 触发库存建议工作流”更像开放集成应用

## 六、对外入口的能力语义

## 6.1 同步请求 `sync_request`

适合轻量、短耗时、无高风险外部写动作的场景。

例如：

- 文本改写
- 结构化抽取
- 小型策略建议

## 6.2 异步运行 `async_run`

适合复杂编排、长耗时、多节点、多审批场景。

外部系统提交后，应获得：

- `run_id`
- 初始状态
- 预计回调方式
- 可轮询接口

## 6.3 外部事件触发 `event_trigger`

适合订单、线索、工单、内容发布等事件型业务。

但必须有：

- 幂等键
- 事件签名
- 事件版本
- 重放保护

## 6.4 回调与回执 `callback`

平台回调外部系统时，应至少包含：

- 运行 ID
- 事件类型
- 状态摘要
- 结果引用
- 错误信息或审批状态
- 签名和时间戳

## 6.5 嵌入式 UI `embed_ui`

嵌入模式建议至少支持：

- `embedded_task_panel`
- `embedded_approval_panel`
- `embedded_recommendation_panel`
- `embedded_run_console`

不同面板暴露的字段和操作权限应不同。

## 七、安全、权限与租户边界

## 7.1 所有外部调用必须绑定企业作用域

不允许存在“不知道归属哪个企业”的开放调用。

至少应明确：

- 调用归属企业
- 调用归属应用安装实例
- 调用者身份或代表身份
- 可访问的工作流/方案/能力范围

## 7.2 认证方式建议

第一阶段建议支持：

- `api_key + secret`
- 短期签名 Token
- 单点登录后生成的嵌入会话 Token
- Webhook 签名校验

### 7.2.1 不建议第一阶段开放的方式

第一阶段不建议把高风险对外能力建立在：

- 永久不过期 Token
- 纯前端明文凭据
- 无签名 Webhook
- 无租户隔离的共享凭据

## 7.3 权限应采用“应用权限 + 用户代理权限 + 策略裁决”三层模型

也就是说，一次外部请求是否能执行，不应只看 Token 对不对。

还应看：

- 这个应用安装实例被授予了哪些能力
- 当前代理用户或系统身份被允许做什么
- 当前策略引擎是否允许在该环境、该套餐、该风险级别下执行

## 7.4 限流、配额和预算必须进入开放能力层

开放能力层至少应支持：

- 每应用限流
- 每企业配额
- 每能力计费
- 每工作流预算
- 异常高频熔断

## 八、嵌入式编排的正式规范

## 8.1 嵌入式体验的本质

嵌入式工作台不是把平台代码复制到第三方系统，而是：

- 平台负责真实能力和治理
- 宿主系统负责承载场景和上下文

## 8.2 宿主系统可提供的上下文类型

宿主系统建议只提供：

- 当前业务对象 ID
- 当前页面筛选条件
- 当前操作人身份映射
- 当前业务动作上下文

宿主系统不应无约束把整页明文数据灌入平台。

## 8.3 嵌入会话 `embed_session`

建议 `embed_session` 至少包含：

- `tenant_id`
- `host_app_id`
- `host_user_ref`
- `allowed_panels`
- `context_scope`
- `expires_at`

## 8.4 宿主操作与平台操作的边界

建议明确：

- 平台负责生成建议、审批、运行、审计
- 宿主系统负责显示结果、承载跳转、必要时执行宿主侧 UI 操作

如果平台要触发宿主动作，应走正式宿主操作协议，而不是脚本任意执行。

## 九、契约、版本与兼容性

## 9.1 API、Webhook、事件都应版本化

后续建议统一定义：

- `api_version`
- `event_contract_version`
- `embed_sdk_version`
- `callback_schema_version`

## 9.2 兼容性策略建议

建议默认遵守：

- 新版本优先向后兼容
- 删除字段前必须有弃用期
- 事件 schema 变化必须有版本标识
- 嵌入组件升级不应默默改变宿主权限

## 9.3 外部集成文档和示例不是可选项

任何对外开放能力正式商用前，至少应有：

- 接口说明
- 字段说明
- 错误码说明
- 签名说明
- 幂等说明
- 示例请求和回调样例

## 十、企业自用与平台托管边界

## 10.1 企业可做的部分

企业可在平台内完成：

- 配置外部触发规则
- 配置回调地址
- 配置嵌入入口的业务上下文映射
- 配置简单表单型 API 入参映射

## 10.2 需要平台方托管的部分

以下能力原则上应由平台方统一生产和审核：

- 官方 SDK
- 官方嵌入组件
- 复杂协议适配器
- 代码型外部系统集成
- 高风险外部写动作协议

这与前面“企业可编排，不可扩核”的原则保持一致。

## 十二、第一阶段实施建议

第一阶段建议优先开放以下能力：

| 能力 | 建议 |
|---|---|
| 异步工作流触发 API | 作为标准对外入口 |
| 运行状态轮询与回调 | 形成完整闭环 |
| 企业侧 Webhook 触发 | 支持常见事件驱动接入 |
| 嵌入式任务/审批/推荐面板 | 先做几个标准嵌入组件 |
| 签名、幂等、限流、审计 | 作为基础能力一起上线 |

第一阶段不建议一开始就做：

- 全量 Graph API
- 任意自定义宿主脚本执行
- 无边界跨企业开放市场 API

第一阶段目标应是：

> 先让平台具备“可安全接入、可安全嵌入、可安全回执”的正式开放能力。

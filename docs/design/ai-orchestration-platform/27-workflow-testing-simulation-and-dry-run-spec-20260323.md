# AI 编排与工作流平台测试、仿真与干跑规范（2026-03-23）

## 一、文档目标

本文档用于定义 AI 编排与工作流平台在正式发布前和正式运行中的测试、仿真、干跑、影子运行和人工验收机制。

这份文档要回答的核心问题是：

1. 工作流、Agent、方案插件、连接器在上线前到底要怎么测。
2. 仿真、干跑、影子运行、评估回归分别解决什么问题。
3. 外部写动作如何做到“不真的写，但能预演真实风险”。
4. 高自治和高风险流程在进入生产前，应该有哪些强制门槛。
5. 平台如何把“测试”做成正式资产，而不是靠几次临时演示。

本文档与发布治理、评估数据集治理、连接器安全和交付验收包强相关。

---

## 二、核心结论

### 2.1 没有测试资产的工作流，不应进入正式发布

平台必须明确：

- 工作流不只是图能保存就算完成
- 行业方案不只是页面能演示就算可交付
- 连接器不只是能连上就算可上线

正式可发布对象，至少要配套：

- 测试样本
- 断言规则
- 仿真说明
- 干跑结果
- 必要的人工验收记录

### 2.2 仿真、干跑、影子运行、评估回归不是一回事

建议正式区分：

- `simulation`
- `dry_run`
- `shadow_run`
- `benchmark_regression`
- `human_acceptance`

它们分别验证：

- 流程逻辑是否正确
- 外部动作是否安全
- 新旧版本在真实输入下是否有偏差
- 质量是否回归
- 业务方是否愿意放行

### 2.3 外部写动作默认先过干跑，而不是先碰生产

凡是：

- 发消息
- 下单
- 改价
- 推送内容
- 创建单据

这类正式外部动作，在第一阶段都应优先支持：

- 干跑预览
- 字段清单预览
- 预计影响说明
- 审批包联动

### 2.4 AI 结果测试必须同时看“结构正确”和“业务合理”

所以测试不应只看：

- 接口是否 200
- Schema 是否通过

还应看：

- 输出是否可用
- 建议是否可解释
- 是否违反业务禁区
- 是否引入高成本或高风险偏差

### 2.5 高自治流程的上线门槛应显著高于普通流程

同样是工作流：

- `deterministic` 主要验证逻辑和连接
- `hybrid` 还要验证 AI 输出稳定性
- `agentic` 必须额外验证策略漂移、异常路径、审批与恢复语义

### 2.6 第一阶段应优先建立“最小但正式”的测试体系

第一阶段不求一次把测试平台做得极复杂，但必须让每个可商用方案有：

- 可回放的样本
- 可执行的仿真
- 可审阅的干跑报告
- 可比较的回归结果

## 三、为什么必须单独写这份文档

虽然前面已经有：

- 运行恢复
- 评估治理
- 交付验收
- 发布和晋级

但还没有一份文档把“上线前怎么验证”完整串起来。

如果这层不单独规范，后面会出现：

1. 评估集很完整，但真正外部动作没人测。
2. 能做离线评分，但图编排逻辑和变量映射错误上线才发现。
3. 行业方案能演示，但企业一开真数据就出现危险动作。
4. 高自治流程没有影子运行和人工签字，风险不可接受。

所以，这份文档是在回答：

> AI 编排平台如何建立一套从逻辑正确、安全可控，到业务可接受的正式测试体系。

---

## 四、正式测试对象模型

建议引入以下对象：

| 对象 | 作用 |
|---|---|
| `test_suite` | 一组测试集合 |
| `scenario_case` | 单个场景样本 |
| `mock_connector_profile` | 仿真连接器画像 |
| `assertion_rule` | 断言规则 |
| `simulation_run` | 一次仿真运行记录 |
| `dry_run_report` | 一次干跑报告 |
| `shadow_run_record` | 一次影子运行比对记录 |
| `acceptance_record` | 人工验收记录 |
| `regression_report` | 回归评估报告 |

## 4.1 `scenario_case` 建议包含的内容

至少包括：

- 输入快照
- 环境说明
- 预期断言
- 风险等级
- 是否允许外部动作
- 是否需要人工审阅

## 4.2 `assertion_rule` 不应只有一种类型

建议支持：

- `schema_assertion`
- `policy_assertion`
- `artifact_assertion`
- `risk_assertion`
- `cost_assertion`
- `external_payload_assertion`
- `human_check_required`

## 五、五类验证机制的正式区分

## 5.1 仿真 `simulation`

仿真用于验证：

- 图是否能跑通
- 节点编排是否符合预期
- 变量、上下文、Artifact 流转是否正确

仿真特点：

- 使用受控输入
- 外部动作不真正提交
- 可重复回放

## 5.2 干跑 `dry_run`

干跑主要用于外部动作安全验证。

它需要回答：

- 这次如果真的执行，会发什么 payload
- 会调用哪个目标系统
- 会命中哪些高风险字段
- 是否需要审批

### 5.2.1 干跑不是假装运行全流程

干跑的重点不是“跑个假的流程”，而是：

- 对真实动作路径做预演
- 对外发数据做字段级展示
- 对风险做可审查说明

## 5.3 影子运行 `shadow_run`

影子运行用于比较：

- 新版本和旧版本在真实输入下的差异
- 新策略与旧策略的结果偏移
- 是否出现明显成本、时延、审批命中率变化

影子运行原则上：

- 不提交真实外部写动作
- 不影响正式主流程结果
- 重点用于版本替换前验证

## 5.4 基准回归 `benchmark_regression`

基准回归更偏离线质量验证。

重点检查：

- 样本得分是否下降
- 错误类型是否新增
- 业务规则命中是否稳定

## 5.5 人工验收 `human_acceptance`

人工验收用于承接：

- 业务可接受性
- 风险容忍度
- 表达风格与输出可用性
- 特殊行业合规确认

## 六、测试层级建议

建议平台采用分层测试体系。

## 6.1 第一层：静态与契约检查

包括：

- 变量引用闭合
- 节点端口匹配
- Schema 校验
- 未授权技能引用检查
- 审批策略缺失检查

## 6.2 第二层：节点级验证

包括：

- 单节点输入输出验证
- Prompt 模板结构验证
- 连接器参数映射验证
- 外部动作字段白名单验证

## 6.3 第三层：场景级仿真

包括：

- 完整流程回放
- 多路径分支验证
- 异常分支与补偿路径验证

## 6.4 第四层：外部动作干跑

包括：

- 目标地址检查
- 幂等键检查
- Payload 字段检查
- 数据脱敏和作用域检查

## 6.5 第五层：影子运行与小流量验证

包括：

- 与旧版本并行跑
- 真实输入但不写回
- 对比时延、成本、结果和审批差异

## 6.6 第六层：人工签字验收

尤其适用于：

- 高风险外部动作
- `L4` 高自治执行
- 新行业方案首次上线
- 企业关键场景启用

---

## 七、不同运行模式的测试要求

## 7.1 `deterministic`

重点验证：

- 流程逻辑
- 参数映射
- 外部系统稳定性

## 7.2 `hybrid`

除以上外，还应验证：

- AI 输出是否符合结构和风格要求
- AI 输出是否稳定落在业务允许范围内

## 7.3 `agentic`

除以上外，必须额外验证：

- 多步决策路径是否可解释
- 是否会误用工具
- 是否会越权扩图
- 审批与接管节点是否正确命中
- 恢复路径是否可行

---

## 八、与审批、风险、成本的联动

## 8.1 风险越高，测试门槛越高

建议至少形成如下规律：

- 低风险只需基础仿真和回归
- 中风险要求干跑和人工抽检
- 高风险要求影子运行和正式审批

## 8.2 成本也应纳入测试结果

测试不应只看“能否产出”，还应看：

- 单次运行成本
- 节点成本峰值
- 检索与模型调用膨胀风险
- 大规模触发时预算是否可控

## 8.3 测试数据也要遵守数据治理

测试用的数据、样本和回放快照，同样应遵守：

- 租户隔离
- 敏感信息脱敏
- 用途限定
- 保留期限

## 九、角色与职责

| 角色 | 主要职责 |
|---|---|
| `solution_designer` | 提供样本与断言、修正设计问题 |
| `platform_reviewer` | 审阅回归、决定是否放行 |
| `connector_operator` | 审查干跑和外部动作安全 |
| `tenant_operator` | 参与场景验收与影子结果确认 |
| `tenant_approver` | 对高风险动作上线做业务放行 |

## 十一、第一阶段实施建议

第一阶段建议先落以下最小闭环：

| 能力 | 建议 |
|---|---|
| 静态校验 | 每次发布候选自动执行 |
| 最小场景仿真 | 每个正式工作流至少一套 |
| 外部动作干跑 | 高风险连接器必须支持 |
| 影子运行 | 版本替换前用于关键场景 |
| 人工验收单 | 高风险和首发方案强制要求 |
| 回归报告归档 | 每次发布都保留可追溯记录 |

第一阶段目标不是测试覆盖率数字有多漂亮，而是让平台真正具备“上线前知道它会怎么跑、会不会乱跑、出了偏差能否提前发现”的能力。

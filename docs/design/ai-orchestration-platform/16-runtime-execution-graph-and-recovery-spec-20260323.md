# AI 编排与工作流平台运行时执行图与恢复规范（2026-03-23）

## 一、文档目标

本文档用于定义平台中的工作流一旦真正开始运行，内部应该如何被表示、如何被暂停和恢复、失败后如何处理、外部写动作如何补偿、人工如何接管。

前面的文档已经定义了很多“运行前”的事情：

- 谁能建工作流
- 谁能触发
- 哪个版本能发布
- 什么数据契约可以流转
- 什么策略会阻断或要求审批

但真正到了运行时，平台还必须回答下面这些问题：

1. 一次 `WorkflowRun` 到底是线性日志，还是图状执行体。
2. 节点失败后是重试、恢复、补偿、跳过，还是直接终止。
3. 高风险外部写动作如果执行了一半，平台怎么处理。
4. `agentic` 模式下动态扩出来的步骤，如何进入同一套治理体系。
5. 人工审核和人工接管进入后，运行图如何继续保持可回放。

这份文档的目标就是把“运行时内核”正式建模出来，避免后续实现时每个模块各做一套恢复逻辑。

---

## 二、核心结论

### 2.1 工作流运行应被视为“执行图”，不是“步骤日志”

平台不能把一次运行只当作一串线性日志。

原因很简单：

- 有条件分支
- 有并行节点
- 有审批暂停
- 有动态计划
- 有重试和恢复
- 有补偿分支

所以更合适的正式语义是：

> 一次工作流运行，是一个带状态、带检查点、带依赖边的运行时执行图。

### 2.2 每个节点执行都必须绑定输入快照、契约快照和策略快照

一个节点之所以能被安全恢复，不是因为我们记得“它大概做了什么”，而是因为我们要能精确还原：

- 它吃了什么输入
- 当时依据什么契约校验
- 当时命中了什么运行时策略
- 产出了什么 Artifact

因此每个 `workflow_node_run` 都应天然带快照，而不是只记录一个状态码。

### 2.3 必须严格区分 `retry`、`resume`、`replay`、`compensate`、`rollback`

这几个动作看起来都像“出了问题后再处理一次”，但语义完全不同。

如果平台不提前区分，后面最容易出现的就是：

- 把外部写动作做了“盲重试”
- 把回滚当成运行时补偿
- 把恢复当成重新从头跑

这些在高自治场景下风险很大。

### 2.4 高风险写动作必须声明“是否可补偿”

平台不能假设所有动作都可以撤回。

应正式区分：

- `compensable`
- `partially_compensable`
- `forward_only`

例如：

- 写草稿通常可补偿
- 外部发布可能只能标记撤回请求
- 某些通知外发一旦发出就是 `forward_only`

### 2.5 平台必须支持自动恢复与人工接管并存

纯自动恢复适合：

- 短时网络故障
- 临时模型错误
- 可幂等的只读节点

但到了以下场景，必须能人工接管：

- 高风险写动作状态不明
- 审批被驳回后要调整材料
- 企业副本存在本地脏数据
- 动态计划需要人工裁决是否继续

---

## 三、为什么现在就必须定义运行时内核

当前平台已经确认：

- 同时支持 `deterministic`、`hybrid`、`agentic`
- 支持审批闸门
- 支持外部触发
- 支持插件方案包
- 支持企业简单工作流和企业副本

这意味着后面运行时绝不可能只是“顺序执行 1 -> 2 -> 3”。

如果不单独定义运行时执行图与恢复规范，后续会快速出现：

1. 不同节点各自实现重试逻辑。
2. 外部写动作失败后不知道能不能继续。
3. 审批节点和系统异常节点混成同一种“等待中”。
4. `agentic` 动态生成的步骤无法进入统一审计和恢复体系。

所以，这份文档本质上是在回答：

> 平台如何把一次复杂 AI 工作流运行，变成一个可恢复、可治理、可接管的正式执行对象。

---

## 四、正式对象模型

建议把运行时相关对象正式抽出来。

### 4.1 核心对象建议

| 对象 | 作用 |
|---|---|
| `workflow_run` | 一次运行实例的总对象 |
| `workflow_node_run` | 某个节点的一次实际执行实例 |
| `runtime_execution_edge` | 运行图中节点之间的依赖边、分支边、补偿边 |
| `execution_checkpoint` | 可恢复的检查点快照 |
| `recovery_task` | 一次失败后的恢复任务记录 |
| `compensation_task` | 一次补偿动作的任务记录 |
| `manual_handover_task` | 一次人工接管或人工恢复动作记录 |
| `execution_snapshot` | 某时刻的图状态、关键变量、Artifact 引用快照 |

### 4.2 `workflow_run` 不只是状态表

建议 `workflow_run` 至少负责：

- 指向运行版本快照
- 指向触发来源
- 指向当前图状态
- 指向当前恢复状态
- 指向当前审批/接管状态

而不是只存：

- status
- started_at
- finished_at

---

## 五、执行图的正式定义

### 5.1 静态图与运行图不是同一个东西

建议正式区分：

| 概念 | 含义 |
|---|---|
| `workflow_definition_graph` | 发布时的结构图 |
| `runtime_execution_graph` | 运行时真正被实例化后的执行图 |

### 5.2 为什么运行图必须单独存在

因为运行过程中会出现很多定义图里没有显式展开的对象：

- 实际分支选择结果
- 并行分支实例
- 动态规划出的步骤
- 重试出来的节点实例
- 补偿分支
- 人工修正后的替代节点

这些都属于运行图，而不是定义图本身。

### 5.3 `agentic` 模式下允许动态扩图，但必须受控

平台可以允许 Planner 或 Agent 在运行时扩展局部步骤，但必须遵守：

1. 动态扩出的节点必须落库成正式 `workflow_node_run`
2. 必须继承当前运行时策略与预算边界
3. 必须记录“由谁规划、为何出现、依据何种契约”

动态扩图不是“临时想到了就直接跑”，而是运行图在治理约束下的受控增长。

---

## 六、运行状态模型

建议分别定义运行级状态和节点级状态。

### 6.1 `workflow_run` 状态建议

| 状态 | 说明 |
|---|---|
| `queued` | 已创建，等待进入执行 |
| `validating` | 做输入与策略预检查 |
| `planning` | 进行动态规划或图展开 |
| `running` | 正在执行 |
| `waiting_approval` | 正在等待审批 |
| `waiting_input` | 正在等待人工补充输入 |
| `paused` | 被人工或系统主动暂停 |
| `recovering` | 进入恢复流程 |
| `compensating` | 正在执行补偿动作 |
| `completed` | 全部完成 |
| `partially_completed` | 主体完成，但有局部未闭环 |
| `failed` | 终态失败 |
| `cancelled` | 被取消 |

### 6.2 `workflow_node_run` 状态建议

| 状态 | 说明 |
|---|---|
| `pending` | 等待上游完成 |
| `ready` | 已满足执行条件 |
| `running` | 执行中 |
| `waiting_approval` | 本节点等待审批 |
| `waiting_input` | 本节点等待人工输入 |
| `retry_scheduled` | 已安排重试 |
| `succeeded` | 执行成功 |
| `failed_retryable` | 失败但可重试 |
| `failed_terminal` | 失败且不可自动重试 |
| `skipped` | 被策略或人工跳过 |
| `compensated` | 已做补偿 |
| `cancelled` | 被取消 |

### 6.3 为什么 `waiting_approval` 与 `paused` 不能混为一谈

因为：

- `waiting_approval` 是业务治理状态
- `paused` 是运行控制状态

两者的恢复入口、责任人、审计语义都不一样。

---

## 七、检查点模型

恢复能力的基础不是“报错后再试一次”，而是要有正式检查点。

### 7.1 建议的检查点类型

| 类型 | 说明 |
|---|---|
| `run_start_checkpoint` | 运行开始时的全局快照 |
| `node_input_checkpoint` | 节点执行前输入快照 |
| `node_output_checkpoint` | 节点执行后输出快照 |
| `approval_wait_checkpoint` | 进入审批前的审批包快照 |
| `external_write_preflight_checkpoint` | 对外写动作前的计划与令牌快照 |
| `external_write_receipt_checkpoint` | 对外写动作后的回执快照 |
| `manual_handover_checkpoint` | 人工接管前后的图状态快照 |

### 7.2 检查点至少要保存什么

建议至少保存：

- 运行版本快照
- 契约引用
- 关键变量
- Artifact 引用
- 命中策略
- 风险等级
- 上游节点状态摘要

### 7.3 检查点不应无限制保存全量大对象

原则上：

- 大对象保存 Artifact 引用
- 检查点保存摘要和哈希

否则存储和回放成本会失控。

---

## 八、`retry`、`resume`、`replay`、`compensate`、`rollback` 的正式定义

### 8.1 `retry`

定义：

- 对同一个节点实例，在相同语义前提下再次尝试执行

适用：

- 临时网络错误
- 短暂模型超时
- 幂等只读调用失败

### 8.2 `resume`

定义：

- 从已保存检查点恢复当前运行图继续执行

适用：

- 审批通过后继续
- 人工补充输入后继续
- 暂停恢复

### 8.3 `replay`

定义：

- 用同一运行输入或同一版本快照重新跑一条新的运行实例

适用：

- 调试
- 复盘
- 版本对比

### 8.4 `compensate`

定义：

- 对已经发生的副作用执行“逆向或补救动作”

适用：

- 草稿撤回
- 状态回写修正
- 补偿通知

### 8.5 `rollback`

定义：

- 把未来新运行切回上一个稳定版本

适用：

- 版本级问题
- 模板级回退
- 方案级回退

### 8.6 这五个动作绝不能互相替代

尤其要避免：

- 用 `retry` 替代 `resume`
- 用 `replay` 假装“恢复当前运行”
- 用 `rollback` 解决单次运行异常

---

## 九、失败分类模型

恢复策略应由失败类型驱动，而不是一律重试。

### 9.1 建议失败分类

| 失败类型 | 典型示例 | 默认动作 |
|---|---|---|
| `transient_infra_error` | 网络抖动、短时 5xx、队列抖动 | 自动重试 |
| `provider_runtime_error` | 模型超时、工具服务暂不可用 | 有限重试 |
| `policy_denied` | 运行时策略拒绝、权限不足 | 终止或等待人工处理 |
| `contract_validation_error` | 输入输出不符合契约 | 终止或要求修正输入 |
| `approval_rejected` | 审批驳回 | 等待人工调整或终止 |
| `budget_exhausted` | Token、配额、预算耗尽 | 暂停或终止 |
| `unknown_write_state` | 外部写动作状态不明 | 人工接管 |
| `non_compensable_side_effect` | 已发出的不可撤销动作 | 进入人工处置流程 |

### 9.2 为什么 `unknown_write_state` 要单列

这是最危险的一类。

因为系统并不知道：

- 动作到底发出去没有
- 对方系统是否成功执行
- 本地是否已经记录回执

这类情况绝不能盲重试。

## 十、不同节点类型的恢复策略

### 10.1 只读节点

例如：

- `data_read`
- `knowledge_lookup`
- `tool.readonly`

建议：

- 支持自动重试
- 支持从输入检查点恢复
- 要求幂等

### 10.2 AI 生成节点

例如：

- `llm`
- `planner`
- `rewrite`

建议：

- 支持有限次数自动重试
- 保留每次输出结果用于对比
- 结构化输出校验失败时可以触发一次“同输入再生”

### 10.3 审批节点

建议：

- 不自动重试审批结果
- 审批超时进入明确状态
- 驳回后可回到上一个可编辑检查点

### 10.4 外部写节点

建议：

- 必须声明幂等能力
- 必须声明补偿能力
- 没有幂等保证时不得自动重试
- 回执状态不明时直接进入人工接管

### 10.5 动态规划节点

建议：

- 保存规划产物和步数预算
- 允许从“已批准的计划检查点”继续执行
- 计划过期时应重新审批或重新规划

---

## 十一、幂等性与执行回执

### 11.1 平台必须正式要求幂等键

以下场景应尽量要求幂等键：

- `api` 触发
- `webhook` 触发
- 外部写动作
- 对内重要状态写回

### 11.2 建议的回执模型

外部动作执行后，应尽量返回标准化 `write.receipt`，至少包含：

- 动作类型
- 目标系统
- 幂等键
- 远端回执 ID
- 执行时间
- 最终状态

### 11.3 没有回执就不应被视为“可稳定恢复”

平台不能把“我发出去了”当作“我知道它成功了”。

如果没有回执，只能进入不确定状态处理。

---

## 十二、补偿模型

### 12.1 建议把补偿能力正式分类

| 分类 | 说明 |
|---|---|
| `compensable` | 可自动或半自动补偿 |
| `partially_compensable` | 只能补部分副作用 |
| `forward_only` | 无法回撤，只能前向处置 |

### 12.2 补偿不等于简单反向执行

很多时候补偿不是“反着调一次 API”。

更现实的场景是：

- 创建修正记录
- 标记异常状态
- 发送补偿通知
- 创建人工复核任务

### 12.3 高风险补偿也可能需要审批

例如：

- 撤回已发布内容
- 覆盖已写入正式业务数据
- 对外重新发送修正消息

这类补偿动作本身就是高风险动作，应再次经过策略和审批判断。

---

## 十三、人工接管模型

平台必须允许运行从“纯自动”切换到“人工接管”。

### 13.1 建议的人工动作类型

| 动作 | 说明 |
|---|---|
| `pause_run` | 暂停运行 |
| `resume_from_checkpoint` | 从检查点恢复 |
| `retry_node` | 人工触发节点重试 |
| `skip_node_with_reason` | 带原因跳过节点 |
| `inject_corrected_artifact` | 人工上传修正后的 Artifact |
| `force_mark_receipt` | 手工确认远端动作结果 |
| `trigger_compensation` | 发起补偿流程 |
| `terminate_run` | 人工终止运行 |

### 13.2 人工动作必须留下结构化痕迹

每次人工接管都应记录：

- 操作人
- 操作时间
- 操作原因
- 操作前后状态
- 关联证据

否则后面根本无法审计。

### 13.3 人工接管不是越权入口

人工接管仍应服从：

- RBAC
- 企业隔离
- 运行时策略
- 审批边界

不能因为“管理员能救火”，就让人工接管变成万能后门。

---

## 十四、恢复路径建议

建议为平台定义 4 条正式恢复路径。

### 14.1 自动恢复路径

适用：

- 瞬时故障
- 只读节点
- 已声明幂等的低风险动作

流程：

```text
节点失败
-> 判断为 retryable
-> 读取输入检查点
-> 有限次数自动重试
-> 成功则继续
```

### 14.2 审批恢复路径

适用：

- 进入 `waiting_approval`
- 审批通过后继续
- 审批驳回后返回上游调整点

### 14.3 人工修正恢复路径

适用：

- 契约校验失败
- 输出质量不达标
- 缺少必要附件或证据

流程：

```text
节点失败
-> 创建 manual_handover_task
-> 人工补充或替换 Artifact
-> 从最近可恢复检查点 resume
```

### 14.4 补偿终止路径

适用：

- 外部写动作失败且需要止损
- 业务上已不允许继续

流程：

```text
异常识别
-> 判断是否可补偿
-> 执行补偿或创建补偿任务
-> 将运行标记为 failed / partially_completed
```

---

## 十五、观察、回放与诊断要求

运行时执行图如果不能被观察和回放，恢复能力就会变成黑盒。

### 15.1 建议至少能展示这些视图

1. 运行图拓扑
2. 当前卡点
3. 关键路径耗时
4. 节点重试历史
5. 检查点列表
6. Artifact 血缘链
7. 审批等待链路
8. 补偿链路

### 15.2 回放的两种含义

建议明确区分：

- `visual_replay`：仅重现当时发生了什么
- `execution_replay`：重新执行一条新的运行实例

两者不能混淆。

### 15.3 故障诊断应能回答什么

至少要能回答：

- 卡在哪个节点
- 失败分类是什么
- 是否已经执行过外部写动作
- 是否存在补偿建议
- 是否允许直接重试

---

## 十六、与前文规范的关系

### 16.1 与触发和发布规范的关系

运行实例必须绑定：

- 已发布版本
- 触发器快照

恢复和回放不能绕开这两层。

### 16.2 与数据契约规范的关系

每个检查点和节点输出都应引用：

- `contract_ref`
- Artifact 描述
- 证据引用

否则恢复后无法确认数据合法性。

### 16.3 与运行时策略引擎的关系

恢复动作本身也应再次进入策略裁决。

例如：

- 是否允许跳过节点
- 是否允许继续执行高风险写动作
- 是否允许触发补偿

### 16.4 与审批规范的关系

审批不是外围系统，而是运行图中的正式停顿点和治理分叉点。

---

## 十七、第一阶段实施建议

### Phase 1：先把“运行图 + 检查点 + 失败分类”做出来

优先建设：

- `workflow_run`
- `workflow_node_run`
- `runtime_execution_edge`
- `execution_checkpoint`
- 标准失败分类

### Phase 2：再补“恢复路径 + 人工接管”

补齐：

- `recovery_task`
- `manual_handover_task`
- 人工动作日志
- 节点级恢复 UI

### Phase 3：最后补“补偿模型 + 动态扩图”

补齐：

- `compensation_task`
- `compensable` 能力声明
- `agentic` 动态扩图运行治理
- 图级回放与诊断视图

---

## 十八、关键结论

1. 工作流运行必须被视为正式的运行时执行图，而不是简单步骤日志，因为它天然包含分支、并行、审批、重试、补偿和动态扩图。
2. 每个节点执行都应绑定输入快照、契约快照、策略快照和 Artifact 引用，否则恢复与审计都不可靠。
3. `retry`、`resume`、`replay`、`compensate`、`rollback` 必须严格区分，尤其不能对高风险外部写动作做盲重试。
4. 平台必须要求外部写动作声明幂等性、回执能力与补偿能力，并在状态不明时优先进入人工接管。
5. 恢复能力必须同时支持自动恢复、审批恢复、人工修正恢复和补偿终止四条正式路径。
6. 第一阶段先把运行图、检查点、失败分类和人工接管链路打稳，再逐步扩展到补偿模型和 `agentic` 动态扩图治理。

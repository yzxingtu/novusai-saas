# AI 编排与工作流平台评估数据集与基准治理规范（2026-03-23）

## 一、文档目标

本文档用于定义平台在做版本评估、回归验证、行业方案比较、企业效果验收时，应该如何管理评估数据集、基准集、标注规则、评分规则和评估基线。

前面的文档已经回答了：

- 平台为什么必须有可观测性和评估
- 评估应该绑定版本
- 运行结果、Artifact、审批记录如何被结构化沉淀

但还缺一个真正决定“评估能不能长期做下去”的底层问题：

1. 评估到底用什么数据来评。
2. 谁来维护这些样本。
3. 哪些样本能作为回归基线，哪些只能做探索测试。
4. 行业方案、企业定制版、企业本地副本如何共享又隔离评估数据。
5. 怎样避免平台每次升级都靠人工临场判断“感觉这次更好了”。

所以，这份文档要解决的是：

> 平台如何把“评估”从一次性演示，变成一套可版本化、可复用、可回归、可治理的基准体系。

---

## 二、核心结论

### 2.1 没有正式评估数据集，就没有真正可持续的评估体系

很多系统以为自己有评估，实际只是：

- 选几个案例临时跑一下
- 找几个人主观看看
- 用线上反馈做事后判断

这不叫正式评估体系。

正式评估体系至少要有：

- 数据集
- 标注规范
- 基准集
- 评分规则
- 版本记录

### 2.2 必须区分“运营反馈数据”和“评估基准数据”

线上运营反馈很重要，但不能直接等于评估基准。

建议正式区分：

- `feedback_data`
- `evaluation_dataset`
- `benchmark_suite`

原因：

- 运营反馈带有噪音和场景偏差
- 基准集需要稳定、可重复、可版本化

### 2.3 平台必须同时维护三层评估样本

建议正式拆成：

1. 平台通用基准集
2. 行业方案基准集
3. 企业局部评估集

这样才能同时回答三类问题：

- 平台总体是否退化
- 某行业方案是否进步
- 某企业自己的版本是否满足业务

### 2.4 基准集必须尽量盲化，不能完全暴露给日常提示词与模板开发

如果所有评估样本都完全暴露，后面很容易变成：

- 模板针对样本调优
- 评估结果看起来很漂亮
- 真实线上却不稳

因此建议至少保留：

- `public_eval_set`
- `private_holdout_set`

### 2.5 评估治理不是只治理“结果分数”，还要治理“样本本身”

真正会让评估失效的，很多时候不是评分器，而是样本出了问题：

- 过期
- 偏科
- 重复
- 泄漏
- 标注不一致

所以平台必须把“样本治理”上升为正式能力。

---

## 三、为什么必须单独写这份文档

前面的 `11-observability-and-evaluation-spec` 已经把评估方向定下来了，但它更偏：

- 为什么要评估
- 评估哪些层
- 评估有哪些方法

还没有回答：

- 评估用的数据长什么样
- 样本怎么组织
- 谁能修改基准
- 什么叫合格的版本回归

如果这层不单独规范，后面会出现：

1. 每个团队自己保存一批测试样本。
2. 标准行业方案和企业定制版没有共同的评估语言。
3. 一次升级后，谁都无法证明“比上个版本更好”。
4. 线上反馈很多，但不能沉淀成正式基准。

所以，这份文档是在回答：

> 平台如何把“评估样本”变成正式产品资产，而不是临时测试材料。

---

## 四、正式对象模型

建议把评估治理相关对象正式抽出来。

### 4.1 核心对象建议

| 对象 | 作用 |
|---|---|
| `evaluation_dataset` | 一组评估样本集合 |
| `evaluation_dataset_version` | 数据集版本 |
| `evaluation_sample` | 单条评估样本 |
| `sample_annotation` | 样本标注结果与解释 |
| `benchmark_suite` | 一组正式基准套件，面向某场景或某方案 |
| `benchmark_run` | 一次基准评测执行 |
| `benchmark_result` | 某次评测的汇总结果 |
| `benchmark_dimension_score` | 某维度评分 |
| `holdout_partition` | 隐藏评估集分区 |
| `evaluation_policy` | 某类评估任务的样本选用、评分和通过规则 |

### 4.2 评估资产不应只存在文件系统

可以有文件形式的导入导出，但平台内部应以正式对象管理：

- 版本
- 归属
- 作用域
- 使用记录
- 评分历史

---

## 五、样本层次模型

建议平台正式拆成四层样本资产。

### 5.1 `feedback_data`

定义：

- 企业日常运行中的人工采用、退回、修改、审批意见、业务结果回写等反馈数据

特点：

- 量大
- 噪音高
- 真实
- 适合挖掘，不适合直接做稳定基准

### 5.2 `curated_eval_set`

定义：

- 从反馈和历史运行中筛选、清洗、标注后的评估数据集

特点：

- 质量更高
- 可重复使用
- 适合作为版本比较输入

### 5.3 `benchmark_suite`

定义：

- 一组正式评测套件，包含样本集合、评分维度、阈值、分层报告规则

特点：

- 面向回归
- 面向发行门禁
- 面向行业方案治理

### 5.4 `holdout_set`

定义：

- 平台保留、不完全公开的盲测集合

特点：

- 用于防止过拟合和样本泄漏
- 用于关键版本验收和发行前回归

---

## 六、三层评估集治理模型

建议正式把评估资产按治理层拆成三层。

### 6.1 平台通用评估集 `platform_eval`

目标：

- 评估平台内核能力是否退化

典型覆盖：

- 触发标准化
- 数据契约稳定性
- 审批包完整性
- 恢复流程稳定性
- 通用分析类和内容类节点

### 6.2 行业方案评估集 `solution_eval`

目标：

- 评估某个行业方案包是否稳定、是否升级有效

典型覆盖：

- 行业输出格式
- 行业场景核心任务
- 行业审批规则命中
- 行业样本质量

### 6.3 企业局部评估集 `tenant_eval`

目标：

- 验证某企业自己的本地配置、企业副本或定制交付是否符合业务

典型覆盖：

- 企业品牌规则
- 企业审批习惯
- 企业素材适配
- 企业专属约束

### 6.4 三层关系原则

建议遵守：

- 平台层负责底层回归
- 方案层负责行业效果
- 企业层负责本地适配

不能让企业局部样本去替代平台基准，也不能让平台通用样本代替企业验收。

---

## 七、样本结构规范

### 7.1 单条评估样本建议字段

| 字段 | 说明 |
|---|---|
| `sample_code` | 样本编码 |
| `sample_type` | `analysis` / `generation` / `approval` / `recovery` / `routing` / `prediction` |
| `source_type` | `synthetic` / `historical_run` / `human_curated` / `tenant_feedback` |
| `input_contract_ref` | 输入契约引用 |
| `input_payload` | 标准化输入 |
| `context_refs` | 关联知识、证据、素材、页面上下文引用 |
| `expected_output_type` | 期望输出类型 |
| `expected_constraints` | 结构和规则约束 |
| `expected_labels` | 期望标签或判断 |
| `golden_artifact_ref` | 标准答案或标准参考对象 |
| `evaluation_dimensions` | 该样本适用的评分维度 |
| `difficulty_level` | 难度 |
| `risk_level` | 风险等级 |
| `freshness_at` | 数据新鲜度时间 |
| `sensitivity_level` | 敏感等级 |

### 7.2 为什么不建议所有样本都要求唯一“标准答案”

因为 AI 场景里很多任务不存在单一标准答案，例如：

- 文案草稿
- 选题建议
- 复盘建议

更合理的方式是：

- 有些样本用 `golden_output`
- 有些样本用 `expected_constraints`
- 有些样本用多维打分

---

## 八、标注与金标准治理

### 8.1 标注不是随手备注，必须可版本化

建议正式维护：

- `annotation_guideline`
- `annotation_version`
- `sample_annotation`

### 8.2 标注类型建议

| 类型 | 说明 |
|---|---|
| `binary_label` | 是/否 |
| `multi_class_label` | 多分类标签 |
| `score_label` | 数值评分 |
| `rank_label` | 排序偏好 |
| `freeform_rationale` | 人工理由说明 |
| `golden_reference` | 标准参考答案或参考产物 |

### 8.3 多人标注一致性要被治理

如果某类样本长期出现：

- 标注人之间意见差异过大
- 理由完全不一致

说明不是模型先有问题，而是标注规范不够稳定。

建议至少跟踪：

- 一致率
- 争议率
- 返工率

### 8.4 高争议样本应进入“争议池”

建议建立：

- `annotation_dispute_pool`

用于：

- 二次复核
- 规则澄清
- 是否移出正式基准集

---

## 九、基准套件 `benchmark_suite` 规范

### 9.1 基准套件的正式定位

建议定义为：

> 面向某一评估目标所组织的一组正式样本、评分维度、阈值、通过条件和报告模板。

### 9.2 建议的套件类型

| 类型 | 目标 |
|---|---|
| `platform_regression_suite` | 平台核心回归 |
| `solution_release_suite` | 行业方案发行评估 |
| `tenant_acceptance_suite` | 企业交付验收 |
| `prompt_experiment_suite` | 提示词实验比较 |
| `safety_suite` | 风险与合规评估 |
| `recovery_suite` | 失败恢复和补偿链路评估 |

### 9.3 套件内容建议

至少包含：

- 样本范围
- 样本分层
- 评分维度
- 阈值规则
- 报告模板
- 版本适用范围

---

## 十、盲测与防泄漏机制

### 10.1 为什么必须有盲测集

如果平台所有评估样本都被模板开发、提示词调优、企业自定义过程充分看到，后面非常容易：

- 对样本过拟合
- 对真实业务欠拟合

### 10.2 建议至少保留两类分区

| 分区 | 说明 |
|---|---|
| `public_eval_partition` | 可供日常开发和方案调优使用 |
| `private_holdout_partition` | 仅供关键回归和发行门禁使用 |

### 10.3 什么场景必须用 `private_holdout_partition`

例如：

- 行业方案大版本发行前
- 平台核心运行时升级前
- 高风险能力或外部写能力放量前
- 定制交付正式验收前

### 10.4 盲测集也不是永远不变

盲测集需要：

- 定期轮换
- 定期补充新样本
- 清理泄漏样本

否则长期看也会逐渐失效。

---

## 十一、评估维度与样本绑定规则

不是每条样本都适合所有维度。

### 11.1 建议的绑定方式

样本应明确声明适用维度，例如：

- `correctness`
- `groundedness`
- `policy_compliance`
- `usability`
- `efficiency`
- `business_impact`

### 11.2 典型示例

| 样本类型 | 重点维度 |
|---|---|
| `analysis` | `correctness` / `groundedness` / `usability` |
| `generation` | `usability` / `policy_compliance` / `style_consistency` |
| `approval` | `policy_compliance` / `evidence_completeness` |
| `recovery` | `correctness` / `safety` / `operability` |
| `prediction` | `correctness` / `confidence_calibration` / `business_impact` |

### 11.3 不建议统一把所有维度平均求总分

更合理的做法是：

- 先看关键维度是否过线
- 再看总分或加权分

否则会出现一个关键风险维度失败，但总分还勉强过线的情况。

---

## 十二、平台、方案、企业三层门禁规则

### 12.1 平台级门禁

适用：

- 平台内核升级
- 核心节点行为变化
- 运行时策略变化

建议要求：

- `platform_regression_suite` 必须通过
- `safety_suite` 不得退化

### 12.2 方案级门禁

适用：

- 行业方案新版本发行
- Prompt/模板结构重构

建议要求：

- `solution_release_suite` 必须通过
- 方案关键指标不低于稳定版

### 12.3 企业级门禁

适用：

- 企业定制交付验收
- 企业副本升级
- 企业关键品牌规则更新

建议要求：

- `tenant_acceptance_suite` 通过
- 企业指定高优先级样本必须通过

---

## 十三、数据来源与回流规则

评估样本不应凭空创造，必须有正式来源治理。

### 13.1 建议的数据来源

| 来源 | 用途 |
|---|---|
| 历史运行结果 | 生成候选样本 |
| 人工反馈 | 生成问题样本与纠错样本 |
| 审批记录 | 生成风险与合规样本 |
| 业务结果回写 | 生成效果样本 |
| 专家设计样本 | 补齐关键空白场景 |
| 合成样本 | 补齐边界和异常场景 |

### 13.2 从反馈到正式基准的建议流程

```text
线上反馈
-> 候选样本池
-> 清洗与去重
-> 标注
-> 小范围验证
-> 进入 curated_eval_set
-> 进入 benchmark_suite
```

### 13.3 不建议线上全量反馈直接进基准

原因包括：

- 重复样本太多
- 噪音太大
- 标签不稳定
- 容易被个别企业行为带偏

---

## 十四、数据集版本化与生命周期

### 14.1 数据集必须版本化

建议：

- `evaluation_dataset` 作为逻辑对象
- `evaluation_dataset_version` 作为具体样本快照

### 14.2 生命周期建议

| 状态 | 说明 |
|---|---|
| `draft` | 草稿整理中 |
| `reviewing` | 标注/治理审核中 |
| `active` | 可用于正式评估 |
| `deprecated` | 不再建议用于新评估 |
| `retired` | 退役，仅保留历史记录 |

### 14.3 退役数据集不应直接删除

原因：

- 历史评估报告需要可追溯
- 版本对比需要知道当时用的是什么数据集

---

## 十五、结果报告与可解释性要求

### 15.1 基准报告不应只给总分

建议至少包含：

- 总体通过情况
- 分维度得分
- 分样本层级结果
- 关键失败样本
- 与上个版本对比
- 风险说明

### 15.2 关键失败样本要能下钻

至少应能查看：

- 输入
- 上下文
- 输出
- 评分理由
- 对应版本

### 15.3 评估报告要支持不同视角

建议至少支持：

- 平台治理视角
- 行业方案视角
- 企业验收视角

---

## 十六、权限与隔离规则

### 16.1 平台层

管理端可以：

- 维护平台通用基准
- 维护行业方案基准
- 审核企业提交的候选样本是否可晋升为行业基准

### 16.2 企业层

企业可以：

- 查看本企业评估结果
- 维护本企业评估集
- 提交候选样本

企业不可以：

- 查看其他企业私有评估样本
- 修改平台通用盲测集
- 直接编辑行业正式基准

### 16.3 方案插件层

方案插件可以附带：

- 行业评估模板
- 行业推荐样本结构
- 行业评分维度

但最终是否进入正式行业基准，仍应经过平台治理。

---

## 十七、与现有文档的关系

### 17.1 与 `11-observability-and-evaluation-spec`

`11` 负责说明为什么评估重要、评估哪些层。

`19` 负责说明评估样本、基准集、标注和门禁到底怎么治理。

### 17.2 与 `15-workflow-data-contract-and-schema-spec`

评估样本的输入、输出、Artifact、审批包应尽量复用统一契约体系。

### 17.3 与 `18-solution-delivery-spec-bundle-and-acceptance-kit`

企业验收包中的验收样本和通过标准，应优先来自正式 `benchmark_suite` 或 `tenant_acceptance_suite`。

---

## 十八、第一阶段实施建议

### Phase 1：先把“数据集对象 + 基准套件 + 基本门禁”做出来

优先建设：

- `evaluation_dataset`
- `evaluation_dataset_version`
- `evaluation_sample`
- `benchmark_suite`
- `benchmark_run`

### Phase 2：再补“标注治理 + 盲测分区”

补齐：

- `sample_annotation`
- 标注规范
- 争议池
- `public_eval_partition` / `private_holdout_partition`

### Phase 3：最后补“平台/行业/企业三层联动”

补齐：

- 平台回归门禁
- 行业发行门禁
- 企业验收基准
- 候选样本回流治理

---

## 十九、关键结论

1. 平台必须把评估数据集和基准套件当作正式产品资产治理，而不是临时测试材料。
2. 必须明确区分运营反馈数据、清洗评估集、正式基准套件和盲测集，不能把它们混为一谈。
3. 平台应同时维护平台通用、行业方案、企业局部三层评估样本体系，以支持回归、发行和验收三类目标。
4. 样本治理和标注治理与评分治理同样重要，否则评估体系会被过期、泄漏、偏科和不一致性拖垮。
5. 关键版本门禁必须尽量依赖正式 `benchmark_suite` 和 `holdout_set`，不能只靠主观演示或线上感觉。
6. 第一阶段先把数据集、样本、基准套件和基本门禁做出来，再逐步补齐盲测分区、标注治理和三层联动机制。

# AI 编排与工作流平台触发与发布规范（2026-03-23）

## 一、文档目标

本文档用于定义平台级的两套关键机制：

1. 工作流在什么条件下被触发运行。
2. 哪个版本的工作流可以被发布、启用、回滚和对外可见。

需要解决的核心问题是：

- 触发和发布经常被混为一谈
- 草稿版本不应被触发
- 平台模板、企业副本、定制交付在发布流程上不能一刀切
- 定时、Webhook、API、事件触发要有统一安全语义

---

## 二、核心结论

### 2.1 “触发”与“发布”是两件不同的事

必须明确区分：

- `trigger`
- `release`

其中：

- `trigger` 决定“什么时候创建一次新的 `WorkflowRun`”
- `release` 决定“哪个版本允许被触发和运行”

### 2.2 未发布版本不能进入自动触发链路

建议默认规则：

- 草稿版本只能手动调试
- 正式触发器只能绑定到已发布版本

否则会导致企业在不知情的情况下跑草稿逻辑。

### 2.3 运行实例必须绑定版本快照

每次 `WorkflowRun` 创建时，都必须固定：

- 来源模板版本
- 来源企业副本版本
- 当时生效的审批策略快照
- 当时生效的触发器快照

不能让发布后的新版本影响已经启动的运行实例。

### 2.4 触发入口可以开放，但必须是平台托管入口

企业端可以拥有：

- 手动触发
- 定时触发
- API 触发
- Webhook 触发
- 事件触发

但这些入口都必须由平台托管：

- 企业只能配置，不可写自定义后端代码
- 企业只能在平台提供的协议和字段映射内工作

### 2.5 发布权限继续遵守所有权原则

坚持前文已确认原则：

> 谁拥有工作流，谁管理它的日常发布。

因此：

- 平台模板由管理端发布
- 企业简单工作流由企业端发布
- 企业副本由企业端管理
- 定制交付按交付模式决定是否企业可接管

---

## 三、术语定义

### 3.1 `Trigger`

指能够创建一个新的 `WorkflowRun` 的入口定义。

### 3.2 `Release`

指把某个工作流版本标记为“可启用、可触发、可运行”的过程。

### 3.3 `Published Version`

指当前允许对外使用的稳定版本。

### 3.4 `Active Version`

指在某个作用域内当前真正生效的版本。

说明：

- 一个版本可以已发布，但未必在所有企业都激活。
- `published` 和 `active` 可以分开建模。

### 3.5 `Rollout Scope`

指一个版本发布后，面向哪些对象开放，例如：

- 全平台
- 指定企业
- 当前企业私有

---

## 四、触发类型模型

### 4.1 推荐支持的五类触发器

| 触发类型 | 说明 | 第一阶段建议 |
|---|---|---|
| `manual` | 人工点击执行 | 必做 |
| `schedule` | 按时间调度执行 | 必做 |
| `api` | 受认证的 API 调用触发 | 必做 |
| `webhook` | 外部系统回调触发 | 建议做 |
| `event` | 平台内部事件总线触发 | 建议做 |

### 4.2 第一阶段不建议扩展的触发器

例如以下触发器可以后置：

- 文件到达触发
- 邮件触发
- IM 消息触发
- 浏览器行为触发
- 跨企业联动触发

这些不是平台第一阶段闭环所必需。

---

## 五、各触发器的边界

### 5.1 `manual`

定义：

由用户在页面上主动点击“运行”发起。

特点：

- 最容易理解
- 最适合草稿调试和人工确认场景
- 默认风险最低

适用：

- 平台模板测试
- 企业简单工作流手动运行
- 草稿生成和复盘

### 5.2 `schedule`

定义：

按固定时间计划自动触发。

建议：

- 复用平台现有 `periodic_tasks` 和 `scheduled` 队列设计思路
- 工作流触发层可单独建工作流触发表，但底层调度模型应尽量一致

适用：

- 每日趋势扫描
- 周报生成
- 定期复盘

### 5.3 `api`

定义：

由外部服务端通过受认证 API 主动发起。

适用：

- 企业系统主动推送任务
- 内部业务系统触发分析流
- 批量入参型流程

要求：

- 必须鉴权
- 必须限制速率
- 必须记录调用方身份和幂等键

### 5.4 `webhook`

定义：

由外部系统向平台托管的标准回调入口发送事件，从而触发工作流。

边界：

- 企业端只配置 URL、密钥、字段映射
- 企业端不写 handler 代码
- 平台统一负责签名校验、幂等、防重放和流量限制

### 5.5 `event`

定义：

由平台内部标准事件触发工作流，例如：

- 新数据入库
- 审批完成
- 某草稿已归档
- 某定时分析完成

边界：

- 事件必须来自平台白名单事件总线
- 企业端只能订阅被授权的事件

## 六、触发器与构建面的关系

### 6.1 构建面触发器矩阵

| 构建面 | `manual` | `schedule` | `api` | `webhook` | `event` |
|---|---|---|---|---|---|
| `platform_workflow_studio` | 允许 | 允许 | 允许 | 允许 | 允许 |
| `tenant_template_editor` | 允许 | 允许 | 受限允许 | 受限允许 | 白名单允许 |
| `tenant_simple_builder` | 允许 | 允许 | 受限允许 | 受限允许 | 白名单允许 |

### 6.2 企业端的受限含义

这里的“受限允许”具体指：

- 只能使用平台托管标准入口
- 必须配置字段映射
- 必须通过权限、套餐和授权校验
- 不允许自定义代码

## 七、触发器数据模型建议

建议新增正式触发器对象，例如：`workflow_triggers`

建议字段：

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `owner_type` | `platform` / `tenant` |
| `owner_tenant_id` | 企业归属 |
| `target_type` | `workflow_template` / `tenant_workflow` |
| `target_id` | 目标工作流 |
| `target_version_id` | 绑定版本 |
| `trigger_type` | `manual` / `schedule` / `api` / `webhook` / `event` |
| `status` | `draft` / `active` / `disabled` |
| `config_json` | 触发配置 |
| `auth_config_json` | 认证配置 |
| `mapping_json` | 输入字段映射 |
| `risk_guard_json` | 触发前风险守卫 |
| `last_triggered_at` | 最近触发时间 |
| `next_trigger_at` | 下次触发时间 |

### 7.1 `manual` 也建议做显式触发定义

虽然手动触发最简单，但建议仍然统一纳入触发模型。

好处：

- 权限模型一致
- 审计链一致
- 可统计不同触发来源占比

---

## 八、触发前校验链路

所有触发器在创建 `WorkflowRun` 前，建议统一做以下校验：

```text
检查目标版本是否已发布
-> 检查目标版本是否在当前作用域激活
-> 检查企业套餐和授权
-> 检查插件 License
-> 检查触发器本身是否启用
-> 检查触发器认证与限流
-> 检查输入是否通过 Schema
-> 创建 WorkflowRun
```

### 8.1 未通过校验时不要降级跑草稿版本

如果正式版本不可用：

- 不要自动回退到草稿
- 不要自动切换到别的版本

而应明确失败并返回原因。

---

## 九、发布对象模型

建议把“发布”抽象为正式对象，而不是仅仅改一个状态字段。

### 9.1 推荐新增 `workflow_releases`

建议字段：

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `release_scope` | `platform_catalog` / `selected_tenants` / `tenant_private` |
| `target_type` | `workflow_template` / `tenant_workflow` |
| `target_id` | 工作流对象 |
| `version_id` | 版本快照 |
| `channel` | `stable` / `beta` / `internal` |
| `status` | `draft` / `reviewing` / `approved` / `published` / `disabled` / `deprecated` |
| `published_by` | 发布人 |
| `published_at` | 发布时间 |
| `rollout_json` | 发布范围和激活规则 |
| `rollback_of_release_id` | 回滚来源 |

### 9.2 版本快照必须不可变

无论平台模板还是企业副本，都建议：

- 发布的是版本快照，不是当前可编辑草稿
- 发布后继续编辑应形成新版本

## 十、平台模板、企业副本、简单工作流的发布差异

### 10.1 平台模板发布

适用对象：

- 平台原生模板
- 行业方案模板
- 托管型模板

建议流程：

```text
draft
-> review
-> approved
-> published
-> deprecated / disabled
```

说明：

- 平台模板建议必须经过正式审核后才能发布。

### 10.2 企业副本发布

适用对象：

- 企业复制平台模板后的本地版本

建议流程：

```text
draft
-> published
-> disabled
```

说明：

- 企业自己拥有的副本，发布流程可以比平台模板更轻。
- 但如果命中高风险能力，仍应要求企业内部审核。

### 10.3 企业简单工作流发布

适用对象：

- 企业从零创建的简单流程

建议流程：

```text
draft
-> validation_passed
-> published
-> disabled
```

说明：

- 企业简单工作流不一定需要复杂的“平台审核”，但必须通过静态校验和权限校验。

---

## 十一、发布权限与所有权矩阵

| 动作 | 管理端 | 企业端 |
|---|---|---|
| 发布平台模板 | 允许 | 不允许 |
| 灰度发布到指定企业 | 允许 | 不允许 |
| 下线平台模板 | 允许 | 不允许 |
| 发布企业副本 | 不需要 | 允许 |
| 下线企业副本 | 不需要 | 允许 |
| 发布企业简单工作流 | 不需要 | 允许 |
| 修改平台模板的发布范围 | 允许 | 不允许 |
| 修改企业私有工作流的触发器 | 不需要 | 允许 |

---

## 十二、发布范围与灰度模型

### 12.1 建议支持三类发布范围

| 范围 | 说明 |
|---|---|
| `platform_catalog` | 面向所有有资格的企业可见 |
| `selected_tenants` | 只面向指定企业可见 |
| `tenant_private` | 仅当前企业私有 |

### 12.2 为什么需要 `selected_tenants`

这个范围很重要，因为它对应：

- 定制交付
- 内测交付
- 小范围灰度
- 特定企业先试用

### 12.3 发布范围不等于最终可运行范围

即使版本已发布到某企业范围内，仍要再经过：

- `TenantEntitlement`
- 插件 License
- 套餐能力
- 工作流触发器启用状态

---

## 十三、触发与审批的联动

### 13.1 自动触发不等于自动完成

即使是 `schedule`、`api`、`webhook`、`event` 自动触发的工作流，只要命中审批闸门，仍应暂停。

正确语义是：

- 触发负责“创建运行”
- 审批负责“是否允许继续”

### 13.2 `L4` 的自动触发更要谨慎

对于 `L4` 工作流，建议：

- 自动触发允许存在
- 但必须有计划预览和关键节点审批

必要时可以要求：

- 计划审批通过后，一段时间内自动触发复用该计划
- 计划过期后必须重新审批

---

## 十四、Webhook 与 API 的安全要求

### 14.1 `api` 触发最低要求

必须具备：

- 认证凭据
- 速率限制
- 幂等键
- 调用审计
- 输入 Schema 校验

### 14.2 `webhook` 触发最低要求

必须具备：

- 签名校验
- 时间戳校验
- 防重放
- 幂等处理
- Payload Schema 校验
- 失败重试策略

### 14.3 企业端可配置，但不能自定义协议栈

企业端最多配置：

- Secret
- Header 映射
- 字段映射
- 幂等键字段

不应允许：

- 自定义 Python/JS 预处理
- 自定义反序列化逻辑
- 自定义服务端中间件

---

## 十五、定时触发与配额控制

定时触发建议至少受以下限制：

- 最小调度粒度
- 单企业触发器数量上限
- 单工作流并发上限
- 单日触发次数上限

### 15.1 为什么调度也要做套餐化

如果调度完全不设限，会直接引发：

- 成本失控
- 队列拥塞
- 企业误用
- 高自治任务泛滥

因此建议把以下能力纳入套餐：

- 定时触发数量
- Webhook 触发数量
- API 触发 QPS
- 最大并发运行数

---

## 十六、回滚与停用

### 16.1 发布必须支持回滚

建议：

- 每次发布生成正式 `release` 记录
- 每次回滚指向来源 `release`

### 16.2 回滚原则

- 只影响未来新触发的运行
- 不影响已经在运行中的实例
- 已运行实例继续绑定原版本快照

### 16.3 停用的语义

建议区分：

- `disabled`
- `deprecated`

其中：

- `disabled`：立即不可用
- `deprecated`：不建议新用，但已存在触发器可逐步迁移

---

## 十七、审计与监控要求

触发与发布必须天然可审计。

建议每次触发至少记录：

- `trigger_type`
- `trigger_id`
- `triggered_by_type`
- `triggered_by_id`
- `idempotency_key`
- `input_payload_hash`
- `resolved_version_id`

建议每次发布至少记录：

- `release_scope`
- `channel`
- `published_by`
- `published_at`
- `rollout_targets`
- `change_summary`

### 17.1 企业端关心什么

企业端主要关心：

- 哪个版本在跑
- 哪个触发器最近触发了
- 为什么没触发
- 为什么被暂停

### 17.2 管理端关心什么

管理端主要关心：

- 哪些模板发布后故障率高
- 哪些触发器滥用严重
- 哪些企业高频触发高成本流程
- 哪些版本需要紧急下线

---

## 十八、第一阶段实施建议

### Phase 1：先把“发布版本 + 手动/定时触发”做稳

优先建设：

- 工作流版本快照
- 发布记录
- 手动触发
- 定时触发
- 运行实例绑定版本

### Phase 2：再补 `api` / `webhook`

补齐：

- 标准认证
- 签名与幂等
- Payload Schema
- 企业端可配置映射

### Phase 3：最后补事件触发与灰度发布

补齐：

- 内部事件总线绑定
- 选定企业灰度
- 回滚与迁移辅助

---

## 十九、关键结论

1. 触发和发布必须严格分开建模，前者决定运行何时开始，后者决定哪个版本允许被运行。
2. 草稿版本不应进入正式自动触发链路，正式触发器只能绑定已发布版本。
3. 每次运行实例都必须绑定不可变版本快照，不能被后续发布覆盖。
4. 企业端可以拥有 `manual`、`schedule`、`api`、`webhook`、`event` 等触发能力，但这些都必须是平台托管入口，而不是企业自定义代码。
5. 平台模板、企业副本、企业简单工作流在发布流程上应区分开来，但都必须遵守版本化和审计化原则。
6. 第一阶段先把版本发布、手动触发、定时触发闭环做稳，再扩展到 API、Webhook 和事件触发。

# AI 编排与工作流平台企业知识与上下文注入规范（2026-03-23）

## 一、文档目标

本文档用于定义企业在平台中提供的“业务知识”应该如何被组织、授权、注入和使用。

这份文档要回答的核心问题是：

1. 企业的价值到底体现在哪些知识输入上。
2. 这些知识通过什么通道进入 Agent 和工作流。
3. 哪些知识适合做知识库，哪些适合做配置，哪些适合做运行时上下文。
4. 知识注入如何保证隔离、安全、可追踪、可控预算。

本文档是平台级规范，不绑定单一行业，但会和现有 KB、RAG、`page_context`、Agent 绑定模型保持一致。

---

## 二、核心结论

### 2.1 企业的核心价值不是开发工具，而是提供业务知识

这一点需要正式写进平台内核规范。

企业在平台中的核心贡献主要是：

- 业务规则
- 品牌规则
- 产品资料
- 组织流程
- 历史经验
- 业务数据
- 当前任务上下文

而不是：

- 新建系统级工具
- 写执行器
- 写连接器
- 扩展平台内核

### 2.2 知识注入不是只有“知识库”一种方式

企业知识不应全部塞进知识库。

建议正式区分四条注入通道：

1. `config_injection`
2. `knowledge_base_injection`
3. `runtime_context_injection`
4. `artifact_feedback_injection`

### 2.3 不同类型知识必须放进不同容器

例如：

- 品牌定位适合做结构化配置
- SOP 文档适合做知识库
- 当前页面表单状态适合做运行时上下文
- 历史驳回原因适合做评估反馈

如果所有东西都塞进 Prompt，不仅成本高，还会失控。

### 2.4 平台必须控制注入预算，不能无上限塞上下文

当前项目已经有 `page_context` 字节预算，这个方向是对的。

后续所有注入通道都应有预算概念：

- Prompt 预算
- RAG 预算
- 页面上下文预算
- 运行时变量预算

### 2.5 企业可以注入业务知识，但不能绕过平台治理

例如：

- 企业可以上传文档
- 企业可以绑定知识库
- 企业可以补充品牌规则

但企业不能：

- 通过知识注入关闭平台审批
- 通过 Prompt 注入覆盖安全底线
- 通过页面上下文泄露超预算数据

## 三、为什么现在必须单独写这份文档

前面的文档已经多次提到：

- 企业价值在于注入业务知识
- 企业知识库和素材库很重要
- 工作流和 Agent 会吃上下文

但还没有系统回答：

- 这些知识从哪里来
- 用什么形式存
- 谁能用
- 在运行时怎么拼接
- 谁优先，谁覆盖谁

如果这层不单独规范，后面实现会出现两类典型问题：

1. 所有东西都做成 Prompt 文本，成本和混乱一起上升。
2. 同一份知识被多处重复存储，运行时来源不清，企业也不知道到底哪份生效。

## 四、企业知识的四类容器

建议正式把企业知识分到四类容器里。

## 4.1 `config_injection`

用于结构化、稳定、需要高优先级覆盖的知识。

典型内容：

- 品牌定位
- 账号定位
- 禁用词
- 审核规则
- 渠道规则
- 审批组映射

特点：

- 结构化
- 稳定
- 易审计
- 不依赖检索

## 4.2 `knowledge_base_injection`

用于长文档、资料库、案例库、说明书等可检索知识。

典型内容：

- 产品资料
- FAQ
- SOP 文档
- 历史方案
- 培训资料
- 行业术语说明

特点：

- 适合 RAG
- 适合按需召回
- 不应全部直接塞 Prompt

## 4.3 `runtime_context_injection`

用于当前这次运行才需要的临时上下文。

典型内容：

- 当前页面表单状态
- 当前任务输入变量
- 当前触发事件 payload
- 当前筛选条件
- 当前选中的记录

特点：

- 时效性强
- 生命周期短
- 预算必须严格控制

## 4.4 `artifact_feedback_injection`

用于历史输出和人工反馈回流。

典型内容：

- 草稿采用情况
- 驳回原因
- 审批意见
- 手工改写对比
- 业务效果标签

特点：

- 适合复盘、评估和后续推荐
- 不一定每次都直接进主 Prompt

---

## 五、企业知识的正式分类建议

为避免每个行业自己乱命名，建议平台统一先定义知识分类框架。

| 分类 | 示例 | 推荐容器 |
|---|---|---|
| `brand_rules` | 品牌语气、禁用词、价值观 | `config_injection` |
| `business_rules` | 审批规则、业务口径、政策 | `config_injection` |
| `product_knowledge` | 产品说明、SKU、卖点 | `knowledge_base_injection` + 配置 |
| `process_knowledge` | SOP、流程图、操作手册 | `knowledge_base_injection` |
| `reference_cases` | 历史样本、最佳实践 | `knowledge_base_injection` |
| `runtime_inputs` | 当前单据、当前事件 payload | `runtime_context_injection` |
| `feedback_signals` | 驳回原因、采用结果 | `artifact_feedback_injection` |

## 六、四条知识注入通道

## 6.1 配置注入 `config_injection`

建议由统一配置模型承载，例如前文提到的：

- `tenant_solution_configs`

适合直接变成：

- 工作流变量
- Prompt 参数
- 审批策略参数

### 6.2 知识库注入 `knowledge_base_injection`

建议复用现有：

- 企业知识库
- Agent 与 KB 的绑定关系
- RAG 检索链路

知识库注入的关键原则是：

- 按需召回
- 有来源
- 可停用
- 可加权

### 6.3 运行时上下文注入 `runtime_context_injection`

建议覆盖以下来源：

- 触发器输入
- 工作流输入变量
- 当前页面 `page_context`
- 当前会话上下文

### 6.4 反馈注入 `artifact_feedback_injection`

建议来源于：

- 审批意见
- 人工修改记录
- 采用/退回结果
- 周期性评估结果

## 七、和现有 KB / RAG 的对齐

当前项目已经有成熟的知识库和 RAG 链路，这一层不应重造。

## 7.1 已有能力可直接复用

现有系统已经具备：

- 企业知识库 CRUD
- Agent 与 KB 绑定
- RAG 上下文构建
- 多模态 RAG
- 企业对平台全局知识库的停用机制

### 7.2 企业知识库绑定的正确理解

知识库是否在运行时生效，不能只看“知识库存在”，还要看：

- Agent 是否绑定了该 KB
- 企业是否有权限访问
- 平台知识库是否被企业停用

### 7.3 平台知识库与企业停用

当前项目已有：

- 企业可对平台全局 KB 做 opt-out

这说明知识注入已经不是“单向强推”，而是带治理边界的。

后续平台设计应继续保留这一能力。

---

## 八、和页面上下文的对齐

当前项目已经有三层页面感知：

1. `page_context`
2. `get_page_context`
3. `invoke_page_operation`

这为企业知识注入提供了很重要的一条临时上下文通道。

### 8.1 页面上下文的定位

`page_context` 不是知识库，也不是配置库。

它是：

- 当前页面的临时上下文
- 当前任务最贴近用户操作面的状态快照

### 8.2 页面上下文必须受预算控制

当前项目已有：

- `ai_page_context_max_bytes`
- 默认 8192 bytes

这个限制必须继续作为平台正式规范的一部分，而不是临时实现细节。

### 8.3 页面上下文不要承担长期知识职责

不要把下面这些内容长期塞给 `page_context`：

- 大量历史样本
- 长篇产品说明
- 冗长品牌手册

这些应进入：

- KB
- 配置
- 资产库

---

## 九、注入优先级建议

不同知识来源如果同时存在，必须有固定优先级。

推荐优先级：

```text
平台安全底线
> 平台方案预设
> 企业结构化配置
> 当前运行时上下文
> 检索召回结果
> 历史反馈和记忆
```

### 9.1 为什么 RAG 不应高于结构化配置

例如：

- 品牌禁用词
- 审批规则
- 企业必带表达

这些是企业确定性规则，不应被检索结果覆盖。

### 9.2 为什么平台安全底线必须最高

因为不能出现：

- 企业 Prompt 覆盖平台安全限制
- 企业文档把审批基线冲掉

## 十、Prompt 分层建议

建议运行时 Prompt 明确拆层，而不是拼成一大段自由文本。

## 10.1 建议的 Prompt 层次

1. `platform_guardrail_prompt`
2. `solution_system_prompt`
3. `tenant_config_prompt`
4. `runtime_context_prompt`
5. `retrieval_context_prompt`

### 10.2 各层职责

#### 平台底线层

包含：

- 安全规则
- 合规规则
- 风险和审批底线
- 作用域隔离要求

#### 方案系统层

包含：

- 行业方案角色设定
- 行业输出格式
- 行业任务目标

#### 企业配置层

包含：

- 品牌语气
- 产品重点
- 组织规则
- 审核偏好

#### 运行时上下文层

包含：

- 当前任务输入
- 当前页面状态
- 当前事件 payload

#### 检索上下文层

包含：

- RAG 召回片段
- 来源信息
- 证据摘要

## 十一、预算与裁剪规范

所有知识注入通道都应具备预算模型。

## 11.1 建议的预算分类

| 预算 | 说明 |
|---|---|
| `prompt_budget` | 主 Prompt 可用预算 |
| `rag_budget` | 检索内容预算 |
| `page_context_budget` | 页面上下文预算 |
| `runtime_variable_budget` | 变量序列化预算 |

### 11.2 裁剪顺序建议

如果上下文过大，建议按以下顺序裁剪：

1. 历史反馈摘要
2. 次要检索结果
3. 页面样本数据
4. 低优先级运行变量

不要优先裁掉：

- 平台安全底线
- 企业关键配置
- 当前任务目标

### 11.3 裁剪结果应可见

建议在运行时 Artifact 中记录：

- 哪些内容被裁剪
- 为什么被裁剪
- 剩余预算是多少

这样后续定位效果问题会更容易。

---

## 十二、知识授权与隔离规则

企业知识注入必须同时遵守：

- 企业隔离
- 授权范围
- 平台知识 opt-out
- 页面上下文预算

### 12.1 企业知识库隔离

企业知识库默认只对本企业可见。

### 12.2 平台知识库可共享但要可控

平台可以下发：

- 行业通用知识库
- 平台全局参考知识库

但企业应保留：

- 可见性边界
- 停用能力

### 12.3 页面上下文也必须隔离

不能因为 `page_context` 是临时对象，就放松隔离要求。

仍应确保：

- 只含当前企业页面数据
- 不跨租户
- 不携带无关敏感字段

---

## 十三、来源可信度与新鲜度

知识注入不仅要问“有没有”，还要问：

- 靠不靠谱
- 新不新

### 13.1 建议为知识来源增加两个维度

- `source_trust_level`
- `freshness_level`

### 13.2 典型示例

| 来源 | 可信度 | 新鲜度 |
|---|---|---|
| 企业结构化配置 | 高 | 中 |
| 审批规则 | 高 | 中 |
| 当前页面表单状态 | 高 | 高 |
| 历史样本库 | 中 | 中 |
| 联网检索结果 | 中 | 高 |

### 13.3 使用建议

当结论严重依赖：

- 低可信度来源
- 过期来源

应在 Artifact 或输出中显式标注。

## 十四、知识注入与工作流节点的关系

不同节点应使用不同的注入组合。

### 14.1 建议的组合矩阵

| 节点类型 | 配置注入 | KB 注入 | 运行时上下文 | 反馈注入 |
|---|---|---|---|---|
| `llm` | 强 | 可选 | 强 | 可选 |
| `planner` | 强 | 可选 | 强 | 可选 |
| `knowledge_lookup` | 弱 | 强 | 弱 | 弱 |
| `approval_packet_builder` | 强 | 可选 | 强 | 可选 |
| `review` | 强 | 可选 | 强 | 强 |
| `retrospective` | 中 | 可选 | 中 | 强 |

### 14.2 不建议所有节点都吃全部上下文

例如：

- 纯路由节点不需要长篇 RAG
- 审批节点不需要全量历史文档

这样可以显著降低成本和噪音。

3. 素材与样本中心
4. 反馈与复盘中心

### 15.1 企业配置中心

- 审核规则
- 组织规则
- 输出偏好

### 15.2 知识库中心

适合管理：

- 产品资料
- SOP
- FAQ
- 案例库

### 15.3 反馈与复盘中心

适合管理：

- 驳回原因

## 十六、与运行时策略引擎的关系

知识注入不应绕开 `12-runtime-policy-engine-spec`。

策略引擎应判断：

- 该知识源是否允许被当前 Agent 使用
- 该 KB 是否在授权范围内
- 平台 KB 是否被该企业停用
- 当前页面上下文是否超预算

### 16.1 正确职责分层

```text
Knowledge Source
-> Policy Engine 裁决
-> Context Builder 组装
-> Agent / Workflow Node 使用
```

### 16.2 不建议每个节点自己判断知识可用性

否则后面会变成：

- 某个节点自己查 KB
- 某个节点自己查 suppress
- 某个节点自己查 page_context budget

这和前面统一策略引擎的目标相冲突。

## 十八、第一阶段实施建议

### Phase 1：先收敛三条主通道

第一阶段优先把这三条通道做扎实：

- 企业结构化配置
- 企业知识库 RAG
- 页面 / 输入运行时上下文

### Phase 2：再补反馈回流

补齐：

- 审批意见回流
- 采用/退回标签

### Phase 3：最后做更复杂的来源策略

补齐：

- 可信度
- 新鲜度
- 自动裁剪策略
- 知识源版本比较

## 十九、关键结论

1. 企业在平台中的核心价值是提供业务知识，而不是开发底层工具。
2. 企业知识注入至少应分成结构化配置、知识库检索、运行时上下文、反馈回流四条正式通道。
3. 不同类型知识必须进入不同容器，不能全部塞进 Prompt 或知识库。
4. 现有 KB 绑定、RAG、多模态检索、平台 KB 停用和页面上下文预算能力都应直接成为这套规范的实施基础。
5. 知识注入必须有优先级、预算、隔离和可信度控制，不能无限制堆上下文。
6. 知识源是否可用应统一经过运行时策略引擎裁决，而不是让各个节点各写一套判断逻辑。

# AI 编排与工作流平台行业方案生命周期与升级作战手册（2026-03-23）

## 一、文档目标

本文档用于把“行业方案插件装上去之后，后续怎么持续演进”正式定义清楚。

前面的文档已经回答了：

- 行业方案如何以插件形式存在
- 企业如何获得授权
- 模板、Agent、审批、知识如何协同
- 企业能改什么、不能改什么

但还缺少一个关键部分：

- 方案从孵化到退役的完整生命周期是什么
- 升级到底升级哪些对象
- 平台原件升级与企业副本升级怎么区分
- 出问题时怎么灰度、回滚、停更、迁移

如果这层不先规范，后面平台一旦进入多行业、多企业、多版本并行，马上会出现：

- 某插件升级后，企业不知道自己是否受影响
- 平台模板升级时误覆盖企业副本
- 定制交付版本和标准方案版本互相打架
- 发布记录、兼容性、迁移动作没有统一口径

所以，本文档的目标不是写“升级说明”，而是定义平台正式的方案生命周期与升级作战机制。

---

## 二、核心结论

### 2.1 行业方案的生命周期不能只看插件安装状态

行业方案不是“安装完成就结束”的静态插件。

它至少同时包含：

- 插件代码和页面
- 工作流模板
- Agent 预设
- Skill 投影
- Prompt 模板
- 审批预设
- 企业配置 Schema
- 资产分类和企业侧操作说明

因此它必须有完整生命周期，而不只是：

- installed
- enabled
- disabled

### 2.2 升级对象不是单一版本，而是多层版本体系

行业方案升级时，真正涉及的对象通常至少包括：

1. 插件版本
2. 方案发行版本
3. 资源清单版本
4. 平台原模板版本
5. 企业激活版本
6. 企业副本版本
7. 定制交付增强版本

所以平台必须承认这是“多层版本升级”，不能把一切都压缩成一个 `plugin.version`。

### 2.3 平台原件升级与企业自有副本升级必须彻底分离

必须坚持：

- 平台拥有的平台原件，由平台升级
- 企业拥有的企业副本，由企业决定是否跟进升级

平台可以：

- 给出升级建议
- 提供差异说明
- 提供迁移向导

但不能在未授权的情况下直接覆盖企业自己的工作流副本。

### 2.4 升级必须带兼容性判断、灰度、观测和回滚

行业方案升级不能是“上传新版本然后全量切换”。

标准动作应该是：

```text
兼容性预检
-> 迁移计划生成
-> 内部验证
-> 指定企业灰度
-> 观察指标
-> 分批放量
-> 稳定后正式推广
-> 必要时一键回滚
```

### 2.5 定制交付必须有独立升级通道

标准行业方案与企业定制交付虽然共享平台内核，但升级路径不能混成一条线。

原因很简单：

- 标准方案追求规模化复制
- 定制交付追求企业特定适配

两者升级的判断标准、验证重点、回滚对象都不一样。

---

## 三、为什么现在必须单独写这份文档

当前平台已经明确要同时支持：

- 插件市场
- 行业解决方案中心
- 企业模板派生
- 企业简单工作流
- 定制交付

这意味着后面同一时间会同时存在：

- 平台标准版方案
- 行业灰度版方案
- 企业私有激活版方案
- 企业定制增强版方案
- 企业派生副本

如果没有生命周期与升级规范，平台会很快进入以下混乱状态：

1. 运营上不知道该先升级哪个层。
2. 技术上不知道哪个版本才是运行时真相。
3. 企业侧不知道自己是不是落后版本。
4. 定制交付和标准方案无法形成产品沉淀关系。

所以这份文档本质上是在回答：

> 一个插件化行业方案，如何在平台里长期“可迭代、可升级、可治理、可回滚”。

## 四、正式对象模型

建议把行业方案生命周期相关对象正式抽出来，而不是散落在不同表里各管一段。

### 4.1 核心对象建议

| 对象 | 作用 |
|---|---|
| `solution_plugin` | 行业方案插件发行单元，对应插件市场中的方案包 |
| `solution_release` | 某个行业方案的正式发行记录 |
| `solution_resource_manifest` | 当前发行版本包含哪些模板、Agent、Prompt、审批预设、配置 Schema |
| `solution_compatibility_matrix` | 描述该版本与平台内核、连接器、Schema、套餐能力的兼容关系 |
| `tenant_solution_installation` | 企业已获得并安装/激活的方案实例 |
| `tenant_solution_activation` | 企业当前正在使用的生效版本与生效策略 |
| `tenant_upgrade_task` | 企业升级任务、阻塞点、人工确认与结果记录 |
| `tenant_copy_sync_state` | 企业副本与平台原件之间的同步状态 |

### 4.2 `Plugin` 仍是发行单元，但不应独自承担全部升级语义

这里要再次强调：

- `Plugin` 负责安装、启停、License、基础生命周期
- `solution_release` 负责“行业方案这个业务包”的正式发行语义

这样可以避免后续把：

- 插件代码升级
- 模板升级
- 企业激活版本切换

全部混在一个对象上。

## 五、行业方案生命周期阶段

建议把行业方案的生命周期拆成 8 个正式阶段。

### 5.1 `incubating`

含义：

- 方案仍在内部构思、打样、验证复用性
- 可能只有少量模板和实验配置

特点：

- 不进入正式插件市场
- 不进入正式授权体系
- 不对企业开放正式 SLA

### 5.2 `internal_validating`

含义：

- 方案已经形成初步资源包
- 开始在平台内部做联调、风险验证、评估与观测验证

特点：

- 可以有内测企业
- 必须有版本记录
- 必须开始产出兼容性矩阵

### 5.3 `pilot_release`

含义：

- 方案进入小范围企业试点
- 往往通过 `selected_tenants` 灰度发布

特点：

- 明确试点名单
- 明确升级回滚负责人
- 明确试点观察指标

### 5.4 `market_ready`

含义：

- 方案已具备对外售卖条件
- 进入插件市场/行业解决方案中心正式目录

特点：

- 必须有正式文档
- 必须有价格与授权模型
- 必须有最小升级路径

### 5.5 `active_scaling`

含义：

- 已有多个企业正式使用
- 平台进入规模化复制和持续迭代阶段

特点：

- 要求升级链路稳定
- 要求兼容性矩阵可维护
- 要求企业升级通知机制成熟

### 5.6 `stabilizing`

含义：

- 方案核心能力趋于稳定
- 后续以优化、降本、补兼容为主

特点：

- 可以开始提供 `LTS` 或长期支持通道
- 大版本节奏应变慢

### 5.7 `deprecated`

含义：

- 方案不再建议新售卖或新启用
- 但存量企业仍在运行

特点：

- 应冻结大部分新功能
- 必须提供迁移目标和迁移窗口

### 5.8 `retired`

含义：

- 方案正式退役
- 不再提供新安装、新授权和常规升级

特点：

- 只保留必要审计数据与退役说明
- 所有企业应在退役前完成迁移或签署例外支持协议

## 六、版本层级模型

### 6.1 建议至少承认六层版本

| 版本层 | 说明 |
|---|---|
| `plugin_version` | 插件代码、前端页面、路由、执行器、资源包格式版本 |
| `solution_release_version` | 面向市场/行业中心的正式方案发行版本 |
| `resource_manifest_version` | 某发行版本包含的模板、Prompt、审批、Agent 等资源清单版本 |
| `platform_template_version` | 平台拥有模板或 Agent 原件的具体版本 |
| `tenant_activation_version` | 某企业当前正式激活使用的方案版本 |
| `tenant_copy_version` | 企业派生副本自己的本地演化版本 |

### 6.2 为什么 `tenant_activation_version` 与 `tenant_copy_version` 要分开

因为企业端会同时存在两类使用方式：

1. 直接使用平台托管原件
2. 复制为本地副本后自行演化

前者更像“激活的平台版本”。

后者更像“企业自己维护的本地版本”。

如果两者不拆开，后面升级建议、差异对比、回滚策略都会混乱。

### 6.3 版本通道建议

建议正式支持 3 类版本通道：

| 通道 | 说明 |
|---|---|
| `beta` | 内测或小范围试用版本 |
| `stable` | 默认推荐正式使用版本 |
| `lts` | 长期支持版本，强调稳定与兼容 |

## 七、资源所有权与升级权边界

升级权必须严格遵守资源所有权原则。

### 7.1 平台拥有并升级的对象

包括：

- 方案插件代码
- 平台原生模板
- 平台原生 Agent 预设
- 平台审批基线预设
- 平台插件页面
- 平台托管连接器与执行器

### 7.2 企业拥有并决定是否升级的对象

包括：

- 企业复制出来的模板副本
- 企业本地 Prompt 调整副本
- 企业本地审批加严规则
- 企业自己的配置数据、知识、素材与触发器

### 7.3 平台可“建议升级”，但不可“强行覆盖”

对于企业自有对象，平台可以提供：

- 差异对比
- 兼容性预警
- 自动迁移建议
- 一键创建升级副本

但不能：

- 静默改企业副本
- 静默移除企业本地字段
- 静默替换企业本地触发器

---

## 八、兼容性矩阵规范

行业方案的升级是否允许，不应靠人脑临时判断，建议正式维护兼容性矩阵。

### 8.1 兼容性应至少覆盖以下维度

| 维度 | 说明 |
|---|---|
| 平台内核兼容 | 与当前平台版本、核心运行时、插件 API 的兼容关系 |
| 工作流契约兼容 | 与输入/输出 Schema、节点端口契约的兼容关系 |
| 模型与 Skill 兼容 | 与 Agent、Skill 授权链、模型能力的兼容关系 |
| 触发器兼容 | 与 `manual` / `schedule` / `api` / `webhook` / `event` 的兼容关系 |
| 审批与策略兼容 | 是否改变审批底线、风险分级、运行时策略要求 |
| 企业配置兼容 | 企业现有配置字段是否仍可直接使用 |
| 企业知识兼容 | KB 绑定、样本、页面上下文预算是否受影响 |

### 8.2 建议的兼容性等级

| 等级 | 含义 |
|---|---|
| `direct_compatible` | 可直接升级，无需迁移 |
| `compatible_with_migration` | 可升级，但必须先执行迁移 |
| `manual_review_required` | 需要人工评估后再升级 |
| `blocked` | 当前条件下禁止升级 |

### 8.3 哪些情况通常属于 `manual_review_required`

例如：

- 企业副本改动较大
- 审批流程被企业本地深度改写
- 数据契约出现破坏性变更
- 依赖新的高风险能力或新的授权项

## 九、升级类型分级

建议把升级正式分成三类，而不是笼统写“有新版本”。

### 9.1 `patch_upgrade`

典型内容：

- Bug 修复
- 文案修正
- Prompt 微调
- 页面小修复
- 低风险兼容补丁

特点：

- 理论上不改变业务契约
- 适合快速灰度和快速回滚

### 9.2 `minor_upgrade`

典型内容：

- 新增可选模板
- 新增可选字段
- 新增低风险节点能力
- 增加观测字段、评估能力、企业配置项

特点：

- 不应破坏已有主流程
- 可能需要企业做轻配置补充

### 9.3 `major_upgrade`

典型内容：

- 工作流结构重组
- 数据契约大改
- 触发器机制变化
- 审批底线显著加强
- 连接器或执行器替换
- 企业配置 Schema 破坏性变更

特点：

- 必须做兼容性预检
- 必须有迁移方案
- 必须有明确回滚预案

## 十、不同资产类型的升级策略

行业方案不是单一资产，所以升级策略也要按资产类型拆开。

### 10.1 资产升级矩阵

| 资产类型 | 默认升级策略 | 企业动作 |
|---|---|---|
| 方案插件代码 | 平台托管升级 | 企业感知通知 |
| 平台托管模板 `managed_template` | 平台升级，可灰度激活 | 企业确认影响面 |
| 企业可编辑模板原件 | 平台升级原件，不覆盖企业副本 | 企业选择是否吸收变更 |
| 企业副本 | 不自动覆盖 | 企业自主升级或合并 |
| Agent 预设原件 | 平台升级原件 | 企业可接受新预设或保留旧版 |
| 审批基线 | 平台可自动加严 | 企业不能放宽，仅可追加本地加严 |
| 企业配置 Schema | 优先兼容追加 | 必要时执行配置迁移 |
| 插件页面 | 平台托管升级 | 企业关注操作差异 |
| 托管连接器/执行器 | 平台托管升级 | 企业不可直接修改 |

### 10.2 审批和风险升级要特殊处理

涉及：

- 风险分级提升
- 强制审批增加
- 高自治动作限制收紧

这类升级属于“治理升级”，通常可以直接加严，但必须：

- 有变更说明
- 有生效时间
- 有影响对象列表

不能无提示地让企业业务突然停摆。

## 十一、企业侧安装、激活与升级模式

建议把企业使用行业方案分成 4 种升级模式。

### 11.1 `auto_follow_managed`

适用：

- 企业直接使用平台托管方案
- 企业不维护本地结构副本

特点：

- 平台可按灰度策略自动推进升级
- 企业主要接收通知和观察影响

### 11.2 `confirm_before_activate`

适用：

- 企业使用平台方案，但关键流程对业务影响较大

特点：

- 平台可推送升级候选
- 企业确认后才切换生效版本

### 11.3 `advisory_only`

适用：

- 企业拥有大量本地派生副本

特点：

- 平台只给差异建议
- 企业自己决定是否合并平台更新

### 11.4 `custom_delivery_lane`

适用：

- 企业有专属定制增强包

特点：

- 升级要走定制交付通道
- 标准版升级不应直接覆盖定制版

## 十二、标准升级作战流程

建议把行业方案升级流程固定为 9 个阶段。

### 12.1 阶段 1：形成升级包

升级包建议至少包含：

- 新版本清单
- 变更摘要
- 兼容性矩阵
- 迁移脚本或迁移说明
- 回滚说明
- 风险等级说明

### 12.2 阶段 2：生成影响分析

平台应自动或半自动生成影响分析报告，至少说明：

- 会影响哪些企业
- 会影响哪些模板
- 会影响哪些触发器
- 是否涉及破坏性契约变更
- 是否涉及审批或风险升级

### 12.3 阶段 3：内部验证

内部验证至少应覆盖：

- 插件安装/升级成功
- 模板与数据契约校验通过
- 关键运行链路回放通过
- 关键审批闸门可正常命中
- 观测和评估指标正常

### 12.4 阶段 4：选定企业灰度

建议先发到：

- 平台自测租户
- 内测企业
- 低风险企业

不要直接全量放开。

### 12.5 阶段 5：企业确认或自动切换

根据升级模式决定：

- 自动切换
- 待企业确认切换
- 仅生成升级建议任务

### 12.6 阶段 6：观察窗口

观察窗口至少应关注：

- 运行成功率
- 审批阻塞率
- 成本变化
- 草稿/结果采用率
- 企业侧异常反馈

### 12.7 阶段 7：分批放量

灰度稳定后，再按批次扩大范围：

```text
内部
-> 试点企业
-> 指定行业批次
-> 全量符合资格企业
```

### 12.8 阶段 8：异常处置

如出现：

- 关键流程失败率升高
- 成本异常飙升
- 审批积压异常
- 高风险动作误放行

应立即触发：

- 暂停放量
- 冻结触发器
- 回滚版本
- 创建修复分支

### 12.9 阶段 9：升级归档

每次升级结束后应归档：

- 最终生效范围
- 异常与修复记录
- 回滚记录
- 企业确认记录
- 指标对比结果

## 十三、企业副本升级与合并机制

企业副本是后续最容易失控的部分，必须单独建模。

### 13.1 平台不直接覆盖企业副本

这是底线。

平台原件更新后，对企业副本只能做：

- 差异检测
- 合并建议
- 升级向导
- 自动创建新候选副本

不能直接替换企业当前生产副本。

### 13.2 建议维护 `tenant_copy_sync_state`

该状态至少应反映：

- 当前副本基于哪个平台原件版本派生
- 平台最新原件版本是多少
- 差异类型是结构差异还是参数差异
- 是否存在阻断合并项

### 13.3 企业副本建议的升级动作

建议支持：

- `accept_all_non_breaking_changes`
- `review_diff_then_merge`
- `fork_new_copy_from_latest`
- `stay_on_current_version`

### 13.4 什么时候建议企业“新建副本而不是合并”

例如：

- 企业副本改动过大
- 原始结构已经偏离平台主线太多
- 新版本是大版本重构

这种情况下，比起做危险的自动合并，更适合：

- 用新版本原件复制出新副本
- 企业再迁移关键参数与知识绑定

---

## 十四、配置迁移与知识迁移

行业方案升级不只是模板升级，经常还涉及企业配置和知识结构变化。

### 14.1 配置迁移原则

企业配置 Schema 升级应优先遵守：

1. 先兼容追加字段
2. 再给默认值
3. 最后才做破坏性移除

### 14.2 破坏性配置变更的处理方式

如果确实要移除或重命名字段，建议至少提供：

- 字段映射表
- 自动迁移建议
- 受影响企业清单
- 迁移后校验结果

### 14.3 知识与资产迁移原则

企业知识库和资产通常不应该因为方案升级而被强制重建。

更合理的做法是：

- 保持知识容器稳定
- 更新知识分类与引用规则
- 必要时做索引重建或标签迁移

不要让企业因为一次方案升级重新上传所有资料。

---

## 十五、回滚、热修与停用机制

### 15.1 回滚必须作用于“未来运行”，不追改“历史运行”

和前文发布规范保持一致：

- 回滚只影响未来新创建的运行
- 已启动的 `WorkflowRun` 仍绑定原版本快照

### 15.2 建议区分三类异常处置

| 类型 | 含义 |
|---|---|
| `rollback` | 回到上一个稳定版本 |
| `hotfix` | 在当前问题版本基础上紧急修补 |
| `freeze` | 暂停新安装、暂停新激活或暂停新触发 |

### 15.3 什么时候优先 `freeze`

例如：

- 问题还没定位清楚
- 不确定是代码、模板还是配置迁移导致
- 高风险外部动作存在误执行风险

此时先冻结，比贸然回滚更安全。

---

## 十六、弃用与退役作战手册

一个成熟平台必须承认：有些行业方案最终会被淘汰。

### 16.1 弃用 `deprecated`

进入弃用阶段后建议：

- 不再新增新客户售卖
- 不再默认推荐新企业启用
- 仅做必要修复和安全维护
- 明确推荐替代方案

### 16.2 迁移窗口

进入弃用后，平台应明确：

- 最晚支持日期
- 推荐迁移目标
- 配置迁移方式
- 企业需要完成的动作

### 16.3 退役 `retired`

退役后应完成：

- 下线市场入口
- 停止新授权
- 停止新激活
- 保留必要审计与历史运行回放能力

---

## 十七、定制交付升级专线

标准方案和定制交付之间必须有清晰边界，但也必须有回流关系。

### 17.1 三种定制交付形态对应三种升级模式

#### `managed_locked_delivery`

特点：

- 平台拥有全部升级控制权
- 企业以接收通知和业务验收为主

#### `managed_partial_delivery`

特点：

- 核心片段由平台升级
- 企业可编辑片段由企业自控
- 升级时要做“锁定片段升级 + 本地片段兼容检查”

#### `tenant_operated_delivery`

特点：

- 平台提供升级候选
- 企业决定何时切换本地生产版本

### 17.2 标准版升级不应直接覆盖企业定制增强

标准行业包升级后，如果企业还挂着：

- 专属连接器
- 专属审批流程
- 专属页面
- 专属执行器

则必须先判断：

- 是否与标准版兼容
- 是否要进入新的变更单
- 是否应先把通用部分产品化，再同步给该企业

---

## 十八、管理端与企业端页面建议

### 18.1 管理端建议增加的页面

建议至少有以下治理入口：

1. 方案生命周期看板
2. 发行记录与升级包管理
3. 兼容性矩阵管理
4. 灰度与放量控制台
5. 企业升级任务中心
6. 退役与迁移中心

### 18.2 企业端建议增加的页面

建议至少有以下使用入口：

1. 当前激活版本
2. 可升级版本提示
3. 变更摘要与影响说明
4. 配置迁移预览
5. 企业副本同步状态
6. 是否立即切换/延期切换

### 18.3 页面职责边界

管理端负责：

- 发行
- 灰度
- 回滚
- 兼容性治理

企业端负责：

- 接收升级建议
- 确认企业副本如何处理
- 迁移企业配置与知识
- 管理自身生产启用节奏

## 十九、第一阶段实施建议

### Phase 1：先把“发行版本 + 升级任务”建出来

优先建设：

- `solution_release`
- `solution_resource_manifest`
- `tenant_solution_installation`
- `tenant_upgrade_task`

### Phase 2：再补“兼容性矩阵 + 企业副本同步状态”

补齐：

- `solution_compatibility_matrix`
- `tenant_copy_sync_state`
- 自动影响分析
- 配置迁移建议

### Phase 3：最后补“灰度控制台 + 退役迁移中心”

补齐：

- 灰度放量
- 观察窗口
- 一键回滚
- 弃用迁移与退役通知

## 二十、关键结论

1. 行业方案必须被视为一个可持续演进的业务包，而不是只看插件安装状态的静态资源。
2. 行业方案升级本质上是多层版本升级，至少应区分插件版本、发行版本、原件版本、企业激活版本与企业副本版本。
3. 平台原件升级与企业副本升级必须彻底分离，平台可以给建议和迁移工具，但不能静默覆盖企业资产。
4. 每次升级都必须经过兼容性预检、内部验证、灰度放量、观测窗口和回滚准备，不能直接全量切换。
5. 定制交付必须有独立升级专线，标准行业包升级不应直接覆盖企业专属增强能力。
6. 第一阶段先把发行版本、企业升级任务和影响分析做出来，再逐步补齐兼容性矩阵、灰度控制台和退役迁移能力。

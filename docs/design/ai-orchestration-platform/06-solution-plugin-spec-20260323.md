# AI 编排与工作流平台行业解决方案插件规范（2026-03-23）

## 一、文档目标

本文档定义“行业解决方案中心并入插件市场”之后，行业方案应如何以插件形式存在、安装、授权、升级与运行。

重点回答：

1. 行业解决方案插件和普通能力插件有什么区别。
2. 一个行业方案插件内部应该包含哪些资源。
3. 管理端、企业端分别如何使用这类插件。
4. 如何与现有 `Plugin`、`PluginLicense`、`SkillPackage`、`Agent`、工作流模板体系对齐。

本文档仍然是平台级规范，不绑定单一行业。

---

## 二、核心结论

### 2.1 行业解决方案就是插件，不单独再造发行系统

“行业解决方案中心”在产品上可以单独展示，但在系统模型上应并入插件市场。

结论：

- 行业方案的发行单元仍然是 `Plugin`
- 行业方案的商业单元仍然走插件定价与 License
- 行业方案的企业可见性仍然通过 `TenantEntitlement` 控制

### 2.2 行业方案插件不是“单个工具”，而是“资源包”

一个行业方案插件通常不是只带一个技能，而是一个完整资源包，可能包含：

- 页面
- 工作流模板
- Agent 预设
- Skill 投影
- Prompt 模板
- 审批预设
- 企业配置 Schema
- 交付说明

### 2.3 平台内核保持行业无关，行业能力一律外挂

行业逻辑不得直接写入平台内核。

应坚持：

- 平台内核负责运行、授权、审批、审计、计费
- 行业方案插件负责行业页面、行业模板、行业策略与资源组合

### 2.4 企业可以使用和配置方案，不可以扩展平台内核

企业端可以：

- 启用已授权方案
- 填写方案配置
- 复制可编辑模板
- 运行方案工作流

企业端不可以：

- 安装插件
- 编写代码型工作流
- 新增连接器、执行器或系统级能力

---

## 三、行业方案插件的正式定义

建议把行业解决方案插件定义为：

> 以 `Plugin` 为发行单元，面向某一行业或业务场景交付的一组工作流模板、Agent 预设、页面、审批策略和业务配置规范。

与普通能力插件相比，行业方案插件更强调：

- 业务场景完整性
- 交付闭环
- 页面与模板协同
- 企业配置接入

---

## 四、方案插件与普通插件的区别

| 维度 | 普通能力插件 | 行业方案插件 |
|---|---|---|
| 核心目标 | 提供单一能力 | 提供可用业务方案 |
| 主要内容 | Skill、Connector、Hook | 页面、模板、Agent、策略、配置 |
| 用户视角 | 技术能力组件 | 可直接购买和启用的行业包 |
| 商业形态 | 能力增购 | 方案包 / 行业包 / 定制交付 |
| 运营方式 | 技术安装与启停 | 授权、启用、配置、运营 |

### 4.1 两类插件可以组合

常见组合方式：

- 能力插件提供联网、抓取、分析、连接器能力
- 产品模块插件提供跨行业共用底座，如任务编排模块、审批工作台或语义指标层
- 行业方案插件通过 `dependencies.plugins` 依赖这些产品模块插件，再在其上挂行业模板和预设
- 行业方案插件引用这些能力，包装成完整业务方案

这样平台可以避免把所有行业逻辑都塞进单个大插件。

---

## 五、方案插件的资源组成模型

### 5.1 推荐组成

一个完整方案插件建议由以下资源组成：

| 资源 | 作用 | 运行时真相 |
|---|---|---|
| `Plugin` | 发行、安装、升级、License | 插件系统 |
| `WorkflowTemplate` | 方案流程模板 | 工作流运行时 |
| `AgentProfile` | 方案 Agent 预设 | Agent 体系 |
| `SkillPackage + Skill` | 能力目录投影 | 目录层；运行时仍看 `AgentSkillGrant` |
| `ApprovalPolicy` | 风险和审批预设 | 审批治理层 |
| `PromptTemplate` | 文本策略和模板 | AI 配置层 |
| `TenantSolutionConfig Schema` | 企业配置结构 | 企业配置层 |
| `TenantSolutionAsset Schema` | 企业资产分类 | 企业资产层 |
| 页面扩展 | 管理端与企业端 UI | 前端插件层 |

### 5.2 `SkillPackage` 仍不是运行时绑定真相

这里再次强调：

- 方案插件可以同步 `SkillPackage + Skill`
- 但运行时能力是否对某个 Agent 生效，仍然取决于 `AgentSkillGrant`

不能因为引入行业方案，就把 `SkillPackage` 又重新变成运行时自动绑定入口。

## 六、推荐目录结构

结合现有插件系统，建议行业方案插件目录大致如下：

```text
solution-example/
├── plugin.yaml
├── README.md
├── backend/
│   ├── main.py
│   ├── api/
│   │   ├── admin_routes.py
│   │   └── tenant_routes.py
│   ├── skills/
│   ├── executors/
│   ├── templates/
│   │   ├── workflows/
│   │   ├── prompts/
│   │   └── approvals/
│   ├── seed/
│   │   ├── agents/
│   │   ├── solution_configs/
│   │   └── assets_schema/
│   └── migrations/
├── frontend/
│   └── dist/
└── locales/
    ├── zh-CN.json
    └── en.json
```

### 6.1 `templates/` 建议分层

为避免后续模板越来越杂，建议把模板分成：

- `workflows/`
- `prompts/`
- `approvals/`

这样有利于分别做版本化与差异对比。

## 七、`plugin.yaml` 建议扩展

当前插件系统已经有稳定清单机制，行业方案插件不应绕开它，建议在现有 `plugin.yaml` 上扩展“方案包元数据”。

### 7.1 顶层分类建议

建议至少补充以下字段或等价语义：

| 字段 | 说明 |
|---|---|
| `plugin_kind` | 固定为 `solution_plugin` |
| `solution_category` | 行业分类，如 `short_video`、`ecommerce` |
| `delivery_mode` | `self_service` / `managed_delivery` / `custom_delivery` |
| `product_code` | 商业 SKU |
| `requires_platform_feature` | 依赖的平台能力开关 |

### 7.2 `extensions.solution_package` 建议结构

推荐增加：

```yaml
extensions:
  solution_package:
    display_category:
      zh-CN: "行业增长"
      en: "Industry Growth"
    scenario_tags:
      - content_growth
      - workflow
      - analysis
    included_resources:
      workflow_templates:
        - code: short_video_topic_scan
        - code: short_video_script_draft
      agent_profiles:
        - code: short_video_strategist
      approval_policy_presets:
        - code: short_video_brand_review
    tenant_builder_policy:
      can_copy_templates: true
      can_edit_copied_templates: true
      can_add_code_nodes: false
      can_add_external_write_nodes: false
    tenant_config_schema:
      - key: brand_profile
      - key: tone_rules
      - key: compliance_rules
```

说明：

- 这里是“资源编排元数据”，不是运行时绑定真相。
- 运行时仍要经授权层和工作流层解析。

## 八、安装、授权与启用流程

### 8.1 建议流程

```text
管理端上架方案插件
-> 管理端安装插件
-> 插件 License 生效
-> 同步资源投影
-> 管理端给企业发放 TenantEntitlement
-> 企业端看到方案
-> 企业填写业务配置
-> 企业启用模板或复制模板
-> 运行工作流
```

### 8.2 各阶段责任划分

#### 安装

只能由管理端完成。

#### 授权

由管理端通过商业授权体系发放。

#### 启用

由企业在自身空间内启用和配置。

#### 运行

由企业在自身空间内发起并运营。

### 8.3 运行前联合校验

企业要真正运行一个方案模板，建议同时满足：

1. 企业有平台基础订阅
2. 企业有该方案包授权
3. 插件已启用且 License 有效
4. 模板状态可用
5. 模板依赖能力已授权

---

## 九、资源所有权与企业可编辑边界

### 9.1 默认所有权

行业方案插件默认属于平台资源：

- 插件归平台
- 方案模板归平台
- 预设 Agent 归平台
- 审批基线归平台

### 9.2 企业可衍生但不改原件

企业对方案资源的常见使用方式应是：

- 启用
- 配置
- 复制
- 派生

不应允许企业直接修改平台原件。

### 9.3 允许企业修改的边界

企业可修改的内容建议仅包括：

- 企业品牌参数
- 企业审批人绑定
- 企业知识和素材
- 被允许复制的无代码模板
- 被允许调参的 Agent 预设

企业不可修改：

- 插件代码
- 执行器
- 连接器
- 平台强制审批底线
- 方案包内核逻辑

---

## 十、与工作流类型边界的联动

### 10.1 方案插件内部允许有两类模板

建议方案插件内部模板分成：

- `managed_template`
- `tenant_editable_template`

### 10.2 `managed_template`

特征：

- 平台维护
- 企业仅能配置参数
- 升级路径清晰
- 适合风险较高或逻辑较复杂的流程

### 10.3 `tenant_editable_template`

特征：

- 企业可复制为副本
- 企业可在白名单节点范围内修改
- 不能增加代码节点与高危连接器

### 10.4 代码型能力只能随方案插件或能力插件交付

如果某个流程依赖：

- 自定义执行器
- 自定义连接器
- 自定义复杂后端逻辑

则只能由平台方通过插件交付，不能让企业在页面上自行拼出来。

---

## 十一、版本与升级策略

方案插件至少涉及三层版本：

1. 插件版本
2. 模板版本
3. 企业副本版本

### 11.1 插件版本

关注：

- 清单与代码
- 页面资源
- 路由与执行器

### 11.2 模板版本

关注：

- 工作流结构
- Prompt 模板
- 审批预设

### 11.3 企业副本版本

关注：

- 企业复制后的本地演化
- 企业是否接受上游升级

### 11.4 升级原则

建议坚持：

- 平台原模板升级不直接覆盖企业副本
- 对 `managed_template` 可做受控升级
- 对企业副本采用“可选同步变更”模式

---

## 十二、页面侧建议

### 12.1 管理端页面

行业方案插件建议至少提供或投影到以下入口：

- 方案详情
- 资源总览
- 默认模板管理
- 授权与交付说明
- 版本记录

### 12.2 企业端页面

行业方案插件建议至少提供或投影到以下入口：

- 方案首页
- 企业配置页
- 模板工作台
- 运行与草稿页
- 审批与复盘页

### 12.3 页面职责边界

管理端页面偏治理与分发。

企业端页面偏使用与运营。

不要让企业端直接看到“插件安装”“升级”“执行器配置”这类平台治理入口。

---

## 十三、安全与风控要求

### 13.1 方案插件必须服从平台内核约束

包括但不限于：

- Agent -> Skill -> AIGateway 链路
- 插件能力声明白名单
- SkillPackage 只做目录投影
- 审批与授权联合闸门

### 13.2 对外写能力应独立成受控能力插件

如果未来行业方案需要对接：

- 抖音发布
- 电商后台改价
- CRM 客户写回

建议把这些高风险外部写能力独立成受控能力插件，再由行业方案按授权组合。

这样更利于：

- 安全审计
- 能力复用
- 风险隔离
- 商业售卖

---

## 十四、与计费和授权的关系

行业方案插件的商业闭环应统一走以下链路：

```text
Plugin(pricing + license)
-> TenantEntitlement(solution_package)
-> Template / Agent / Page Visibility
-> Run Permission
```

说明：

- `PluginLicense` 负责插件是否可运行
- `TenantEntitlement` 负责企业是否获得该方案
- 两者缺一不可

### 14.1 企业定制交付如何挂接

企业定制交付建议仍然挂在方案插件下面，而不是另起一套平行体系。

即：

- 标准版方案包是一个 `solution_plugin`
- 某企业的定制增强能力是该插件下的 `custom_delivery_entitlement`

这样产品和技术模型都更清晰。

---

## 十五、第一阶段实施建议

### Phase 1：先让方案插件成为正式分类

优先补齐：

- `plugin_kind = solution_plugin`
- 方案包元数据
- 方案包在插件市场中的展示分类

### Phase 2：再补资源绑定

补齐：

- 模板清单绑定
- Agent 预设绑定
- 审批预设绑定
- 企业配置 Schema

### Phase 3：再补升级与交付模型

补齐：

- 企业副本升级建议
- 定制交付记录
- 方案版本兼容矩阵

---

## 十六、关键结论

1. 行业解决方案中心在系统模型上应并入插件市场，行业方案的正式发行单元仍然是 `Plugin`。
2. 行业方案插件本质上是“资源包”，而不是单个工具，通常包含模板、页面、Agent、审批预设和企业配置结构。
3. 企业可以启用、配置、复制和运营方案，但不能安装插件、扩展内核或创建代码型能力。
4. 方案插件与运行时之间必须通过授权层、模板层和 Agent 授权层衔接，不能把 `SkillPackage` 重新变成运行时真相。
5. 高风险对外写能力应尽量沉到受控能力插件中，再由行业方案组合使用。
6. 第一阶段先把方案插件分类、授权传播和资源清单打通，再做更复杂的版本升级与定制交付能力。

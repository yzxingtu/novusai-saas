# AI 编排与工作流平台方案市场准入、审核与商业治理规范（2026-03-23）

## 一、文档目标

本文档用于定义插件市场和行业解决方案中心的准入标准、审核流程、上架规则、商业治理与下架机制。

这份文档要回答的核心问题是：

1. 什么样的方案、插件、模板可以进入平台市场。
2. 平台方、企业方、合作伙伴各自能发布什么，不能发布什么。
3. 上架前需要经过哪些安全、质量、评估、文档和商业审查。
4. 上架后如何做授权、试用、下架、暂停、投诉与版本治理。
5. 如何把市场做成可交易、可复用、可治理的正式能力，而不是资源堆放区。

本文档适用于公共市场、管理端定向分发、企业私有模板库与合作伙伴托管发布场景。

---

## 二、核心结论

### 2.1 市场不是文件上传区，而是受治理的能力分发面

任何进入市场的对象，都不应只满足“能安装”。

还必须满足：

- 能被理解
- 能被评估
- 能被授权
- 能被审查
- 能被升级
- 能被下架

### 2.2 必须正式区分三类市场对象

建议至少分为：

1. `public_market_listing`
2. `managed_private_listing`
3. `tenant_private_template_listing`

这三类的发布权限、审核强度、可见范围、商业化方式都不相同。

### 2.3 代码型方案和代码型扩展仍应由平台方统一生产与审核

与前面的平台边界保持一致：

- 平台方可发布代码型行业方案、复杂连接器、复杂执行器、官方组件
- 企业方可以编排简单流程和模板
- 企业方自建的简单流程可以企业内复用，或由管理端定向分配
- 企业方不能直接把复杂代码型扩展公开上架给全平台销售

### 2.4 上架审核必须同时覆盖技术、业务、合规和商业四个维度

建议至少检查：

- 安全和权限边界
- 功能可用性
- 文档完整性
- 评估与验收结果
- 版本兼容性
- 定价与授权映射

### 2.5 市场治理不止“上架”，还包括持续监控和必要时下架

正式市场还必须具备：

- 投诉与问题反馈
- 风险冻结
- 版本弃用
- 授权撤销
- 指标监控

### 2.6 第一阶段应先做“可控市场”，而不是完全开放的创作者平台

第一阶段更适合：

- 平台方主导供给
- 企业侧以私有模板和定向分发为主
- 公共市场对象经过强审核

而不是一开始就做完全开放投稿市场。

---

## 三、为什么必须单独写这份文档

前面已经明确：

- 行业解决方案中心并入插件市场
- 方案以插件形式安装
- 企业允许轻编排，但不可扩核

但还缺少一份市场治理文档，来明确：

- 谁能发
- 发什么
- 怎么审
- 怎么卖
- 出问题怎么办

如果这层不写清楚，后面会出现：

1. 公共市场和企业私有模板库混在一起。
2. 企业上传的简单模板与平台官方代码方案拥有同样的“可信外观”。
3. 市场里有可安装对象，但没有评估、文档、支持边界和下架机制。
4. 商业授权、试用、续费、定向分发与安装审核没有统一口径。

所以，这份文档是在回答：

> 平台如何把方案生态做成正式商业市场，而不是简单的资源展示页。

## 四、市场对象分层

## 4.1 `public_market_listing`

面向全平台有权限企业公开可见。

适合：

- 平台官方行业方案
- 平台审核通过的合作伙伴方案
- 平台审核通过的官方连接器包

## 4.2 `managed_private_listing`

由管理端定向分发给指定企业。

适合：

- 某类重点客户专用方案
- 尚未公开发行的试点方案
- 管理端制作后分配给某批企业的模板

## 4.3 `tenant_private_template_listing`

仅企业内可见和可复用。

适合：

- 企业自己搭建的简单工作流模板
- 企业内部运营模板
- 企业本组织内的经验模版

### 4.3.1 这类对象默认不应跨企业公开售卖

如果企业想把自己的模板跨企业公开售卖，建议另走：

- 平台收编
- 所有权与支持责任重定义
- 正式审核与上架流程

而不是直接从企业私有模板一键变成全平台公共商品。

## 五、正式对象模型建议

建议引入以下对象：

| 对象 | 作用 |
|---|---|
| `marketplace_listing` | 市场上架对象 |
| `listing_submission` | 一次上架申请 |
| `review_checklist` | 审核清单 |
| `review_report` | 审核报告 |
| `compatibility_matrix` | 兼容性矩阵 |
| `pricing_binding` | 定价与授权绑定 |
| `trust_badge` | 可信标识 |
| `publish_record` | 发布记录 |
| `suspension_record` | 暂停/下架记录 |
| `listing_feedback` | 投诉、评价、安装反馈 |

## 5.1 `trust_badge` 建议

建议市场中至少区分：

- `platform_official`
- `platform_reviewed`
- `partner_managed`
- `tenant_private_only`
- `pilot_only`

这样企业才能一眼知道：

- 这个东西是谁生产的
- 谁负责支持
- 现在是不是正式稳定版

## 六、准入与审核流程

建议统一采用六步准入流程。

## 6.1 提交 `submission`

提交内容至少包括：

- 上架对象本体
- 功能说明
- 适用行业与场景
- 数据边界说明
- 风险和审批要求
- 文档与示例
- 定价与授权建议

## 6.2 自动检查 `automated_scan`

建议自动检查：

- 插件结构完整性
- 依赖关系
- 未授权代码能力
- 权限声明与作用域声明
- 缺失文档或缺失测试资产

## 6.3 审核 `review`

建议至少分四类审核：

- 技术审核
- 安全与合规审核
- 功能与体验审核
- 商业与支持审核

## 6.4 评估与验收 `evaluation_and_acceptance`

至少要求：

- 关键路径可演示
- 有最小基准结果
- 有限制说明
- 有安装和激活说明

## 6.5 定价与授权绑定 `pricing_and_entitlement_binding`

市场对象正式发布前，应明确：

- 是否可试用
- 哪个套餐可见
- 哪些企业可安装
- 是否按企业、按工作流、按次数收费

## 6.6 发布或驳回 `publish_or_reject`

最终结果不应只有“通过/不通过”两种粗糙状态。

建议至少支持：

- `draft`
- `in_review`
- `pilot_only`
- `published`
- `deprecated`
- `suspended`
- `removed`

## 七、不同发布主体的边界

## 7.1 平台方

可发布：

- 代码型行业方案
- 官方连接器
- 官方嵌入组件
- 官方复杂执行器

## 7.2 合作伙伴

可在平台审核下发布：

- 托管型行业方案
- 托管型连接能力
- 平台认可的市场对象

但必须明确：

- 支持责任
- 安全责任
- 升级责任

## 7.3 企业方

企业默认可发布到自己私有模板库：

- 简单工作流模板
- 简单表单编排
- 内部运营模板

企业默认不可直接发布到公共市场：

- 复杂代码型扩展
- 复杂连接器
- 平台内核插件

这与“企业使用工具 + 提供业务知识，不负责扩核”保持一致。

---

## 八、商业治理与授权

## 8.1 市场对象必须映射正式商业语义

建议每个上架对象至少声明：

- 交付类型
- 授权类型
- 支持等级
- 试用策略
- 升级策略
- 退款或撤销策略说明

## 8.2 商业模式建议

可支持：

- 平台套餐内含
- 独立方案授权
- 定向企业授权
- 试用期授权
- 交付项目绑定授权

## 8.3 定向分发与公共发行必须分开

很多对象只适合：

- 给指定企业
- 给试点企业
- 给某交付项目

不应因为“能安装”就进入公共市场。

---

## 九、持续监控、投诉与下架机制

## 9.1 上架后必须持续观察

建议观察：

- 安装成功率
- 激活成功率
- 运行异常率
- 投诉率
- 卸载率
- 续费率

## 9.2 风险事件处理

市场对象如出现：

- 越权访问
- 数据泄漏
- 高风险误动作
- 大面积故障

应支持：

- 暂停安装
- 暂停新激活
- 冻结部分能力
- 紧急下架

## 9.3 弃用和退役

正式弃用前，建议提供：

- 替代方案
- 迁移说明
- 兼容期
- 企业侧通知

---

## 十、市场透明度要求

市场页面上不应只展示营销文案。

建议正式展示：

- 适用行业
- 适用场景
- 风险等级
- 是否需要审批
- 是否需要连接器
- 是否支持试用
- 是否为官方/审核/试点对象
- 已知限制

这对企业判断是否安装，比单纯介绍页更重要。

## 十二、第一阶段实施建议

第一阶段建议优先落以下机制：

| 能力 | 建议 |
|---|---|
| 市场对象分层 | 公共、定向、企业私有三类先分清 |
| 审核清单 | 至少覆盖技术、安全、文档、商业四类 |
| 信任标识 | 先让企业知道谁负责 |
| 定向分发 | 支持管理端分配给指定企业 |
| 暂停与下架 | 出问题能及时止损 |
| 透明展示 | 风险、依赖、限制、试用口径清楚展示 |

第一阶段的目标不是做一个完全开放的创作者经济平台，而是先让市场里的每一个可安装对象都“来源清楚、能力清楚、责任清楚、边界清楚”。

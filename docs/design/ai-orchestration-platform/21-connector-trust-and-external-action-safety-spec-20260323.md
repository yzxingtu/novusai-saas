# AI 编排与工作流平台连接器可信度与对外动作安全规范（2026-03-23）

## 一、文档目标

本文档用于定义平台中的连接器、外部系统接入、对外写动作、第三方 API 调用、外部平台发布和回写操作，应该如何分级、治理、审批、审计和恢复。

前面的文档已经回答了很多核心问题：

- 什么能力企业能编排，什么能力只能平台托管
- 高风险动作如何审批
- 运行时恢复和补偿怎么做
- 预算、配额和成本怎么守卫

但只要平台要真正接外部世界，就还会遇到更危险的一层问题：

1. 什么样的连接器可信，什么样的不可信。
2. 企业配置一个外部账号后，到底允许做读操作、草稿写入，还是正式写入。
3. 对外写动作怎么防止误发、重发、串企业、串账号。
4. 外部平台返回不确定状态时，平台该重试、补偿、人工接管还是冻结。
5. 连接器升级、凭据变更、平台 API 变更时，如何避免整批流程失控。

所以，这份文档要解决的是：

> 平台如何让“连接外部系统”从一个危险的黑盒，变成可分级、可验证、可审批、可回放的正式能力。

---

## 二、核心结论

### 2.1 连接器不是普通工具，而是高风险边界对象

连接器直接决定平台与外部世界之间如何交换数据和动作。

因此连接器不应被视为普通节点或普通插件能力，而应被视为：

- 权限边界对象
- 风险边界对象
- 凭据边界对象
- 审计边界对象

### 2.2 必须同时治理“连接器可信度”和“动作风险等级”

平台不能只看动作危险不危险，也不能只看连接器是不是官方的。

真正的安全判断至少要联合两套尺度：

1. `connector_trust_level`
2. `action_risk_level`

例如：

- 一个高可信官方连接器，也可能执行高风险外部写动作
- 一个低可信自定义接入，即使只做写草稿，也可能需要更高警惕

### 2.3 外部连接能力必须默认分成“只读、草稿写、正式写、管理写”四层

建议正式区分：

- `external_read`
- `external_draft_write`
- `external_publish_write`
- `external_admin_mutation`

这四层不能混在一个“已连接”状态里。

### 2.4 企业端可以配置连接器实例，但不能扩展连接器内核

这条必须继续和前文保持一致。

企业端可以做：

- 绑定账号
- 配置映射
- 配置可用范围
- 决定哪些流程可以用这个连接器实例

企业端不可以做：

- 写新的连接器驱动
- 改写连接器执行逻辑
- 绕过平台的动作白名单
- 自定义危险协议栈

### 2.5 对外动作必须默认具备五个安全要素

建议正式要求：

1. 身份绑定
2. 作用域绑定
3. 幂等键
4. 回执记录
5. 动作预览

缺一不可。

---

## 三、为什么必须单独写这份文档

前面的文档已经多次提到：

- 高风险写能力应独立为受控能力插件
- 企业端不允许自己做复杂代码型能力
- 外部写动作应尽量走平台托管

但还没有正式回答：

- 什么叫“受控能力插件”
- 什么叫“可信连接器”
- 企业接一个第三方账号后，平台到底允许它做哪些事
- 外部动作如何做预检、审批、回执和补偿

如果这层不单独规范，后面一定会出现：

1. 企业认为“连上账号就什么都能做”。
2. 平台把只读分析连接器和正式发布连接器混成同一种能力。
3. 外部写动作出了问题后，没有统一处理语义。

所以，这份文档本质上是在回答：

> 平台如何把外部连接能力治理成“可信且受控”的正式能力面。

---

## 四、正式对象模型

建议把连接器和外部动作相关对象正式抽出来。

### 4.1 核心对象建议

| 对象 | 作用 |
|---|---|
| `connector_definition` | 一个连接器的正式定义 |
| `connector_version` | 连接器版本 |
| `connector_capability_profile` | 连接器支持的动作和能力画像 |
| `connector_trust_policy` | 连接器可信度规则 |
| `tenant_connector_instance` | 企业绑定的连接器实例 |
| `tenant_connector_credential` | 企业连接器实例使用的凭据绑定 |
| `external_action_intent` | 一次对外动作的执行意图 |
| `external_action_receipt` | 一次对外动作的执行回执 |
| `external_action_policy` | 对外动作的审批、预算、重试和补偿规则 |
| `connector_health_snapshot` | 连接器健康快照 |

### 4.2 为什么要把 `external_action_intent` 独立出来

因为真正危险的不是“连接器存在”，而是“这次要对外做什么”。

例如：

- 发一条草稿
- 正式发布内容
- 修改商品价格
- 创建 CRM 线索
- 撤回已发内容

这些都需要正式意图对象，而不是把参数塞在节点日志里就算了。

---

## 五、连接器分类模型

建议平台正式把连接器分成四类，而不是只有“官方”与“自定义”。

### 5.1 `platform_managed_connector`

定义：

- 平台方开发、维护、审核、升级的正式连接器

特点：

- 可信度最高
- 版本和能力可控
- 适合正式写动作

### 5.2 `solution_managed_connector`

定义：

- 随行业方案插件交付的、由平台审核通过的场景型连接器

特点：

- 依附特定行业方案
- 仍由平台治理升级
- 常用于行业专属 API 场景

### 5.3 `tenant_configured_connector_instance`

定义：

- 企业基于平台已有连接器定义，配置自己的账号、空间、店铺、频道等形成的实例

特点：

- 企业可配置
- 企业不可扩核
- 风险取决于底层连接器定义和实例作用域

### 5.4 `custom_managed_connector`

定义：

- 平台为特定企业或特定行业做的定制托管连接器

特点：

- 需要交付和升级专线
- 不应开放给企业自行开发

---

## 六、连接器可信度模型

建议正式定义 `connector_trust_level`。

### 6.1 建议等级

| 等级 | 含义 |
|---|---|
| `T0_untrusted` | 未审核、不可正式使用 |
| `T1_limited` | 仅允许低风险测试或只读使用 |
| `T2_verified` | 已验证，可用于受限业务场景 |
| `T3_managed` | 平台托管可信，可用于正式业务 |
| `T4_high_assurance` | 高保证等级，适合高价值或高风险关键路径 |

### 6.2 可信度受哪些因素影响

至少建议考虑：

- 是否平台托管
- 是否有正式版本记录
- 是否有动作白名单
- 是否有幂等和回执模型
- 是否有健康监控
- 是否有审计和补偿能力
- 是否经过安全评估

### 6.3 为什么 `trust_level` 不能直接等于“官方/非官方”

因为有些平台自做连接器也可能能力不成熟。

反过来，有些场景型连接器虽然不是平台通用能力，但在特定方案下是经过完整治理的。

所以要用可信度模型，而不是简单的来源标签。

---

## 七、对外动作分类模型

建议平台正式定义 `external_action_class`。

### 7.1 建议分类

| 分类 | 含义 |
|---|---|
| `external_read` | 只读获取外部数据 |
| `external_probe` | 只做探测、预检、校验，不产生业务副作用 |
| `external_draft_write` | 创建草稿、候选项、预发布对象 |
| `external_publish_write` | 正式发布、正式提交、正式写回 |
| `external_admin_mutation` | 对外部系统配置、账号、策略做管理级变更 |

### 7.2 分类和风险等级的关系

建议默认映射：

| 动作分类 | 默认风险等级 |
|---|---|
| `external_read` | `R0-R1` |
| `external_probe` | `R1` |
| `external_draft_write` | `R2` |
| `external_publish_write` | `R3` |
| `external_admin_mutation` | `R4` |

### 7.3 企业简单工作流的开放边界

建议：

- `external_read` 可按授权开放
- `external_draft_write` 受限开放
- `external_publish_write` 默认不开放或必须强审批
- `external_admin_mutation` 不开放

---

## 八、连接器能力画像规范

每个连接器都不应只写“支持某平台”，而应有正式能力画像。

### 8.1 建议字段

| 字段 | 说明 |
|---|---|
| `supports_read` | 是否支持只读 |
| `supports_draft_write` | 是否支持草稿写 |
| `supports_publish_write` | 是否支持正式写 |
| `supports_admin_mutation` | 是否支持管理写 |
| `supports_preflight` | 是否支持执行前探测 |
| `supports_dry_run` | 是否支持干跑 |
| `supports_idempotency` | 是否支持幂等 |
| `supports_receipt` | 是否支持回执 |
| `supports_compensation` | 是否支持补偿 |
| `credential_scope_model` | 凭据作用域模型 |
| `tenant_configurable_fields` | 企业可配置字段 |

### 8.2 为什么必须显式声明

否则后面会出现：

- 前端可以配置
- 运行时才发现不支持幂等
- 审批通过后才发现不支持回执

这会非常危险。

---

## 九、凭据与作用域绑定

### 9.1 凭据不是简单的账号密码存储

平台必须把凭据视为正式边界对象。

建议至少绑定：

- 企业
- 连接器定义
- 外部系统空间
- 可用动作范围
- 生效环境

### 9.2 建议的作用域字段

| 字段 | 说明 |
|---|---|
| `tenant_id` | 所属企业 |
| `connector_definition_id` | 所属连接器 |
| `external_workspace_id` | 外部空间/店铺/账号 |
| `allowed_action_classes` | 允许的动作分类 |
| `environment` | `sandbox` / `production` |
| `status` | `active` / `expired` / `revoked` / `disabled` |

### 9.3 为什么环境必须显式区分

因为很多外部系统都有：

- 沙箱
- 测试号
- 生产号

如果不区分，很容易把测试流程直接打到生产账号上。

---

## 十、对外动作安全五件套

建议平台把每次对外动作都强制落到五个安全要素。

### 10.1 身份绑定 `identity_binding`

必须明确：

- 用的是哪个企业的哪个连接器实例
- 对应的是哪个外部账号/空间

### 10.2 作用域绑定 `scope_binding`

必须明确：

- 这次动作能影响什么对象
- 能影响哪个店铺、账号、频道、业务单元

### 10.3 幂等键 `idempotency_key`

必须尽量提供：

- 平台侧幂等键
- 对外请求幂等标识

### 10.4 回执 `receipt`

必须记录：

- 对方是否接收
- 是否成功执行
- 对方返回了什么业务 ID

### 10.5 动作预览 `action_preview`

必须在执行前可查看：

- 将要做什么
- 影响哪些对象
- 关键字段前后差异

---

## 十一、预检、干跑与正式执行模型

建议平台正式区分三种执行模式。

### 11.1 `preflight`

作用：

- 检查连接器是否健康
- 检查凭据是否有效
- 检查目标对象是否存在
- 检查权限是否足够

### 11.2 `dry_run`

作用：

- 模拟生成本次对外动作包
- 不产生正式副作用
- 可生成预览和审批材料

### 11.3 `commit`

作用：

- 真正执行对外动作

### 11.4 为什么必须三段式

因为高风险动作如果没有 `preflight` 和 `dry_run`，审批人看到的材料和实际执行内容很容易不一致。

---

## 十二、审批、策略与预算联动

### 12.1 对外动作必须同时经过三类判断

建议固定链路：

```text
连接器可信度判断
-> 动作风险与审批判断
-> 预算与成本守卫判断
-> 才允许 commit
```

### 12.2 高风险外部写动作的最低要求

建议至少满足：

- 连接器 `trust_level >= T2_verified`
- 动作有 `preflight`
- 动作有 `action_preview`
- 动作可生成 `external_action_intent`
- 动作回执可追踪

### 12.3 哪些情况应直接 `managed_only`

例如：

- `external_admin_mutation`
- 无幂等保证的正式写动作
- 无回执的高价值动作
- 无法明确作用域绑定的动作

---

## 十三、失败、重试与补偿规则

### 13.1 外部动作失败不能一律自动重试

必须至少先判断：

- 是否有幂等
- 是否已经收到部分回执
- 是否存在未知状态

### 13.2 建议的失败处理矩阵

| 场景 | 默认动作 |
|---|---|
| 只读请求失败 | 自动重试 |
| `preflight` 失败 | 终止或等待人工修复 |
| `dry_run` 失败 | 终止并要求修正 |
| `commit` 明确失败且幂等可重试 | 有限重试 |
| `commit` 状态不明 | 人工接管 |
| `commit` 成功但后续链路失败 | 评估是否补偿 |

### 13.3 补偿不应默认等于“撤销远端动作”

很多外部平台并不支持真正撤销。

更现实的补偿可能是：

- 标记撤回申请
- 创建修正草稿
- 发送更正内容
- 创建人工工单

---

## 十四、连接器健康与冻结机制

### 14.1 连接器应有正式健康状态

建议至少包括：

- `healthy`
- `degraded`
- `unstable`
- `frozen`

### 14.2 什么时候应自动冻结

例如：

- 短时间大量未知状态写动作
- 凭据批量过期
- 外部平台接口签名异常
- 关键回执模型失效

### 14.3 冻结后的语义

建议：

- 新的高风险动作不得再发起
- 已在执行中的实例进入人工接管或等待恢复判断
- 企业运营控制台与管理端都应收到告警

---

## 十五、企业端与管理端的职责边界

### 15.1 管理端负责什么

管理端负责：

- 连接器定义
- 连接器版本
- 可信度审核
- 能力画像
- 高风险动作白名单
- 紧急冻结

### 15.2 企业端负责什么

企业端负责：

- 绑定自己的账号实例
- 管理可用范围
- 决定哪些工作流能用这个实例
- 处理本企业对外动作审批和接管

### 15.3 企业端不能做什么

企业端不能：

- 新增连接器驱动
- 修改连接器动作分类
- 放宽平台定义的可信度规则
- 把正式写动作伪装成草稿写动作

---

## 十六、审计要求

每次外部动作都应至少记录：

- 连接器定义版本
- 企业连接器实例
- 动作分类
- 意图对象
- 审批记录
- 预算快照
- 幂等键
- 回执
- 最终状态

### 16.1 为什么这里的审计要比普通节点更重

因为外部动作一旦出问题，往往：

- 不可逆
- 影响真实业务
- 牵涉第三方平台责任

因此必须比普通生成节点记录得更完整。

---

## 十七、与现有文档的关系

### 17.1 与 `05-approval-and-risk-gate-spec`

`21` 进一步把高风险外部动作的可信度、预检、干跑、回执和补偿规则落地化。

### 17.2 与 `06-solution-plugin-spec`

高风险对外写能力继续建议独立成受控能力插件，再由行业方案插件按授权组合。

### 17.3 与 `16-runtime-execution-graph-and-recovery-spec`

外部动作的未知状态、回执、补偿和人工接管应直接进入运行图治理。

### 17.4 与 `20-runtime-budget-quota-and-cost-guard-spec`

对外动作执行前还应经过预算守卫，尤其是高价值、高成本、高并发外部动作。

## 十八、第一阶段实施建议

### Phase 1：先把“连接器可信度 + 动作分类 + 安全五件套”做出来

优先建设：

- `connector_definition`
- `connector_capability_profile`
- `connector_trust_level`
- `external_action_intent`
- `external_action_receipt`

### Phase 2：再补“预检、干跑、审批和冻结”

补齐：

- `preflight`
- `dry_run`
- 高风险动作审批链
- 连接器健康与冻结机制

### Phase 3：最后补“补偿与高级治理”

补齐：

- 复杂补偿语义
- 企业实例作用域细分
- 平台/方案/企业多层安全策略联动

---

## 十九、关键结论

1. 连接器是平台连接外部世界的高风险边界对象，必须同时治理可信度、能力画像、凭据作用域和对外动作语义。
2. 平台必须联合判断 `connector_trust_level` 和 `action_risk_level`，不能只看动作风险或只看连接器来源。
3. 对外连接能力应至少区分只读、草稿写、正式写和管理写四层，企业简单工作流只能在严格白名单下开放其中低风险层。
4. 每次对外动作都应具备身份绑定、作用域绑定、幂等键、回执和动作预览五个安全要素。
5. 高风险对外动作必须支持 `preflight`、`dry_run`、审批、预算守卫和未知状态人工接管，不能直接“连上就发”。
6. 第一阶段先把可信度模型、动作分类和安全五件套做出来，再逐步补齐预检、冻结、补偿和多层联动治理。

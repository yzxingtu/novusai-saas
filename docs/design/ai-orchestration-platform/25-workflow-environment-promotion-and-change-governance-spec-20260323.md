# AI 编排与工作流平台环境晋级与变更治理规范（2026-03-23）

## 一、文档目标

本文档用于定义 AI 编排与工作流平台中的环境模型、版本晋级机制、变更单元、上线门禁、回滚机制与紧急变更规则。

这份文档要回答的核心问题是：

1. 工作流、方案插件、策略包、连接器配置、Prompt 包到底应该如何从草稿走向正式生产。
2. 平台环境和企业运行环境应该如何拆分，而不是所有东西直接在生产上改。
3. 变更需要经过哪些验证、审批、灰度、观察与回滚步骤。
4. 企业副本、平台原件、方案激活版本和定制版本之间如何避免升级冲突。
5. 平台如何把“能改”变成“可控地改、可追踪地改、可撤销地改”。

本文档是平台级规范，适用于工作流定义、行业方案插件、Agent 绑定、连接器绑定、运行时策略与配置类变更。

---

## 二、核心结论

### 2.1 正式生产环境禁止直接活体编辑

平台必须明确：

- 生产运行的是版本快照，不是当前编辑器里的草稿
- 正式自动触发链路只认发布快照
- 任何高风险变更都必须经过晋级流水线，而不是“改完直接保存生效”

### 2.2 环境治理不只是技术环境，更是业务运行分层

平台不应只理解为传统的：

- 开发环境
- 测试环境
- 生产环境

对 AI 编排平台来说，更重要的是：

- 草稿设计层
- 验证仿真层
- 试运行层
- 正式生产层

也就是说，环境模型应同时承载技术和业务发布语义。

### 2.3 变更单元必须正式建模，不能把所有改动混成一次“发布”

后续至少应区分：

- 工作流定义变更
- 方案插件版本变更
- Prompt 或策略包变更
- 连接器绑定变更
- 知识绑定变更
- 评估基线变更
- 风险审批策略变更

不同变更的门禁和回滚方式不应相同。

### 2.4 企业副本和平台原件必须分层晋级

平台原件升级，不代表企业自动升级。

企业正式环境中的激活版本，必须有自己独立的：

- 升级确认
- 兼容性验证
- 灰度范围
- 回滚入口

否则平台一改，企业全线受影响，后续无法商用。

### 2.5 上线前必须先通过“验证门”而不是只靠人工信心

验证门至少应包括：

- 静态校验
- Schema 校验
- 仿真运行
- 干跑验证
- 基准评估
- 风险和成本检查
- 必要的人工审阅

### 2.6 紧急变更可以走快车道，但不能绕过留痕与回滚设计

事故时可以加速，但不能失去：

- 变更编号
- 责任人
- 影响范围
- 回滚方案
- 事后复盘

## 三、为什么必须单独写这份文档

前面的文档已经定义了：

- 触发与发布
- 方案生命周期
- 交付验收
- 运行图恢复
- 评估门禁
- 成本守卫

但平台仍然缺一层“把所有变更串起来”的正式框架。

如果这层不单独写，后面会出现四类典型问题：

1. 工作流编辑器里保存一下，就和正式运行混在一起。
2. 企业副本、平台原件、插件版本、策略版本的升级关系全部靠人脑记忆。
3. 发布失败时，只能手工临时回改，无法快速回滚到已知稳定快照。
4. 同一个变更既改 Prompt、又改连接器、又改审批，却没有统一变更包和门禁口径。

所以，这份文档是在回答：

> 平台如何把“变更”正式化，避免 AI 编排系统在长期运营中因为频繁改动而逐步失控。

---

## 四、正式环境模型

## 4.1 平台级环境建议

建议平台至少抽象四类正式环境：

| 环境 | 作用 |
|---|---|
| `draft_env` | 编辑、设计、草稿验证 |
| `test_env` | 契约验证、仿真、干跑、自动回归 |
| `staging_env` | 准生产验证、灰度预演、运维观测 |
| `prod_env` | 正式触发、正式执行、正式计费 |

### 4.1.1 `draft_env` 不是运行真相

`draft_env` 中可以频繁调整：

- 节点结构
- Prompt 片段
- 变量映射
- 方案配置

但这些内容不应直接代表生产真相。

生产真相只能来自发布快照。

## 4.2 企业运行环境建议

对企业侧，建议进一步抽象为：

| 环境 | 作用 |
|---|---|
| `tenant_sandbox` | 企业配置验证、样本试跑、培训演示 |
| `tenant_pilot` | 小范围灰度、真实低风险试运行 |
| `tenant_prod` | 正式业务运行 |

### 4.2.1 为什么企业也需要环境分层

因为企业真正关心的不是代码分支，而是：

- 这套流程现在能不能给真实业务用
- 会不会动到真实外部系统
- 风险审批是否已经配置完整
- 出问题时影响的是试点用户还是全量业务

所以企业环境必须服务于“业务启用治理”。

## 4.3 环境对象模型建议

建议正式引入以下对象：

| 对象 | 作用 |
|---|---|
| `environment_profile` | 环境定义与能力边界 |
| `promotion_pipeline` | 某类资源的晋级流水线 |
| `change_set` | 一次变更包 |
| `deployment_snapshot` | 可运行快照 |
| `rollback_snapshot` | 可回退目标 |
| `freeze_window` | 冻结窗口 |
| `promotion_approval` | 晋级审批 |
| `post_release_observation` | 发布后观察记录 |

## 五、变更单元与版本包

## 5.1 变更单元应正式拆分

建议至少支持以下变更单元：

| 变更单元 | 示例 |
|---|---|
| `workflow_definition_change` | 节点拓扑、变量映射、节点配置调整 |
| `solution_plugin_change` | 行业方案插件版本升级 |
| `prompt_package_change` | Prompt 模板、系统提示、Few-shot 更新 |
| `policy_bundle_change` | 审批策略、风险分级、预算守卫调整 |
| `connector_binding_change` | 凭据绑定、字段映射、动作白名单调整 |
| `knowledge_binding_change` | 知识库绑定、召回配置、知识范围变化 |
| `evaluation_suite_change` | 基准集、阈值、盲测规则更新 |

## 5.2 一次发布可以包含多个变更单元，但必须形成正式 `change_set`

`change_set` 至少应包含：

- 变更类型清单
- 影响对象清单
- 目标环境
- 依赖版本
- 风险等级
- 验证结果
- 审批记录
- 回滚方案

### 5.2.1 为什么不能只有一个“发布按钮”

因为实际发布往往不是单点变化。

例如一次上线可能同时涉及：

- 新工作流版本
- 新知识绑定
- 新审批规则
- 新连接器映射

如果没有统一 `change_set`，后续根本无法复盘“到底改了什么”。

## 六、正式晋级流水线

建议所有正式变更统一经过以下阶段。

## 6.1 阶段一：草稿冻结 `draft_freeze`

进入晋级前，应先冻结本次候选内容：

- 生成不可变候选快照
- 记录依赖版本
- 锁定本次评估口径

## 6.2 阶段二：静态校验 `static_validation`

至少检查：

- Schema 是否完整
- 变量引用是否闭合
- 节点端口是否匹配
- 未授权技能或连接器是否被引用
- 风险节点是否缺审批策略

## 6.3 阶段三：仿真与干跑 `simulation_and_dry_run`

在测试环境中进行：

- 运行图仿真
- 关键路径样本回放
- 外部写动作干跑
- 成本和预算估算

## 6.4 阶段四：评估门禁 `evaluation_gate`

至少检查：

- 关键指标是否达到基线阈值
- 是否出现明显回归
- 是否引入新的高风险失败模式
- 是否超出预算或时延范围

## 6.5 阶段五：审批与放行 `promotion_approval`

不同风险等级对应不同放行角色。

例如：

- 低风险模板微调可由方案负责人放行
- 影响高风险动作的变更应要求平台治理或企业负责人确认

## 6.6 阶段六：灰度与观察 `staged_release`

正式环境中不建议直接全量切换。

建议支持：

- 按企业灰度
- 按场景灰度
- 按触发类型灰度
- 按流量比例灰度

并记录：

- 成功率
- 审批命中率
- 异常率
- 成本变化
- 业务结果变化

## 6.7 阶段七：确认或回滚 `confirm_or_rollback`

观察期结束后必须做正式决策：

- 确认升级为稳定版本
- 回滚到上一稳定快照
- 继续延长灰度观察

## 七、回滚、补丁与紧急变更

## 7.1 回滚必须是快照级，而不是手工回忆级

平台应支持回滚到：

- 某个工作流稳定版本
- 某个方案激活版本
- 某个策略包版本
- 某个连接器绑定快照

而不是要求操作人员自己手工改回去。

## 7.2 紧急补丁 `hotfix` 需要专用通道

建议单独定义：

- `hotfix_change_set`
- `hotfix_reason`
- `hotfix_expiry`
- `hotfix_review_postmortem`

即：

- 可以快速上
- 但必须补齐审计和复盘

## 7.3 冻结窗口管理

建议平台支持：

- 大促冻结
- 财务结算冻结
- 企业关键周期冻结
- 平台升级冻结

冻结窗口内，不同类型变更可设置：

- 完全禁止
- 只允许低风险
- 只允许紧急补丁

## 八、平台原件、企业激活版与企业副本的关系

## 8.1 三层版本模型应继续保持

建议继续维持：

- `platform_source_version`
- `tenant_activated_version`
- `tenant_derived_version`

### 8.1.1 晋级规则建议

- 平台原件可以继续迭代，但不直接覆盖企业激活版
- 企业激活版升级应经过企业确认
- 企业副本升级要做兼容性校验，避免把企业定制覆盖掉

## 8.2 兼容性矩阵必须进入正式治理

后续至少要能回答：

- 某个工作流版本依赖哪个插件版本
- 某个插件版本依赖哪个连接器能力
- 某个策略包版本是否兼容当前审批模型
- 某个知识绑定方式是否兼容当前 Prompt 包

没有兼容性矩阵，就不能做可靠晋级。

## 九、角色与职责

| 角色 | 主要职责 |
|---|---|
| `solution_designer` | 方案草稿设计、候选版本准备 |
| `platform_reviewer` | 验证结果审阅、晋级确认 |
| `platform_governor` | 风险规则、冻结与例外裁决 |
| `delivery_manager` | 企业项目型升级协调 |
| `tenant_owner` | 企业正式升级授权 |
| `tenant_operator` | 观察灰度结果、异常反馈 |

### 9.1 责任边界

仍应坚持：

- 平台方负责平台原件和托管生产能力的晋级
- 企业方负责企业激活和企业副本的启用决策
- 平台方不能替企业做日常生产切换决定

## 十一、第一阶段实施建议

第一阶段不必上来就做完整 DevOps 平台，但以下能力必须具备：

| 能力 | 建议 |
|---|---|
| 草稿与发布快照分离 | 正式运行只认发布快照 |
| 候选变更包 | 用 `change_set` 聚合一次上线影响 |
| 自动静态校验 | 节点、变量、依赖、授权、风险策略检查 |
| 仿真与干跑 | 对关键路径与外部动作做预演 |
| 基准门禁 | 发布前至少过一套最小评估集 |
| 灰度发布 | 按企业或流量做小范围试放 |
| 回滚快照 | 一键回到上一稳定版本 |
| 紧急补丁通道 | 有快车道，也有强留痕 |

第一阶段目标不是打造一个复杂的发布中台，而是先把平台从“谁都能改生产”推进到“所有生产变化都有版本、有门禁、有回滚”。

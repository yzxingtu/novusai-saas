# AI 编排与工作流平台任务编排模块插件化策略（2026-03-23）

## 一、文档目标

本文专门回答一个平台级问题：

> 任务编排 / 工作流能力不是每个企业都需要，是否可以做成“可安装、可授权、可禁用、可卸载”的模块。

本文基于当前仓库已有插件系统现状核查，给出正式设计结论，而不是只给抽象建议。

重点回答：

1. 现有插件系统是否足以承载“任务编排模块”。
2. 哪些部分适合做成插件，哪些部分不适合硬塞进插件。
3. 如何设计，才能让模块后续真的容易启停、授权、卸载。
4. 该模块与行业解决方案插件、插件市场、企业授权之间应该是什么关系。

---

## 二、核心结论

### 2.1 一句话结论

现有插件系统可以支撑“任务编排模块”做成可安装 / 可卸载的可选模块，但前提是把它定义成一个**自包含的产品模块插件**，而不是把整个平台编排内核粗暴做成一个可以无限侵入宿主的超级插件。

这里的“平台内核常驻”是**平台职责分层**，不是这次模块实施要去改主项目。

本模块第一版必须遵守硬约束：

- 所有业务代码、页面、API、迁移、任务都只落在 `backend/plugins/workflow-orchestration/**`
- 不允许为了实现本模块去修改 `backend/app/**`、主系统前端源码或其他宿主目录
- 如果当前插件沙箱内做不到，就要么在插件内自包含实现，要么明确延期，不允许先开宿主口子

### 2.2 推荐结构

推荐采用三层结构：

- 平台内核常驻
- 任务编排模块插件按需安装
- 行业解决方案插件依赖任务编排模块插件

### 2.3 这意味着什么

这意味着：

- 不是每个企业默认开通任务编排
- 平台可以单独售卖“任务编排模块”
- 购买了该模块的企业，才继续购买或激活依赖它的行业方案包
- 企业停用时可以先撤销授权，再决定是否禁用或卸载插件本体

### 2.4 “轻易卸载”要分三级理解

平台里“卸载”至少要拆成三种动作：

| 动作 | 目标 | 结果 |
|---|---|---|
| 企业级撤权 | 某个企业不再使用模块 | 企业端菜单、API、运行入口立即不可用 |
| 平台级禁用 | 平台暂时停用该模块 | 所有企业入口关闭，但插件文件和数据保留 |
| 平台级卸载 | 物理移除该模块 | 插件扩展、插件记录、插件自有表和文件被清理 |

真正决定模块是否“可拔插”的，不是有没有 `uninstall` 按钮，而是边界是否设计干净。

### 2.5 零宿主落地原则

针对本模块，必须再补一条执行级原则：

- 平台内核只作为概念层存在，不作为本次研发改造清单
- 任务编排模块的第一版实现不能向主项目落任何业务文件
- 文档里提到的审批、审计、附件、计量等平台公共能力，只能作为“未来可统一收敛的方向”
- 如果某项能力当前没有稳定插件能力承接，就不能以“先给主项目补一个扩展口”为理由进入第一版范围

## 三、现有插件系统能力核查结论

结合当前仓库插件框架，已有能力足以支撑“可选产品模块”的基本生命周期。

| 能力项 | 当前现状 | 对任务编排模块的意义 |
|---|---|---|
| 生命周期 Hook | 支持 `install / enable / disable / uninstall / upgrade` | 满足模块生命周期管理 |
| 运行时闸门 | 插件执行前会做 `enabled / scope / license` 校验 | 满足按企业授权启用 |
| 前端页面 | 支持 `admin` / `tenant` 插件页面 | 可挂管理端和企业端编排页面 |
| API 分发 | 支持统一插件 API dispatcher | 可承载模块后端接口 |
| 权限与菜单 | 启用时同步、禁用 / 卸载时回收 | 可做模块级菜单与 RBAC |
| 技能 / 任务 / 通知 / Hook | 已支持 | 可挂编排专属技能、调度、通知 |
| 插件依赖 | 支持 `dependencies.plugins` | 行业方案插件可依赖编排模块 |
| 数据隔离 | 默认只允许插件自有 `px_{plugin}_*` 表 | 有利于可卸载，但限制深侵入 |
| 热卸载 | 中间件 / consumer 有重启要求 | 设计上应避免把模块核心建立在这两类扩展上 |

### 3.1 结论解释

这说明插件系统已经具备“可选产品模块”的核心基础设施，但它更适合承载**边界清晰的业务模块**，不适合承载**无限制修改主系统行为的超级插件**。

---

## 四、为什么不能把“整个平台编排内核”都粗暴做成纯插件

如果任务编排模块需要以下能力，纯插件化的收益会迅速下降：

- 直接读写大量宿主核心业务表
- 在宿主任意路由前缀下注入专属页面
- 依赖中间件深度拦截所有请求
- 依赖 Celery consumer 长驻逻辑且要求完全热卸载
- 无边界地修改 Agent、审批、权限、审计等基础模型

原因不是插件系统“不够强”，而是当前插件系统本来就故意做了约束：

- 数据库默认只允许访问插件自有表
- 前端插件页面路径有限制
- 部分扩展类型可以停用，但不保证零重启彻底拔除
- 插件通过受控上下文访问系统，而不是拿到宿主原始 root 权限

这其实是好事。因为你的目标是“可装可卸、可按企业售卖”，而不是“插件无限大”。

## 五、推荐分层模型

### 5.1 平台内核常驻

这里说的“常驻”是平台层职责划分，不代表当前要为任务编排模块去增改主项目文件。

以下能力不建议做成可卸载模块：

- 多租户与认证鉴权
- RBAC 与资源作用域控制
- 插件市场、插件生命周期、License 与 runtime gate
- `Agent -> Skill -> AIGateway` 基础链路
- 审计、日志、通知、附件、指标
- 通用审批引擎
- 通用任务调度与事件机制
- 通用策略引擎与预算 / 配额治理

这些能力属于平台公共底座，不是“任务编排专属”。

### 5.2 任务编排模块插件

这一层才是应该插件化的对象。建议它拥有：

- 管理端编排工作台
- 企业端编排与运行控制台
- 工作流模板管理
- 工作流版本、发布、回滚、环境晋级
- 运行实例、节点运行、产物记录
- 编排专属的 API、菜单、权限资源
- 编排专属的技能、调度任务、通知模板
- 编排专属配置和企业级配置
- 编排专属的行业依赖关系声明

换句话说，用户感知到的“任务编排产品”应尽量收敛在这个插件里。

### 5.3 行业解决方案插件

行业方案插件不应该自己重复实现一套编排运行时，而应该：

- 通过 `dependencies.plugins` 依赖任务编排模块插件
- 提供行业模板、预设 Agent、Prompt、规则包、看板和资产 Schema
- 复用任务编排模块的页面能力和运行能力
- 只补行业资源，不再复制平台内核

### 5.4 结构图

```text
┌──────────────────────────────┐
│          平台内核             │
│ 租户 / 权限 / 插件框架 / AI链路 │
│ 审批 / 审计 / 通知 / 配额 / 日志 │
└──────────────┬───────────────┘
               │ 提供公共基础能力
               v
┌──────────────────────────────┐
│      任务编排模块插件         │
│ Builder / Runtime / Release  │
│ Run / NodeRun / Artifact UI  │
│ Admin + Tenant Pages / APIs  │
└──────────────┬───────────────┘
               │ 被依赖
               v
┌──────────────────────────────┐
│       行业解决方案插件        │
│ 模板 / Agent预设 / Prompt包  │
│ 行业规则 / 行业看板 / 资产模型 │
└──────────────────────────────┘
```

## 六、为了“轻易卸载”，模块边界必须这样设计

### 6.1 数据边界

任务编排模块的业务表应尽量全部落在插件自有表，例如：

- `px_workflow_orchestration_definitions`
- `px_workflow_orchestration_versions`
- `px_workflow_orchestration_runs`
- `px_workflow_orchestration_node_runs`
- `px_workflow_orchestration_artifacts`
- `px_workflow_orchestration_tenant_settings`
- `px_workflow_orchestration_solution_bindings`

原则：

- 编排模块拥有自己的事实表
- 对宿主核心能力采用引用和 ID 关联
- 需要宿主信息时通过受控服务或只读能力获取
- 不直接把编排核心事实散落到宿主通用表里

### 6.2 路由边界

编排模块所有前端页面和 API 都应走插件标准入口：

- `/admin/plugins/workflow-orchestration/*`
- `/tenant/plugins/workflow-orchestration/*`
- `/admin/plugins/workflow-orchestration/api/*`
- `/tenant/plugins/workflow-orchestration/api/*`

不要依赖宿主任意位置注入专属业务路由。这样禁用或卸载时入口收口才干净。

### 6.3 权限边界

编排模块的权限应全部通过插件 manifest 声明，例如：

- 模块可见
- 模板管理
- 运行查看
- 运行重试
- 发布
- 回滚
- 审批配置
- 企业构建
- 企业运行操作

不要把这些权限散落成宿主固定权限。否则后面就卸不干净。

### 6.4 运行时边界

为了支持“无需大改主系统即可卸载”，建议：

- 核心运行入口走插件 API dispatcher
- 模块内部状态推进走插件任务扩展或模块服务
- 高风险审批继续复用宿主通用审批引擎
- 模块不要把关键执行链路建立在插件 `middleware` 上
- 模块不要把关键事件消费建立在必须热卸载的 `consumer` 上

换句话说：

- 页面、API、权限、定时任务、技能都适合插件化
- 深中间件、全局拦截、重型常驻消费者不适合作为该模块的核心支柱

## 七、模块安装、启用、授权、卸载的正式语义

### 7.1 平台安装

管理端把“任务编排模块插件”安装到平台。

这一步解决的是“平台有没有这个产品”。

### 7.2 平台启用

管理端启用插件后：

- 菜单权限同步
- 运行时 gate 可放行
- 模块页面与 API 可被访问
- 模块技能与计划任务被注册

这一步解决的是“平台当前是否允许这个模块运行”。

### 7.3 企业授权

管理端把模块授权给指定企业后：

- 企业满足 `scope` 和 `license` 校验
- 企业端才可见该模块页面
- 行业方案插件才可在该企业上继续激活

这一步解决的是“哪个企业可以买、能不能用”。

### 7.4 平台禁用

管理端禁用插件后：

- 所有企业入口关闭
- 模块菜单权限撤销
- 模块技能停用
- 模块周期任务停用
- 插件数据保留，便于稍后重新启用

这一步适合“暂停服务”，不适合“删除产品”。

### 7.5 平台卸载

管理端卸载插件后：

- 先禁用
- 执行 `on_uninstall`
- 清理扩展点
- 删除插件菜单权限记录
- 删除插件 Skill、通知、任务记录
- 备份并清理插件自有表
- 删除插件记录和物理文件

这一步适合“真正移除产品模块”。

### 7.6 热卸载限制

需要明确写死一条规则：

- 如果模块使用了插件 `middleware` 或 `consumer`，停用后仍可能需要服务重启才能完全拔除运行时痕迹。

因此必须把“可热卸载”当作架构约束，而不是卸载时再碰运气。

## 八、面向商业化的推荐插件分类

现有文档里行业方案插件已经定义为 `solution_plugin`。

为了让“任务编排模块”这类跨行业可选产品更清晰，建议在**平台分类语义**上新增一类正式插件类型：

- `product_module_plugin`

但在当前仓库第一版落地时，这仍然只是一种**产品语义分类**，不是要求主项目立即新增一个 manifest 一等字段。

第一版建议继续：

- 以标准插件包形态交付
- 在 `plugin.yaml -> extensions.custom` 中声明 `module_kind` 等元数据
- 不因等待宿主新增正式字段而阻塞插件实现

它和其他插件类型的区别如下：

| 类型 | 目标 | 典型示例 |
|---|---|---|
| `capability_plugin` | 提供单点技术能力 | 存储驱动、联网能力、抓取能力 |
| `product_module_plugin` | 提供跨行业可售卖产品模块 | 任务编排、语义指标层、BI 助手 |
| `solution_plugin` | 提供行业化业务方案 | 短视频增长方案、电商经营分析方案 |
| `ui_plugin` | 提供纯 UI 扩展 | 控件面板、可视化组件 |
| `content_plugin` | 提供模板、知识、内容资产 | Prompt 包、知识包、素材包 |

这样分层后关系才清楚：

- 任务编排不是行业方案
- 任务编排也不只是一个小能力插件
- 它是跨行业可售卖的“产品模块插件”

## 十、什么必须留在平台内核，什么可以放进模块插件

| 领域 | 建议放置位置 | 原因 |
|---|---|---|
| 多租户、认证、RBAC | 平台内核 | 全平台通用基础设施 |
| 插件市场、插件 License、runtime gate | 平台内核 | 所有模块都依赖 |
| Agent、Skill、AIGateway 基础链路 | 平台内核 | AI 公共底座 |
| 通用审批引擎 | 平台内核 | 不止编排模块复用 |
| 审计、日志、通知、附件、配额 | 平台内核 | 治理底座 |
| 工作流 Builder UI | 编排模块插件 | 不是所有企业都需要 |
| 工作流模板与版本 | 编排模块插件 | 模块自有业务域 |
| Run、NodeRun、Artifact 运营页面 | 编排模块插件 | 模块自有业务域 |
| 行业模板与行业预设 | 行业方案插件 | 行业外挂资源 |
| 企业复杂代码型工作流交付 | 平台方通过模块插件交付 | 企业端不可扩内核 |

## 十一、最小落地策略

为了降低后续返工，推荐按以下顺序推进：

1. 先在产品语义上把“任务编排”定义为产品模块，并通过 `extensions.custom` 声明 `module_kind`。
2. 编排模块第一版只走插件标准能力：页面、API、权限、任务、技能、配置、插件自有表。
3. 第一版不要依赖插件 `middleware` 作为核心链路。
4. 第一版不要依赖必须热卸载的 `consumer` 作为核心状态机。
5. 行业方案插件从第二阶段开始通过 `dependencies.plugins` 依赖编排模块。
6. 企业授权先走“平台安装一次 + 按企业授权可见 / 可用”的模式。
7. 第一版严格执行“零宿主落地”：不修改 `backend/app/**`，不把插件业务落入主系统源码。
7. 卸载前默认执行备份 / 导出策略，避免企业误删运行数据。

## 十二、最终建议

如果你的目标是：

- 不是每个企业都要任务编排
- 想做成一个可卖、可授权、可启停、可卸载的模块
- 后续行业方案还能挂在它上面

那么当前插件系统是可以承接的。

但正确做法不是：

- 把所有编排基础设施都塞进一个超级插件
- 让插件深度侵入宿主所有核心模块

正确做法是：

- 平台内核保留公共底座
- 任务编排做成 `product_module_plugin`
- 行业方案再作为 `solution_plugin` 依赖它

这样才同时满足：

- 可商业化
- 可按企业授权
- 可轻量卸载
- 可长期演进

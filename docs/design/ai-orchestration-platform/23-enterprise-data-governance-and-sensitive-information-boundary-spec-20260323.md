# AI 编排与工作流平台企业数据治理与敏感信息边界规范（2026-03-23）

## 一、文档目标

本文档用于定义 AI 编排与工作流平台中的企业数据治理规则，以及敏感信息在各类容器、运行链路、人机协作链路中的正式边界。

这份文档要回答的核心问题是：

1. 企业数据在平台中应如何正式分类。
2. 不同级别的数据可以进入哪些容器，不能进入哪些容器。
3. Prompt、RAG、`page_context`、Artifact、审批包、评估集、日志、导出链路分别该如何控边界。
4. 平台方、企业方、人机协作通道在访问数据时应遵守什么规则。
5. 数据治理如何与前面已经定义的策略引擎、审批闸门、连接器安全、评估治理和知识注入机制对齐。

本文档是平台级规范，不绑定某个行业，但会直接约束后续所有行业方案插件、企业工作流、连接器、运营控制台和评估体系。

---

## 二、核心结论

### 2.1 企业数据必须被正式分类，而不是默认都能给 AI 看

平台不能再沿用“只要企业上传了，就默认可以喂给模型”的思路。

后续所有进入平台的数据对象，都应至少携带：

- `data_classification`
- `sensitivity_tags`
- `owner_scope`
- `allowed_use_purposes`
- `retention_policy`

没有治理元数据的数据对象，不应进入正式运行链路。

### 2.2 多企业隔离只是底线，数据还必须做对象级作用域约束

仅有 `tenant_id` 还不够。

平台还必须回答：

- 这份数据属于哪个方案、哪个工作流、哪个运行实例。
- 谁可以在什么用途下读取它。
- 它是否允许进入 Prompt、评估集、日志、导出包、审批包。

所以正式治理对象不能只停留在“租户隔离”，还必须进入“对象级用途治理”。

### 2.3 Prompt、RAG、日志、评估、导出都不是天然安全容器

很多系统把“是否能存数据库”当作安全边界，这不够。

真正的高风险点往往是：

- 直接注入 Prompt
- 检索召回片段
- 运行日志与调试日志
- 审批预览包
- 评估样本和盲测集
- 导出、下载、分享链路

这些链路都必须单独治理。

### 2.4 敏感信息治理的原则是最小化、脱敏化、目的限定，而不是完全禁用

平台不是要禁止企业使用真实业务数据，而是要正式区分：

- 什么数据可以原样进入正式系统
- 什么数据只能经过脱敏后进入
- 什么数据只能以引用方式进入
- 什么数据只能在审批后进入
- 什么数据在当前阶段一律不能进入模型上下文

### 2.5 人机协作通道也必须继承数据边界

审批人、编辑人、运营人、平台交付人员，看到的数据不应相同。

也就是说：

- 协作通道不只是“谁来处理”，还必须回答“他能看到什么粒度的数据”
- 同一条运行实例，在 `review_lane`、`approval_lane`、`incident_lane` 中可见字段可能不同
- 平台方默认不能读取企业敏感业务明文，除非进入有审计的例外通道

### 2.6 第一阶段应采用保守治理，不要一开始就做全自动数据自由流转

第一阶段推荐采用：

- 先分类
- 先标记
- 先做默认拒绝
- 先做脱敏和审计
- 再逐步放开按用途授权

而不是反过来。

## 三、为什么现在必须单独写这份文档

前面的文档已经分别定义了：

- 企业知识注入
- 审批和风险闸门
- 运行时策略引擎
- 连接器可信治理
- 评估数据集治理
- 人机协作通道

但这些文档都隐含了同一个更底层的问题：

> 到底哪些数据可以在平台里怎么流动。

如果这一层不正式写清楚，后面一定会出现三类问题：

1. 企业上传的业务数据被无差别用于 Prompt、评估、日志和导出，最终边界失控。
2. 同一份敏感数据在多个容器中重复复制，既增加成本，也增加泄漏面。
3. 平台方和企业方都以为自己看的是“正常必要信息”，但实际上看到了不该看的明文。

所以，这份文档是在回答：

> 数据在平台里不是“能不能存”的问题，而是“在什么作用域、以什么粒度、为了什么目的、能走到哪一步”的问题。

---

## 四、正式数据分类模型

建议平台统一采用“分级 + 标签”双轨治理，而不是只用一个粗糙字段。

## 4.1 基础分级 `data_classification`

建议至少定义五级。

| 等级 | 含义 | 示例 |
|---|---|---|
| `public` | 可公开传播的数据 | 已发布宣传文案、公开活动信息、公开商品介绍 |
| `internal` | 企业内部可流转，但风险较低 | 内部 SOP、普通运营报表、非敏感配置 |
| `confidential` | 非公开业务数据，泄漏后有明显商业影响 | 未发布产品计划、经营指标、供应商价格、投放策略 |
| `sensitive` | 涉及个人、交易、合同、关键经营信息的数据 | 用户手机号、订单明细、退款原因、未公开财务数据 |
| `regulated` | 受更严格法规或合同控制的数据 | 支付信息、身份信息、证件、医疗信息、受监管合规数据 |

### 4.1.1 分级不是审批替代物

分级只回答数据本身的风险等级，不直接决定运行时是否允许使用。

真正是否允许使用，还要叠加：

- 用途
- 容器
- 操作类型
- 当前协作通道
- 当前角色

## 4.2 敏感标签 `sensitivity_tags`

建议在基础等级之外，再用标签表达更细粒度特征，例如：

- `pii`
- `financial`
- `contract`
- `credential`
- `trade_secret`
- `biometric`
- `compliance_hold`
- `export_controlled`

这样平台后续才能做细粒度策略，例如：

- `credential` 不允许进入 Prompt
- `pii` 允许进入企业内部审批预览，但默认脱敏显示
- `trade_secret` 不允许进入跨企业基准集

## 4.3 数据治理对象建议

平台中至少要治理以下容器和对象：

| 对象 | 说明 |
|---|---|
| `structured_record` | 业务表中的结构化记录 |
| `knowledge_document` | 企业文档、说明书、SOP、FAQ |
| `retrieval_chunk` | 文档切片、向量召回片段 |
| `runtime_context_payload` | 运行时输入、触发 payload、`page_context` |
| `artifact` | 草稿、报告、执行建议、摘要、分析结论 |
| `approval_packet` | 审批预览包、证据包、风险摘要 |
| `evaluation_sample` | 评估集、盲测集、标注样本 |
| `log_event` | 运行日志、错误日志、审计日志 |
| `export_bundle` | 导出文件、下载包、交接包 |
| `memory_item` | 会话记忆、偏好记忆、长期学习信号 |

## 4.4 每个对象必须具备的治理元数据

建议后续所有正式对象统一具备以下字段或等价字段：

| 字段 | 作用 |
|---|---|
| `tenant_id` | 企业隔离主键 |
| `owner_scope` | 所属层级，例如平台、方案、企业、工作流、运行实例 |
| `data_classification` | 基础分级 |
| `sensitivity_tags` | 敏感标签集合 |
| `allowed_use_purposes` | 允许用途，如运行、审批、检索、评估、导出 |
| `masking_policy` | 显示脱敏规则 |
| `retention_policy` | 保留时长和清理方式 |
| `export_policy` | 是否允许导出、谁可导出 |
| `audit_level` | 需要记录的审计粒度 |
| `source_trace` | 数据来源追踪信息 |

## 五、作用域、隔离与所有权边界

## 5.1 平台应同时支持五类作用域维度

建议后续所有数据对象至少能映射到以下维度中的一部分：

| 维度 | 含义 |
|---|---|
| `platform_scope` | 平台级规则、平台样板、平台标准资产 |
| `solution_scope` | 某个行业方案插件或方案包 |
| `tenant_scope` | 某家企业 |
| `workflow_scope` | 某个工作流、模板或节点 |
| `run_scope` | 某次运行实例、某次审批、某次协作任务 |

### 5.1.1 为什么必须引入 `run_scope`

因为很多数据本质上只适合存在于一次运行中，例如：

- 当前订单快照
- 当前选中的页面记录
- 本次审批说明
- 本次分析过程中的临时推导

这类数据如果被错误升级成长期资产，后续就会污染记忆、评估和推荐。

## 5.2 所有权与管理权应继续遵守前面已确认原则

平台仍然坚持：

- 平台方管理平台资产
- 企业方管理企业资产
- 谁的工作流谁管理
- 谁的数据谁负责确认

这意味着：

- 平台方不能把企业数据默认转成平台训练资产
- 企业方不能把平台基线规则私自降级
- 方案方不能越权读取未授权企业明文

## 5.3 多企业隔离之外，还要有对象级最小可见原则

即使都在同一家企业里，也不代表所有人都应看到全部字段。

例如：

- `tenant_operator` 可能只需要订单摘要，不需要完整身份信息
- `tenant_editor` 需要看草稿上下文，但不需要看连接器凭据
- `tenant_approver` 需要看风险摘要和关键金额，但不一定需要看全部原始记录

所以可见性应由“角色 + 通道 + 用途 + 字段策略”共同决定。

## 六、各类数据流动链路的正式规则

## 6.1 `page_context` 与运行时上下文

`page_context`、触发事件 payload、运行时变量属于高风险链路，因为它们最容易被直接塞进 Prompt。

正式规则建议如下：

- 只允许注入当前任务必需字段，禁止整行整表原样塞入
- 必须保留现有字节预算思路，并扩展到更多上下文通道
- 高敏字段默认不进入 `page_context`
- 如确需进入，必须先走字段级脱敏或引用化
- 运行结束后，这类临时上下文默认不升级为长期资产

## 6.2 Prompt 注入链路

Prompt 是最需要保守治理的容器之一。

建议正式规定：

- `credential`、受监管原文、完整身份标识、完整支付信息默认禁止进入 Prompt
- `sensitive`、`regulated` 数据进入 Prompt 时必须满足“必要 + 最小 + 有审计”
- 能用结构化变量表达的，不要改写成大段自然语言
- 能用引用 ID 的，不要直接拼接明文
- 同一个对象不能在一次运行中重复多处拼接，避免泄漏面膨胀

## 6.3 RAG 与检索片段链路

知识库和检索片段不是天然低风险区。

建议正式规定：

- 检索前先按 `tenant_id`、`owner_scope`、`allowed_use_purposes` 过滤
- 召回片段应继承原文档分级与敏感标签
- 召回结果在进入 Prompt 前仍需走二次脱敏和预算裁剪
- 高敏文档默认不进入共享评估集和跨方案样本池
- 企业停用某文档后，其召回资格应立即撤销

## 6.4 Artifact 与输出链路

AI 输出的 Artifact 既是结果，也是二次传播载体。

建议 Artifact 默认继承其主要输入中的最高风险等级，除非经过显式降级审查。

例如：

- 用敏感订单数据生成的分析报告，不应自动被视为低风险摘要
- 用受监管原文生成的建议结论，仍需按上游等级治理导出和分享

## 6.5 审批包与证据预览链路

审批节点需要看证据，但不代表必须看全部明文。

建议审批包分三层视图：

- `summary_view`：风险摘要、关键指标、推荐动作
- `evidence_view`：必要证据片段，默认脱敏
- `raw_view`：仅在高权限例外通道中可见

这样才能兼顾可审批与最小暴露。

## 6.6 评估数据集与基准套件链路

评估集是非常容易被忽略的泄漏面。

正式规则建议如下：

- 评估样本必须登记来源、用途、版本、脱敏方式
- 默认不允许直接复用生产明文作为通用评估集
- 企业专属评估集必须留在企业边界内
- 平台级基准套件优先使用脱敏、合成、经批准抽样的数据
- `regulated` 与 `credential` 类数据不得进入平台通用盲测集

## 6.7 日志、调试、可观测性链路

日志默认应视为“低信任扩散容器”。

因此建议：

- 运行日志记录 ID、计数、状态、分类，不记录原始高敏内容
- 调试日志默认关闭原文输出
- 异常栈中如包含用户输入，必须先裁剪或脱敏
- 观测指标优先记录聚合统计，不记录可逆原文

## 6.8 导出、下载、交接和分享链路

导出是边界最容易失守的环节之一。

建议后续统一治理：

- 导出必须检查 `export_policy`
- 导出文件应标记来源、时间、操作人、导出范围
- 敏感导出默认需要审批或二次确认
- 临时下载链接必须有时效
- 平台交接包默认不包含企业高敏明文，除非进入正式交付例外流程

## 6.9 连接器和外部动作链路

连接器外发数据必须同时接受：

- 数据分级约束
- 动作风险约束
- 凭据作用域约束

正式要求应包括：

- 凭据只能以引用形式使用，不能明文拼接进入 Prompt
- 外部写动作仅发送必要字段
- 外发前应生成预检摘要和字段列表
- 高敏字段外发应可审计、可追踪、可回执

## 七、敏感信息处理机制

## 7.1 字段级脱敏是基础能力，不是可选增强

建议平台统一提供字段级策略，例如：

- `mask_full`
- `mask_partial`
- `hash_only`
- `tokenize_reference`
- `omit_entirely`

后续各容器按策略复用，不允许每个页面、每个工作流自己写一套。

## 7.2 Prompt 与审批包应优先使用“引用化”而不是“全文复制”

例如：

- 用 `customer_ref`
- 用 `order_ref`
- 用 `document_ref`
- 用 `credential_ref`

再通过受控工具按需读取局部字段。

这比一次性把整份原文塞进上下文更可控。

## 7.3 高敏字段应区分“可存储”和“可见”

某些字段出于业务需要可以被系统存储，但不代表：

- 能被 LLM 看到
- 能被编辑人看到
- 能被导出
- 能进入评估样本

因此“系统内存在”与“AI 可见”必须明确拆开。

## 7.4 平台应支持按用途脱敏，而不是只有一种全局脱敏

同一字段在不同用途下应允许不同策略：

- 审批用
- 运行用
- 导出用
- 评估用
- 调试用

否则企业要么觉得平台过度严格无法用，要么会因为一刀切放开而失控。

## 八、人机协作与访问边界

## 8.1 平台方默认看治理信息，不看企业敏感业务明文

平台方角色默认应看到：

- 运行状态
- 风险等级
- 错误码
- 摘要化证据
- 资源占用

而不是企业完整业务明文。

需要查看明文时，应进入：

- 审计留痕
- 临时授权
- 指定范围
- 明确目的

的正式例外流程。

## 8.2 企业方不同协作通道应看到不同粒度

建议至少区分：

- `review_lane` 看摘要和必要证据
- `approval_lane` 看风险摘要、关键金额、关键字段
- `editor_lane` 看草稿和编辑上下文
- `operator_lane` 看运行态、异常态和恢复信息
- `incident_lane` 仅在事故处理中扩展可见范围

## 8.3 协作动作应绑定字段级审计

后续如支持高敏对象查看，应至少审计：

- 谁查看了
- 通过哪个协作通道查看
- 查看了哪些字段
- 目的是什么
- 持续了多久

## 九、审计、留存与删除要求

## 9.1 保留策略必须按容器区分

不同容器不应共用一种保留时长。

例如：

- `runtime_context_payload` 应短期保留
- `artifact` 可能需要业务保留
- `log_event` 应按审计等级保留
- `evaluation_sample` 应按版本和用途保留
- `memory_item` 应按记忆类型和同意状态保留

## 9.2 删除语义必须正式定义

平台至少应区分：

- 逻辑删除
- 物理删除
- 脱敏替换
- 引用失效
- 审计保留但业务不可见

否则后续企业会频繁遇到“删了但其实还在别的地方”的问题。

## 9.3 数据清理应联动上下游容器

例如某数据对象被删除或失效后，应考虑联动：

- RAG 索引撤销
- Artifact 关联标记
- 评估样本失效
- 记忆项失效
- 导出资格撤销

## 十、与平台其他治理内核的关系

本规范不是独立存在的，它需要与前面文档形成联动。

### 10.1 与运行时策略引擎联动

策略引擎需要回答：

- 某对象能否进入当前运行
- 能进入哪个容器
- 是否必须脱敏
- 是否需要审批
- 是否允许导出或外发

### 10.2 与审批和风险闸门联动

风险等级不仅来自动作本身，也来自所处理数据的敏感等级。

同一个外部动作，在处理 `internal` 数据和 `regulated` 数据时，不应有相同门槛。

### 10.3 与知识注入规范联动

知识注入规范解决“知识从哪来、怎么进”。

本文档解决“这些知识和数据进来后，能以什么粒度和目的被使用”。

### 10.4 与评估治理联动

评估治理解决“怎么构建评估资产”。

## 十一、第一阶段实施建议

第一阶段不建议一开始就做极复杂的数据合规平台，而应先把最容易失守的口子堵住。

## 11.1 第一阶段必须落地的能力

| 能力 | 建议 |
|---|---|
| 数据分级字段 | 为关键对象补齐 `data_classification` 与 `sensitivity_tags` |
| 作用域字段 | 为知识、Artifact、评估样本、记忆对象补齐 `owner_scope` |
| `page_context` 预算 | 延续现有预算思路，扩展到更多运行时上下文 |
| Prompt 脱敏 | 高敏字段默认不直接注入 Prompt |
| 审批包分层视图 | 摘要、证据、原文三层拆开 |
| 导出审计 | 记录导出人、范围、时间、对象 |
| 评估登记 | 评估样本必须登记来源和脱敏方式 |
| 日志裁剪 | 调试日志默认不落高敏原文 |
| 连接器字段白名单 | 外发字段最小化，凭据只走引用 |

## 11.2 第一阶段不建议做得过重的部分

暂时不建议把第一阶段目标定成：

- 全字段自动识别一切合规类型
- 全量自动 DLP 编排
- 自动跨法域规则引擎
- 自动判断所有摘要是否可视为低敏

第一阶段更现实的目标是：

> 先把平台从“数据去哪都不清楚”推进到“每份关键数据都知道它是什么、能去哪、谁能看、谁看过”。

## 11.3 对后续行业方案插件的直接要求

所有行业方案插件在进入正式市场前，至少要提交：

- 关键数据对象清单
- 数据分级与标签表
- Prompt 注入字段清单
- 外部动作字段清单
- 审批视图字段清单
- 评估样本来源与脱敏说明

没有这份说明的方案，不应进入正式交付和商业授权流程。

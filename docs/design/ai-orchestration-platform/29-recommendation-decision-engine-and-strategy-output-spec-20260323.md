# AI 编排与工作流平台推荐决策引擎与策略输出规范（2026-03-23）

## 一、文档目标

本文档用于定义平台中的推荐决策引擎，规范平台如何基于企业数据、知识资产、外部情报和运行反馈，输出可执行、可解释、可审阅的策略建议。

这份文档要回答的核心问题是：

1. 平台如何把“分析”“推荐”“预测”“行动建议”做成统一能力，而不是散落在各个 Agent 里。
2. 推荐结果应该长什么样，包含哪些证据、假设、置信度和行动建议。
3. 推荐引擎如何与工作流、审批、评估、预算、外部联网分析联动。
4. 什么建议可以自动执行，什么建议只能作为人工决策草案。
5. 平台如何让推荐能力跨行业复用，而不是只服务某个具体业务。

本文档是平台级规范，适用于经营分析、价格建议、库存建议、内容选题建议、投放建议、排班建议、下一步行动建议等场景。

---

## 二、核心结论

### 2.1 推荐决策引擎应成为平台内核能力，而不是某个行业方案里的临时 Prompt

平台必须正式承认：

- 推荐不是普通聊天回答
- 推荐不是简单报表解释
- 推荐更不是随便给一段建议文本

真正可商用的推荐能力，必须有：

- 结构化输入
- 结构化输出
- 证据链
- 假设说明
- 置信度和风险提示
- 人工审阅与反馈闭环

### 2.2 推荐结果默认应是“决策草案”，不是“自动真相”

平台推荐的默认定位应是：

- 供人判断的策略草案
- 供工作流引用的结构化建议
- 供审批链审阅的行动备选项

而不是一上来就自动下单、自动改价、自动发布。

### 2.3 推荐能力应同时吸收三类信息

建议统一汇聚三类输入：

1. 企业内部数据
2. 企业知识和业务规则
3. 外部情报与联网分析

这三类缺一不可。

只看内部数据，会缺行业和时效性。

只看联网信息，会脱离企业实际供给和约束。

只看知识规则，会变成静态问答。

### 2.4 推荐不应只给一个答案，而应给一组可比较方案

建议推荐引擎默认输出：

- `primary_option`
- `alternative_options`
- `do_nothing_option`

并明确：

- 适用条件
- 预计收益
- 风险与成本
- 为什么排在这个顺序

### 2.5 推荐能力应与执行能力正式解耦

推荐引擎负责：

- 预测
- 评分
- 排序
- 解释
- 生成行动建议草案

是否执行，应由：

- 工作流策略
- 风险分级
- 审批节点
- 企业操作人

共同决定。

### 2.6 第一阶段应优先做“强建议、弱自动”

第一阶段推荐：

- 强化推荐质量、证据和解释
- 弱化自动写回外部系统
- 让平台先成为可信的“决策助手”

而不是急于成为“无审核自动决策系统”。

## 三、为什么必须单独写这份文档

前面的文档已经把：

- 编排能力
- 数据契约
- 知识注入
- 联网与连接器
- 审批与风险

都铺好了。

但平台还缺一层真正承接“业务智能价值”的中枢：

> 这些能力最后如何组合成一套可审阅、可落地的决策建议系统。

如果不单独写这份文档，后面会出现：

1. 每个行业方案各自写一套推荐逻辑，没有统一输出口径。
2. AI 给出一句建议，但没有证据、没有假设、没有置信度，业务方不敢用。
3. 联网查询做了，但与企业供给、库存、预算、风险根本没结合。
4. 预测、推荐、执行混在一起，最后既不可解释，也难以审批。

所以，这份文档是在回答：

> 平台如何把“AI 帮企业做判断”正式产品化。

---

## 四、推荐决策引擎的正式定位

建议把推荐决策引擎定义为平台中的一个正式子系统，用于输出：

- 预测结果
- 候选方案
- 决策排序
- 行动草案
- 解释与证据

## 4.1 引擎不等于单一模型

推荐决策引擎应被视为一条组合流水线，而不是一个 LLM 调用。

它可以组合：

- 规则引擎
- 指标计算
- 检索增强
- 外部情报抓取
- LLM 解释与方案生成
- 预测或评分模块
- 场景仿真模块

## 4.2 典型能力类型

建议至少抽象以下能力类型：

| 能力类型 | 示例 |
|---|---|
| `trend_forecast` | 趋势预测、需求预测、增长预测 |
| `anomaly_explanation` | 异常波动解释 |
| `opportunity_detection` | 机会点发现 |
| `pricing_plan` | 定价建议 |
| `inventory_plan` | 备货建议、补货建议 |
| `schedule_plan` | 上线时间、发布窗口、排班建议 |
| `content_topic_plan` | 选题建议、素材方向建议 |
| `next_best_action` | 下一步业务动作建议 |
| `budget_allocation` | 预算或资源分配建议 |

这些能力是通用型的，行业方案只是在其上做参数化和知识化。

---

## 五、正式对象模型建议

建议引入以下对象：

| 对象 | 作用 |
|---|---|
| `recommendation_request` | 一次推荐请求 |
| `decision_context_snapshot` | 决策上下文快照 |
| `constraint_profile` | 业务约束画像 |
| `evidence_bundle` | 证据包 |
| `forecast_result` | 预测结果 |
| `candidate_strategy` | 候选策略 |
| `scenario_option` | 情景方案 |
| `recommendation_scorecard` | 评分卡 |
| `action_draft` | 行动草案 |
| `recommendation_feedback` | 推荐反馈结果 |

## 5.1 `decision_context_snapshot`

建议至少包含：

- 目标对象
- 时间窗口
- 指标快照
- 数据鲜度
- 企业规则和约束
- 当前预算和配额
- 相关历史结果

## 5.2 `constraint_profile`

推荐引擎不能只看“想要什么”，还要看“不能做什么”。

建议至少包括：

- 风险上限
- 预算上限
- 审批要求
- 品牌禁区
- 外部供应约束
- 人员与资源约束

## 5.3 `candidate_strategy`

每个候选策略建议至少包含：

- 策略标题
- 适用场景
- 核心动作
- 预计收益
- 预计成本
- 风险说明
- 前置条件

## 六、推荐引擎的标准流水线

建议统一为十步。

## 6.1 第一步：目标界定 `goal_scoping`

首先明确：

- 要解决什么问题
- 指标目标是什么
- 时间范围是什么
- 结果用于建议还是用于自动执行准备

## 6.2 第二步：内部数据汇聚 `internal_data_ingestion`

汇聚：

- 业务结构化数据
- 运行结果数据
- 历史 Artifact 与反馈
- 关键指标序列

## 6.3 第三步：知识与规则汇聚 `knowledge_and_rule_merge`

引入：

- 企业知识
- 业务规则
- 审批策略
- 约束条件

## 6.4 第四步：外部情报汇聚 `external_intelligence_fetch`

引入：

- 行业趋势
- 平台规则变化
- 节点时间因素
- 外部热点与时效性信息

### 6.4.1 外部情报必须记录鲜度和来源

建议每次外部情报写入证据包时都登记：

- 来源
- 抓取时间
- 适用地域
- 可信度

## 6.5 第五步：特征与指标构建 `feature_building`

把原始数据转成更适合决策的指标。

例如：

- 环比、同比、滚动窗口
- 价格区间弹性
- 历史采用率
- 内容效果标签分布
- 供需匹配指数

## 6.6 第六步：候选策略生成 `candidate_generation`

候选策略可以来自：

- 规则模板
- 行业样板
- LLM 方案生成
- 历史高表现方案召回

## 6.7 第七步：规则过滤与风险裁决 `policy_filtering`

过滤掉：

- 违反审批政策的
- 超预算的
- 违反品牌规则的
- 违反数据边界的
- 缺少必要前提的

## 6.8 第八步：情景仿真与预测 `scenario_simulation`

对保留下来的候选策略进行：

- 结果预测
- 资源消耗预测
- 风险暴露预测
- 最坏/基准/乐观三种情景估计

## 6.9 第九步：评分与排序 `scoring_and_ranking`

建议从多维度打分：

- 预期收益
- 可执行性
- 风险
- 成本
- 解释性
- 数据充分性

## 6.10 第十步：产出与反馈 `publish_and_feedback`

最终输出：

- 推荐摘要
- 候选方案
- 证据包
- 行动草案
- 审批建议

并接收：

- 采用
- 驳回
- 改写
- 实际结果

---

## 七、推荐结果的标准输出格式

推荐结果不应只有一段自然语言。

建议至少包含以下结构：

| 字段 | 说明 |
|---|---|
| `recommendation_type` | 推荐类型 |
| `decision_goal` | 决策目标 |
| `time_horizon` | 时间范围 |
| `primary_option` | 首选方案 |
| `alternative_options` | 备选方案 |
| `assumptions` | 关键假设 |
| `evidence_summary` | 证据摘要 |
| `confidence_level` | 置信度 |
| `risk_notes` | 风险提示 |
| `expected_outcome` | 预计结果 |
| `action_draft` | 可执行草案 |
| `requires_approval` | 是否需审批 |

## 7.1 为什么必须保留 `do_nothing_option`

推荐系统不能默认“必须做点什么”。

有时最好的建议反而是：

- 继续观察
- 暂不执行
- 等更多信息

所以建议保留显式的 `do_nothing_option`，避免系统因追求“看起来积极”而产生伪建议。

## 八、推荐、执行与审批的边界

## 8.1 推荐默认是草案层

推荐结果默认只进入：

- 企业运营控制台
- 审批包
- 工作流后续节点输入
- 复盘与反馈池

## 8.2 进入执行链路前仍需经过正式门禁

即使推荐质量很高，若后续要触发：

- 改价
- 下单
- 内容发布
- 外部写入

仍需经过：

- 风险裁决
- 预算检查
- 审批或确认

## 8.3 `deterministic`、`hybrid`、`agentic` 三种用法

| 模式 | 推荐引擎角色 |
|---|---|
| `deterministic` | 生成规则内建议和评分 |
| `hybrid` | AI 补充方案解释和候选策略 |
| `agentic` | 在约束内自主探索方案空间，但仍输出结构化可审阅结果 |

## 九、反馈闭环与长期学习

## 9.1 推荐系统最重要的学习信号

建议优先沉淀：

- 是否被采用
- 被采用后是否被修改
- 驳回原因
- 执行结果
- 实际业务指标变化

## 9.2 推荐反馈不应直接等于原始聊天记忆

推荐引擎应优先使用：

- 结构化反馈
- 明确标签
- 指标变化

而不是依赖零散对话内容。

这与前面的记忆与长期学习边界保持一致。

## 9.3 推荐系统需要“解释资产”而不只是“历史答案”

长期价值更高的不是存下每次说了什么，而是存下：

- 为什么推荐这个
- 哪类证据支撑最强
- 什么情况下会失败
- 哪些约束最常导致驳回

## 十、跨行业复用原则

为避免平台退化成单行业工具，推荐引擎应坚持：

## 10.1 通用能力层

平台内核提供：

- 趋势预测
- 机会发现
- 候选方案生成
- 多目标评分
- 证据包装配

## 10.2 行业参数层

行业方案插件提供：

- 行业特征
- 行业约束
- 指标权重
- 行业样板策略

## 10.3 企业个性层

企业提供：

- 自己的数据
- 自己的品牌规则
- 自己的资源边界
- 自己的审批和预算约束

三层叠加后，才能既通用又真正有业务价值。

## 十二、第一阶段实施建议

第一阶段建议优先做成：

| 能力 | 建议 |
|---|---|
| 推荐请求与结果 Schema | 统一所有行业方案输出口径 |
| 证据包和假设说明 | 让建议可解释、可审阅 |
| 候选方案排序 | 不只给一个答案 |
| 基础外部情报接入 | 支持时效性分析 |
| 人工采用/驳回反馈 | 建立长期学习信号 |
| 行动草案但不自动提交 | 先做强建议、弱自动 |

第一阶段的目标应是：

> 让平台先成为可信、可解释、可回看、可复盘的推荐决策助手，再逐步向更高自治推进。
